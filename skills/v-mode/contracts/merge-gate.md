# 병합 관문

## 판정식

관리자가 병합 명령을 내리기 바로 전에, 지금 원격에서 읽은 대상 `T = (H, B)`로 판정한다. `H`는 `gh pr view <PR> --json headRefOid`, `B`는 `git ls-remote origin refs/heads/<기준 브랜치>`로 읽는다.

**병합 가능 ⇔ G1 ∧ G2 ∧ G3 ∧ G4 ∧ G5**

| | 조건 | 근거 |
| --- | --- | --- |
| G1 | 필수 수용 기준이 모두 대상 `T`에서 **통과**다 | [evidence.md](evidence.md) "수용 기준 집계" |
| G2 | 그 통과 기록의 수용 기준 버전이 모두 현재 버전이다 | evidence.md "유효와 통과" 3 |
| G3 | 대상 `T`에 대한 `scope: review` rev 시도 가운데(`취소` 제외) 가장 나중에 배정된 시도의 결론이 `통과`이고, 5단계에서 `지금 고침`으로 정한 지적이 모두 해결됐고, `사용자에게 물음`으로 둔 결정이 남아 있지 않다. 그 시도가 `보관됨`·`정리됨`이 아니면 G3 실패 | orchestra `SKILL.md` 5단계, `fixes.md` |
| G4 | 이 작업에 배정된 모든 시도가 정산됐다 | [archive.md](archive.md) "정산" |
| G5 | G1·G3에 쓴 rev 시도가 모두 역할 자격을 채웠다 | evidence.md "역할 자격" |

- G1·G3에 쓰는 시도는 판정할 때마다 보관 확인([archive.md](archive.md) "보관 확인")을 다시 한다. 실패하면 archive.md "보관 손상"으로 간다.
- 수용 기준이 모두 통과여도 G3이 깨지면 병합하지 않는다. 수용 기준 재실행은 코드 검토를 대신하지 않는다.
- 하나라도 깨지면 병합하지 않는다. 깨진 조건, 해당 수용 기준, 이유를 `state.md`의 관문 기록에 적고 사용자에게 보고한다.

## 진입점

orchestra 6단계에서 병합으로 들어가는 모든 지점이다. **대상이 바뀌면 새 대상마다 rev `scope: review` 시도를 반드시 하나 배정한다.** 그 시도가 G1의 rev 기록과 G3의 결론을 함께 만든다.

| 진입점 | 대상이 바뀌나 | 할 일 |
| --- | --- | --- |
| 자동 병합(6단계 3 직전) | 검토 뒤 바뀌지 않았으면 아니다 | 관문 |
| "병합해" 지시 | 지시 대기 동안 기준 브랜치가 갔을 수 있다 | `B`를 다시 읽는다. 같으면 관문. 바뀌었으면 rebase 행 |
| rebase 뒤(6단계 2) | 바뀐다 | rebase 작업자(impl)가 필수 수용 기준 전부 → rev `review` 시도(rebase diff, 브랜치 전체, 필수 수용 기준 전부) → 관문 |
| 지금 고침 수정 뒤(`fixes.md` 재검토) | 바뀐다 | 수정 작업자(impl)가 필수 수용 기준 전부 → 재검토를 rev `review` 시도로 맡긴다(지적 해결 판정 + 수정 diff + 브랜치 전체 + 필수 수용 기준 전부) → 관문 |
| 사소 수정 뒤(`fixes.md` 관리자 확인) | 바뀐다 | 관리자 확인은 지적 해결 기록으로만 남긴다. 수정 작업자(impl)가 필수 수용 기준 전부 → rev `review` 시도(수정 diff + 필수 수용 기준 전부) → 관문 |
| "리뷰 반영해" 뒤 | 바뀐다 | 5단계 판정 → 수정 → 위 "지금 고침 수정 뒤"와 같다 |

rev `review` 시도의 결과가

- `수정 필요`면: 5단계로 돌아간다.
- 필수 수용 기준에 `막힘`이 있으면: evidence.md "막힘"을 따른다. 대상이 그대로면 그 수용 기준만 `rerun-only`로 다시 맡길 수 있다. G3은 그 `review` 시도의 결론을 쓴다.

첫 버전에서 관리자는 검토자 역할을 맡지 않는다. orchestra `tiers.md` 검토 목록의 `관리자` 항목은 건너뛰고 다음 항목을 고른다.

## 병합 명령과 확인

병합 방법은 프로젝트 설정을 따른다. `merge`·`squash`·`rebase` 모두 쓸 수 있다. 다만 `rebase`는 아래 3의 경쟁 확인을 할 수 없어 "확인 불가"로 기록된다. 경쟁 확인이 필요하면 `merge`나 `squash`를 권한다.

```
gh pr merge <PR> --<병합 방법> --match-head-commit <H> --subject "<제목> (<이슈 표시>)"
```

1. `--match-head-commit`은 판정한 `H`와 원격 head가 다르면 병합을 거부한다. 거부되면 대상이 바뀐 것이므로 진입점 표로 돌아간다.
2. 명령이 성공해도 병합 완료가 아니다(병합 대기열에 들어갔을 수 있다). `gh pr view <PR> --json state,mergedAt,mergeCommit,baseRefName`을 읽는다.
   - `state`가 `MERGED`이고 `baseRefName`이 기준 브랜치면: **병합 확인**. `state.md`에 적고 orchestra 6단계 4로 간다.
   - 아니면: `state.md` 첫 줄을 `병합 대기`로 두고 다음에 깨어날 때 다시 읽는다. 그사이 head가 바뀌면 진입점 표로 돌아간다.
3. **기준 브랜치 경쟁**: 판정과 병합 사이에 다른 병합이 들어왔는지 본다.
   - `merge`: 병합 커밋의 첫 부모가 `B`와 다르면 경쟁.
   - `squash`: squash 커밋의 부모가 `B`와 다르면 경쟁.
   - `rebase`: 확인 불가로 기록.
   경쟁이면 `state.md`에 "기준 브랜치 경쟁(<B> 검증, <실제 부모> 위에 병합)"을 적고 사용자에게 알린다. 관문은 이 경쟁까지 막는다고 주장하지 않는다.

## 사람이 직접 병합한 경우

"병합됐어" 지시를 받으면:

1. `gh pr view <PR> --json state,headRefOid,mergeCommit,baseRefName`을 읽는다. `state`가 `MERGED`가 아니면 병합되지 않은 것이다. 사용자에게 알리고 아무것도 정리하지 않는다.
2. `MERGED`이고 `baseRefName`이 기준 브랜치면, 병합된 head를 `state.md`의 마지막 관문 통과 기록의 `H`와 비교한다.
   - 같으면: 정상으로 보고 정리를 이어 간다.
   - 다르거나 관문 통과 기록이 없으면: "관문 미확인 병합"으로 보고한다. 되돌리지 않는다.

지금 원격 기준 브랜치는 그 병합 때문에 이미 앞으로 갔으므로 사후 판정에 쓰지 않는다.
