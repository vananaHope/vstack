# 병합 관문

## 판정식

관리자가 병합 명령을 내리기 바로 전에, 지금 읽은 대상 `T = (H, B)`로 판정한다. 병합 위치(orchestra 프로젝트 설정 "병합" 절)가 `원격`(기본)이면 원격에서 읽는다. `H`는 `gh pr view <PR> --json headRefOid`, `B`는 `git ls-remote origin refs/heads/<기준 브랜치>`다. `로컬`이면 아래 "로컬 병합" 1로 로컬에서 읽는다.

**병합 가능 ⇔ G1 ∧ G2 ∧ G3 ∧ G4 ∧ G5**

| | 조건 | 근거 |
| --- | --- | --- |
| G1 | 필수 수용 기준이 모두 대상 `T`에서 **통과**다 | [evidence.md](evidence.md) "수용 기준 집계" |
| G2 | 그 통과 기록의 수용 기준 버전이 모두 현재 버전이다 | evidence.md "유효와 통과" 3 |
| G3 | 대상 `T`에 대한 `scope: review` rev 시도 가운데(`취소` 제외) 가장 나중에 배정된 시도의 결론이 `통과`이고, 5단계에서 `지금 고침`으로 정한 지적이 모두 해결됐고, `사용자에게 물음`으로 둔 결정이 남아 있지 않다. 그 시도가 `보관됨`·`정리됨`이 아니면 G3 실패 | orchestra `SKILL.md` 5단계, `fixes.md` |
| G4 | 이 작업에 배정된 모든 시도가 정산됐다 | [archive.md](archive.md) "정산" |
| G5 | G1·G3에 쓴 rev 시도가 모두 역할 자격을 채웠다 | evidence.md "역할 자격" |

- G1·G3에 쓰는 시도는 판정할 때마다 보관 확인([archive.md](archive.md) "보관 확인")을 다시 한다. 실패하면 archive.md "보관 손상"으로 간다.
- 수용 기준이 모두 통과여도 G3이 깨지면 병합하지 않는다. 수용 기준 재실행은 코드 검토를 대신하지 않는다.
- 하나라도 깨지면 병합하지 않는다. 깨진 조건, 해당 수용 기준, 이유를 `state.md`의 관문 기록에 적고 사용자에게 보고한다.

## 진입점

orchestra 6단계에서 병합으로 들어가는 모든 지점이다. **대상이 바뀌면 새 대상마다 rev `scope: review` 시도를 반드시 하나 배정한다.** 그 시도가 G1의 rev 기록과 G3의 결론을 함께 만든다.

| 진입점 | 대상이 바뀌나 | 할 일 |
| --- | --- | --- |
| 자동 병합(6단계 3 직전) | 검토 뒤 바뀌지 않았으면 아니다 | 관문 |
| "병합해" 지시 | 지시 대기 동안 기준 브랜치가 갔을 수 있다 | `B`를 다시 읽는다. 같으면 관문. 바뀌었으면 rebase 행 |
| rebase 뒤(6단계 2) | 바뀐다 | rebase 작업자(impl)가 필수 수용 기준 전부 → rev `review` 시도(rebase diff, 브랜치 전체, 필수 수용 기준 전부) → 관문 |
| 지금 고침 수정 뒤(`fixes.md` 재검토) | 바뀐다 | 수정 작업자(impl)가 필수 수용 기준 전부 → 재검토를 rev `review` 시도로 맡긴다(지적 해결 판정 + 수정 diff + 브랜치 전체 + 필수 수용 기준 전부) → 관문 |
| 사소 수정 뒤(`fixes.md` 관리자 확인) | 바뀐다 | 관리자 확인은 지적 해결 기록으로만 남긴다. 수정 작업자(impl)가 필수 수용 기준 전부 → rev `review` 시도(수정 diff + 필수 수용 기준 전부) → 관문 |
| "리뷰 반영해" 뒤 | 바뀐다 | 5단계 판정 → 수정 → 위 "지금 고침 수정 뒤"와 같다 |

rev `review` 시도의 결과가

- `수정 필요`면: 5단계로 돌아간다.
- 필수 수용 기준에 `막힘`이 있으면: evidence.md "막힘"을 따른다. 대상이 그대로면 그 수용 기준만 `rerun-only`로 다시 맡길 수 있다. G3은 그 `review` 시도의 결론을 쓴다.

첫 버전에서 관리자는 검토자 역할을 맡지 않는다. orchestra `tiers.md` 검토 목록의 `관리자` 항목은 건너뛰고 다음 항목을 고른다.

## 병합 명령과 확인

병합 방법은 프로젝트 설정을 따른다. `merge`·`squash`·`rebase` 모두 쓸 수 있다. 다만 `rebase`는 아래 3의 경쟁 확인을 할 수 없어 "확인 불가"로 기록된다. 경쟁 확인이 필요하면 `merge`나 `squash`를 권한다.

```
gh pr merge <PR> --<병합 방법> --match-head-commit <H> --subject "<제목> (<이슈 표시>)"
```

1. `--match-head-commit`은 판정한 `H`와 원격 head가 다르면 병합을 거부한다. 거부되면 대상이 바뀐 것이므로 진입점 표로 돌아간다.
2. 명령이 성공해도 병합 완료가 아니다(병합 대기열에 들어갔을 수 있다). `gh pr view <PR> --json state,mergedAt,mergeCommit,baseRefName`을 읽는다.
   - `state`가 `MERGED`이고 `baseRefName`이 기준 브랜치면: **병합 확인**. `state.md`에 적고 orchestra 6단계 4로 간다.
   - 아니면: `state.md` 첫 줄을 `병합 대기`로 두고 다음에 깨어날 때 다시 읽는다. 그사이 head가 바뀌면 진입점 표로 돌아간다.
3. **기준 브랜치 경쟁**: 판정과 병합 사이에 다른 병합이 들어왔는지 본다.
   - `merge`: 병합 커밋의 첫 부모가 `B`와 다르면 경쟁.
   - `squash`: squash 커밋의 부모가 `B`와 다르면 경쟁.
   - `rebase`: 확인 불가로 기록.
   경쟁이면 `state.md`에 "기준 브랜치 경쟁(<B> 검증, <실제 부모> 위에 병합)"을 적고 사용자에게 알린다. 관문은 이 경쟁까지 막는다고 주장하지 않는다.

## 사람이 직접 병합한 경우

"병합됐어" 지시를 받으면:

1. `gh pr view <PR> --json state,headRefOid,mergeCommit,baseRefName`을 읽는다. `state`가 `MERGED`가 아니면 병합되지 않은 것이다. 사용자에게 알리고 아무것도 정리하지 않는다.
2. `MERGED`이고 `baseRefName`이 기준 브랜치면, 병합된 head를 `state.md`의 마지막 관문 통과 기록의 `H`와 비교한다.
   - 같으면: 정상으로 보고 정리를 이어 간다.
   - 다르거나 관문 통과 기록이 없으면: "관문 미확인 병합"으로 보고한다. 되돌리지 않는다.

지금 원격 기준 브랜치는 그 병합 때문에 이미 앞으로 갔으므로 사후 판정에 쓰지 않는다.

## 로컬 병합

병합 위치가 `로컬`일 때 위 "병합 명령과 확인"과 "사람이 직접 병합한 경우"를 대신한다. 이슈마다 PR을 만들지 않고, 관문을 통과한 대상을 관리자가 로컬 기준 브랜치에 병합한다. 판정식(G1~G5)과 진입점 표는 그대로다. PR이 없으므로 진입점 표의 "리뷰 반영해" 행은 생기지 않는다. 기준 브랜치가 기본 브랜치면 쓰지 않는다(orchestra `SKILL.md` "기준 브랜치"의 병합 위치). 이 길은 돌려 보지 않았다.

`X`는 기준 브랜치가 체크아웃된 checkout이다(orchestra `SKILL.md` "기준 브랜치"의 pull하는 곳). 체크아웃된 곳이 없으면 병합하지 않고 사용자에게 알린다.

1. **대상 읽기**: `H` = `git rev-parse refs/heads/<작업 브랜치>`. 작업 worktree의 `git rev-parse HEAD`도 `H`이고 `git status --porcelain`이 비어야 한다. `B` = `git rev-parse refs/heads/<기준 브랜치>`.
2. **병합 전 확인**: `X`가 기준 브랜치에 있고(`git -C X symbolic-ref --short HEAD`) `git -C X status --porcelain`이 비었다. `git merge-tree --write-tree <B> <H>`가 충돌 없이 트리 `W`를 낸다. 충돌이면 병합하지 않고 진입점 표의 rebase 행으로 간다.
3. **병합 명령**: 판정을 기록한 직후 1을 다시 읽어 `H`·`B`가 판정한 값과 같을 때만 한다. 다르면 진입점 표로 돌아간다. 이 다시 읽기가 원격의 `--match-head-commit`을 대신한다. 커밋 메시지 제목은 `<제목> (<이슈 표시>)`이고, 본문은 orchestra `pr-template.md` 본문이다(`Closes` 줄 대신 이슈 표시를 적는다). PR이 없으므로 이 커밋 메시지가 이슈의 검증 기록이다.
   - `merge`: `git -C X merge --no-ff -F <메시지 파일> <H>`
   - `squash`: `git -C X merge --squash <H>` 뒤 `git -C X commit -F <메시지 파일>`
   - `rebase`는 쓰지 않는다. 병합 커밋 하나로 4를 확인할 수 없기 때문이다.

   명령이 실패하면 `git -C X merge --abort`(squash면 `git -C X reset --merge`)로 되돌리고 사용자에게 알린다. 관리자는 충돌을 풀지 않는다.
4. **병합 확인**: 새 tip `M` = `git rev-parse refs/heads/<기준 브랜치>`. `M`의 첫 부모가 `B`이고, `M`의 트리가 `W`이고, `merge`면 둘째 부모가 `H`다. 맞으면 관문 기록의 결과를 `로컬 병합 확인(<M>)`으로 적는다. 대기열이 없으므로 `병합 대기`를 거치지 않는다.
   - 첫 부모가 `B`가 아니면(판정과 병합 사이에 다른 커밋이 들어왔다) "기준 브랜치 경쟁(<B> 검증, <실제 부모> 위에 병합)"을 적고 사용자에게 알린다. 첫 부모는 `B`인데 트리가 `W`와 다르면 "트리 불일치"를 적고 알린다. 어느 쪽이든 되돌리지 않는다. 관문은 이 경쟁까지 막는다고 주장하지 않는다.
5. **끊겼을 때**: 관문 통과 줄은 있는데 결과가 `로컬 병합 확인`이 아니면, 기준 브랜치 tip을 본다. tip이 `B`이고 `X`가 깨끗하면 병합하지 않은 것이므로 1부터 다시 한다. tip이 `B`인데 `X`가 깨끗하지 않으면 병합 도중 끊긴 것이다. `squash`이고 작업 트리 변경이 없고(`git -C X diff --quiet`) 스테이징된 트리(`git -C X write-tree`)가 `git merge-tree --write-tree <B> <H>`의 `W`와 같으면 squash 커밋만 남은 것이므로 3의 메시지로 `git -C X commit -F <메시지 파일>`을 하고 4로 확인한다. 그 밖이면 되돌리지 않고 사용자에게 알린다(버릴지는 사용자가 정한다). tip의 첫 부모가 `B`면 그 tip을 `M`으로 4를 한다. 그 밖이면 사용자에게 알린다.
6. **사람이 직접 병합했을 때**: "병합됐어"면 기준 브랜치에서 그 작업을 합친 커밋 `M`을 찾는다(`merge`면 둘째 부모가 `H`인 커밋, `squash`면 사용자에게 묻는다). `M`의 트리가 `git merge-tree --write-tree <M의 첫 부모> <마지막 관문 통과 기록의 H>`와 같으면 정상으로 보고 정리를 이어 간다. 찾지 못했거나, 트리가 다르거나, 관문 통과 기록이 없으면 "관문 미확인 병합"으로 보고한다. 되돌리지 않는다.
7. **원격**: 로컬 병합은 원격을 읽지도 쓰지도 않는다. 기준 브랜치를 원격에 올리는 일은 orchestra `SKILL.md` 8단계에서 사용자 지시로만 한다.

## 관문 기록

`state.md`의 "관문" 절에 판정마다 한 줄을 더한다.

```
| 시각 | H | B | G1 | G2 | G3 | G4 | G5 | 결과 |
| 2026-11-08 10:40 | 2222bbb | bbbb002 | 통과 | 통과 | 통과(rev-3ecbf1e7-2) | 통과 | 통과 | 병합 확인 |
```

병합 위치가 `로컬`이면 결과는 `로컬 병합 확인(<M>)`이다. `M`은 기준 브랜치에 생긴 병합 커밋이고, orchestra `SKILL.md` "새 작업 시작 조건"의 로컬 커밋 확인이 이 값을 읽는다.
