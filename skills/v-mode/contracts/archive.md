# 증거 보관

작업자는 worktree 안에 증거를 쓰고, 관리자가 메인 저장소로 옮겨 보관한다. worktree를 지워도 증거가 남게 하려는 절차다.

## 준비(배정 전)

1. ignore 경로를 찾는다: `git -C <worktree> rev-parse --git-path info/exclude`. 결과가 상대 경로면 `<worktree>` 기준으로 절대 경로로 바꾼다.
2. 그 파일에 `.vstack/` 줄이 없으면 더한다. 작업자는 이 파일을 고치지 않는다.
3. `state.md`의 "시도" 표에 이번 시도를 `배정됨`으로 적는다. 역할, scope, 맡은 수용 기준, 실행기, 세션, dispatch ID, 대상을 함께 적는다([state-and-rollback.md](state-and-rollback.md)).
4. 명세에 증거 폴더를 적는다: `<worktree>/.vstack/evidence/<작업 이름>/<시도 ID>/`.

## 시도의 상태

`state.md`의 "시도" 표에 시도마다 한 줄. 관리자만 고친다.

| 상태 | 뜻 | 정산됨 |
| --- | --- | --- |
| `배정됨` | 작업자를 띄웠다 | 아니오 |
| `취소` | 제출이 실패해 작업자가 시작하지 않았다(제출 확인 실패 기록이 있어야 한다) | 예 |
| `보고됨` | 완료 보고를 받았다 | 아니오 |
| `보관됨` | 보관 폴더와 manifest 해시 포인터를 적었다 | 아니오 |
| `정리됨` | 보관을 다시 확인하고 worktree 원본을 지웠다 | 예 |
| `원본정리대기` | 보관은 됐는데 원본 삭제가 실패했다(파일 잠김 등) | 아니오 |
| `격리대기` | 증거가 없거나 손상된 시도의 잔여물을 옮기는 중이다 | 아니오 |
| `증거없음` | manifest 없이 끝났거나 manifest가 맞지 않았고, 잔여물 격리를 마쳤다 | 예 |
| `손상정산` | 보관 뒤 손상이 발견됐고, 손상본과 잔여물 격리를 마쳤다 | 예 |

`증거없음`·`손상정산`인 시도가 맡은 수용 기준은 집계에서 **증거 없음**이 된다([evidence.md](evidence.md) "수용 기준 집계" 3). 정산됐다는 것은 "더 할 일이 없다"는 뜻이지 "통과"가 아니다.

## 보관 확인

이 문서에서 **보관 확인**은 두 가지를 모두 확인하는 것이다.

1. 보관 폴더의 `manifest.json` sha256이 `state.md` 포인터의 값과 같다.
2. manifest `files`의 모든 파일이 보관 폴더에 있고, 크기와 sha256이 같다.

## 보관 순서

시도마다, 판정과 관계없이(통과·실패·막힘 모두) 완료 보고를 받은 뒤 한다.

1. **복사**: worktree의 시도 폴더를 `.local/vstack/<작업 이름>/evidence/.staging/<시도 ID>/`로 복사한다.
2. **대조**: staging의 파일 목록·크기·sha256을 manifest `files`와 대조한다. 어긋나면 staging을 지우고 아래 "증거 없음 정산"으로 간다(이유: manifest 불일치).
3. **승격**: staging 폴더를 `.local/vstack/<작업 이름>/evidence/<시도 ID>/`로 이름을 바꾼다. staging과 보관 폴더는 같은 볼륨이다.
4. **포인터**: `state.md`의 그 시도 줄에 보관 경로와 manifest sha256을 적고 상태를 `보관됨`으로 바꾼다. `state.md`는 새 내용을 임시 파일에 다 쓴 뒤 원래 파일과 바꾼다.
5. **원본 정리**: 보관 확인을 한 뒤 worktree의 시도 폴더를 지운다. 지우기 전에 지울 경로의 절대 경로가 `<worktree>/.vstack/evidence/<작업 이름>/<시도 ID>`인지 확인한다. 성공하면 `정리됨`, 실패하면 `원본정리대기`.

이미 `보관됨` 이상인 시도는 다시 복사하거나 덮지 않는다.

## 증거 없음 정산

작업자가 manifest 없이 끝났거나, 2단계 대조가 실패했을 때.

1. **정지 확인**: 작업자가 더 이상 쓰지 않는다는 것을 확인한다. Orca에서는 작업자 상태가 종료·닫힘이거나, 관리자가 정지를 요청하고 그 정지가 확인된 경우다. 응답 없음, 시간 초과, `escalation` 수신만으로는 정지로 보지 않는다. 확인되지 않으면 상태를 `배정됨`(또는 `보고됨`)으로 두고 기다린다.
2. 상태를 `격리대기`로 바꾸고 비고에 `격리: 원인=증거없음(<이유>), 단계=시작`을 적는다.
3. worktree에 시도 폴더가 남아 있으면 아래 "격리"를 한다. 없으면 4로.
4. `증거없음(<이유>)`으로 바꾼다.

## 보관 손상

`보관됨`·`정리됨`인 시도의 보관 확인이 실패하면(누군가 파일을 바꿨거나 잃었다).

1. worktree에 원본이 남아 있으면 지우지 않는다.
2. **먼저** 상태를 `격리대기`로 바꾸고 비고에 `격리: 원인=손상(<어긋난 파일>), 단계=시작`을 적는다. 관문 기록과 사용자 보고에 "보관 손상(<시도 ID>, 어긋난 파일)"을 적는다.
3. 손상된 보관 폴더를 `<시도 ID>.damaged/`로 이름을 바꾼다. 그 뒤 비고의 단계를 `damaged`로 바꾼다.
4. worktree 원본이 남아 있으면 아래 "격리"로 `<시도 ID>.void/`에 옮긴다.
5. `손상정산(<이유>)`으로 바꾼다.
6. 그 시도가 맡았던 수용 기준은 증거 없음이 되므로, 관리자는 같은 대상에 새 시도를 맡긴다.

## 격리

증거 없음 정산과 보관 손상에서 worktree에 남은 원본을 옮기는 절차다. 단계는 `state.md` 비고의 `격리:` 줄에 적는다. **확정된 `.void` 폴더는 어떤 경우에도 지우지 않는다.**

1. **복사**(단계 `복사`): 원본을 `.local/vstack/<작업 이름>/evidence/.staging/<시도 ID>.void/`로 복사한다.
2. **대조**: 원본과 사본의 파일 목록·크기·sha256을 대조한다(manifest가 없으므로 원본을 직접 해시한다). 그 목록을 사본 안의 `void-manifest.json`으로 쓴다. 어긋나면 staging 사본만 지우고 1부터.
3. **확정**: staging 사본을 `.local/vstack/<작업 이름>/evidence/<시도 ID>.void/`로 이름을 바꾼다.
4. **포인터**(단계 `확정`): 비고에 `.void` 경로와 `void-manifest.json`의 sha256을 적는다.
5. **원본 정리**(단계 `원본정리`): `.void`를 포인터로 확인(`void-manifest.json` 해시 + 목록의 모든 파일)한 뒤, 원본에 **남아 있는 파일만** 지운다. 실패하면 단계 `원본정리`로 두고 다음에 다시 한다.
6. 원본이 비면 격리 끝. 원래 절차(증거 없음 정산 4 또는 보관 손상 5)로 돌아간다.

## 중단 복구

관리자가 재시작하면 `state.md`의 "시도" 표를 보고 시도마다 다음을 한다.

| 끊긴 지점 | 남은 상태 | 복구 |
| --- | --- | --- |
| 복사 중 | staging 일부, 보관 폴더 없음, 포인터 없음 | staging을 지우고 1부터 |
| 대조 뒤, 승격 전 | staging 전체, 보관 폴더 없음, 포인터 없음 | staging을 지우고 1부터 |
| 승격 뒤, 포인터 전 | 보관 폴더 있음, 포인터 없음 | 보관 폴더를 manifest `files`와 대조. 맞으면 4부터. 틀리면 보관 폴더를 지우고 1부터 |
| 포인터 뒤, 원본 정리 전 | 포인터 있음, 원본 있음 | 보관 확인 후 5 |
| 원본 정리 중 | 포인터 있음, 원본 일부 | 5를 다시 한다. 또 실패하면 `원본정리대기` |
| 격리 복사·대조 중 | 단계 `시작`·`복사`, staging 사본 있음, 확정 `.void` 없음 | staging 사본만 지우고 격리 1부터. 원본은 아직 그대로다 |
| 격리 확정 뒤, 포인터 전 | 단계 `복사`, 확정 `.void` 있음, 포인터 없음 | `.void`의 파일을 그 안의 `void-manifest.json`과, 그리고 남은 원본과 대조한다(원본 삭제 전이므로 원본은 그대로다). 맞으면 격리 4부터. 틀리면 사용자에게 보고하고 멈춘다(확정 `.void`를 지우지 않는다) |
| 격리 포인터 뒤 | 단계 `확정`·`원본정리`, 원본 전부 또는 일부 | `.void`를 포인터로 확인한 뒤 격리 5(남은 원본 파일만 삭제). 확인이 실패하면 원본을 지우지 않고 사용자에게 보고하고 멈춘다 |
| 손상 표시 뒤, 이름 바꾸기 전 | 비고 `원인=손상, 단계=시작`, 보관 폴더가 원래 이름 | 보관 손상 3부터 |
| 손상 이름 바꾸기 뒤, 단계 기록 전 | 비고 `원인=손상, 단계=시작`, `<시도 ID>.damaged/` 있음, 원래 이름 없음 | 단계를 `damaged`로 적고 보관 손상 4부터 |
| 손상 단계 `damaged` | 원본 있음 또는 없음 | 원본이 있으면 격리, 없으면 보관 손상 5 |

## 정산

시도 표의 모든 줄이 "정산됨: 예" 상태(`취소`, `정리됨`, `증거없음`, `손상정산`)면 **정산됐다**.

- 병합 관문 G4는 정산을 요구한다([merge-gate.md](merge-gate.md)).
- orchestra 6단계 "worktree 지우기" 전 확인에 정산을 더한다. 정산되지 않았으면 worktree를 지우지 않는다.

## Windows

- PowerShell에서 `Copy-Item -LiteralPath`, `Get-FileHash -Algorithm SHA256 -LiteralPath`, `Move-Item -LiteralPath`, `Remove-Item -LiteralPath -Recurse`를 쓴다. 한글·공백이 든 경로 때문에 `-Path` 대신 `-LiteralPath`를 쓴다.
- 폴더 이름은 작업 이름과 시도 ID(ASCII)만 쓴다. 이슈 제목 같은 사용자 문자열을 넣지 않는다.
- 파일이 잠겨 삭제가 실패해도 보관은 되돌리지 않는다. `원본정리대기`·`격리대기`로 두고 다음 깨어날 때 다시 시도한다.
- 경로가 260자를 넘을 수 있으면 `git config core.longpaths true`와 장경로 사용 설정을 확인한다. 이것은 시범에서 실제로 확인할 항목이다.
