# 증거

검토 결과는 실제 패치를 덮어야 한다(pstack `playbooks/shipping.md:5~8`). 첫 버전은 증거를 재사용하는 예외를 두지 않는다.

## 용어

- **대상(target)**: `(H, B)`. `H`는 브랜치 head 커밋, `B`는 기준 브랜치 tip 커밋이다.
- **시도(attempt)**: 작업자 한 번의 실행 단위. ID는 `<역할>-<세션 키>-<n>`(역할은 `impl` 또는 `rev`). **세션 키**는 관리자가 새 세션을 띄우기 전에 정하는 8자 16진수다(dispatch ID는 띄운 뒤에야 생기므로 쓰지 않는다). 같은 세션에 다시 맡기는 시도는 같은 키를 쓰고 `n`을 올린다. ASCII만 쓴다.
- **세션**: 작업자 하나의 실행 맥락. 세션 키로 식별한다. 관리자는 `state.md` 시도 표에 세션 키와 함께 실행 환경의 식별자(Orca 작업자 터미널 핸들)를 적는다. 작업자는 자기 터미널 핸들을 알 수 없으므로 manifest에는 세션 키를 쓴다. 끝난 작업자에게 `send`로 다시 맡기면 dispatch ID는 새로 생겨도 세션은 같다.
- **변경 작성자**: 대상 `T`를 만든 마지막 커밋을 만든 세션(구현자, 지적 수정자, rebase 작업자 중 하나).
- **수용 기준**: 티켓의 `AC-<n>@<버전>`. 필수 여부는 명세가 정한다.

## manifest.json

시도 폴더마다 하나. 자기 자신의 해시는 넣지 않는다(manifest 해시는 관리자가 `state.md`에 적는다). `results[].artifacts`에 나온 파일은 모두 `files`에 있어야 한다.

```json
{
  "contract": "vstack-contract@5",
  "task": "issue-42",
  "attempt": "rev-3ecbf1e7-1",
  "role": "rev",
  "scope": "review",
  "executor": "claude",
  "session": "3ecbf1e7",
  "recipe": "bug-fix@8",
  "target": { "head": "<40자 SHA>", "base": "<40자 SHA>", "base_ref": "main" },
  "tree_before": "",
  "env": {
    "os": "Windows 11", "runtime": "node 22.11.0",
    "seed": "fixtures/todos.json",
    "ignored_inputs": [{ "path": ".env.local", "sha256": "<해시>" }],
    "build_from_head": "이 시도에서 H를 checkout한 상태로 npm run build 후 서버 시작"
  },
  "patch_id": "<git diff B...H | git patch-id --stable 값, 참고용>",
  "results": [
    {
      "acceptance": "AC-1@1",
      "command": "npm run verify -- toggle-persist",
      "cwd": "<worktree 절대 경로>",
      "exit": 0,
      "started": "2026-11-08T10:02:11+09:00",
      "finished": "2026-11-08T10:02:40+09:00",
      "result": "체크 후 새로고침해도 완료 상태 유지",
      "artifacts": ["ac-1/before.png", "ac-1/after-reload.png", "ac-1/run.log"],
      "verdict": "통과",
      "note": ""
    }
  ],
  "files": [
    { "path": "ac-1/before.png", "sha256": "<해시>", "bytes": 48211 },
    { "path": "ac-1/after-reload.png", "sha256": "<해시>", "bytes": 47930 },
    { "path": "ac-1/run.log", "sha256": "<해시>", "bytes": 1234 }
  ]
}
```

- `session`은 시도 ID의 세션 키다(위 "용어"). 명세가 값을 준다.
- **과정 증거**(유효하지 않은 실행, 재현·진단 기록, 커밋 전 red→green)는 시도 폴더의 `process/` 아래에 두고 `files`에만 올린다. `results[].artifacts`에는 넣지 않는다.
- 완료 보고를 파일로도 남기면 시도 폴더의 `report.md`에 두고 `files`에 올린다.
- manifest와 `report.md` 안의 증거 경로(증거 파일을 가리키는 경로)는 **시도 폴더 기준 상대 경로**로만 쓴다. `results[].cwd` 같은 실행 위치는 절대 경로 그대로 쓴다. 보관하면 폴더가 메인 저장소로 옮겨지므로 worktree 절대 경로는 곧 틀린 경로가 된다. 보관 뒤의 위치는 `state.md` 시도 표의 보관 경로가 정본이다.

`scope`는 rev 시도에만 쓴다.

- `review`: 그 대상의 코드 검토(diff와 브랜치 전체, 지적 해결 확인)와 필수 수용 기준 전부의 재실행을 함께 맡은 시도. 결론(`통과`/`수정 필요`)을 낸다.
- `rerun-only`: 대상이 그대로인 채 일부 수용 기준만 다시 돌리는 시도(환경 복구 뒤, 막힘 해소 뒤). 결론을 내지 않는다. **대상이 바뀐 뒤의 첫 rev 시도는 `rerun-only`일 수 없다.**

## 유효와 통과

- **유효한 기록**: 다음을 모두 만족하는 수용 기준 결과다.
  1. manifest의 `target`이 판정하려는 대상과 같다.
  2. `tree_before`가 빈 문자열이다(추적 파일과 ignore되지 않은 새 파일에 변경이 없다).
  3. `acceptance`의 버전이 현재 수용 기준 버전과 같다.
  4. `env.build_from_head`가 이 시도에서 `H`로 빌드·실행했음을 보인다.
  5. 그 시도가 `보관됨` 또는 `정리됨`이다([archive.md](archive.md)).
  6. 그 시도의 역할 자격이 맞다(아래 "역할 자격").
- **통과 기록**: 유효하고 `verdict`가 `통과`인 기록.
- 유효한 `실패` 기록은 "믿을 수 있는 최신 실패"다. 유효하다고 통과한 것이 아니다.
- 유효하지 않은 기록(커밋 전 red→green 등)은 **과정 증거**로 보관하되 판정에 쓰지 않는다.
- 작업자는 `tree_before`가 빈 문자열이 아닌 실행을 `results`에 넣을 때 `verdict`를 `막힘`으로, `note`에 "작업 트리가 깨끗하지 않음"과 그 출력을 적는다. 실행 결과가 통과처럼 보여도 `통과`로 적지 않는다. 그 실행의 산출물은 `process/` 아래에 둔다.

## 수용 기준 집계

대상 `T`, 역할 `r`(`impl`, `rev`), 필수 수용 기준 `AC`마다 판정한다. 입력은 `state.md` 시도 표의 **배정 기록**이다(manifest만 보지 않는다).

1. 시도 표에서 역할이 `r`이고, **결과 대상**이 `T`이고(아직 결과 대상이 없는 시도는 배정 대상이 `T`이고), "맡은 수용 기준"에 `AC`가 있는 시도 가운데 **가장 나중에 배정된 시도** `A`를 고른다. `취소`된 시도는 고르지 않는다.
2. `A`의 상태가 `보관됨`·`정리됨`이면 그 manifest에서 `AC` 기록을 읽는다. 기록이 없으면 **증거 없음**.
3. `A`의 상태가 `증거없음`·`손상정산`·`격리대기`·`배정됨`·`보고됨`이면 **증거 없음**. 더 앞선 시도의 기록으로 되돌아가지 않는다.
4. 두 역할 모두 통과 기록이면 `AC`는 **통과**. 어느 한쪽이 유효한 `실패`면 **실패**, 유효한 `막힘`이면 **막힘**, 나머지는 **증거 없음**. 유효하지 않은 기록은 `verdict`와 관계없이 **증거 없음**이다. 예: `tree_before`가 비어 있지 않은 실행의 `막힘`은 증거 없음이고, `tree_before`가 빈 실행에서 환경 입력이 없어 난 `막힘`은 막힘이다.

시도가 일부 수용 기준만 맡았으면, 맡지 않은 수용 기준은 1에서 그보다 앞선 시도가 골라진다. 맡았는데 결과를 잃은 시도는 3에 걸린다. 이전 시도의 통과 보고를 다시 보내는 것은 새 기록이 아니다.

## 역할 자격

- **impl**: 기본은 변경 작성자 세션이다. 변경 작성자 세션이 사라졌으면(닫힘, 멈춤 뒤 정지 확인) 관리자가 새 세션을 **impl 인계**로 지정할 수 있다. `state.md` 시도 표에 `impl 인계(<이유>)`를 적는다. impl은 자기 검증이며 독립 검토를 대신하지 않는다.
- **rev**: 다음을 모두 만족해야 한다.
  - 대상 `T`에 커밋을 만들지 않은 세션이다. 변경 작성자 세션도, impl 세션도 아니다.
  - 실행기 계열(`codex`/`claude`)이 변경 작성자와 다르다. 다를 수 없으면 orchestra `tiers.md`의 같은 계열 조건(맥락 없는 새 작업자, 2차 의견 필수, PR 본문 기록)을 모두 채운다. 하나라도 없으면 자격이 없다.

## 최신성

대상이나 수용 기준 버전이 바뀌면 이전 기록은 새 대상에 쓸 수 없다.

- `H`가 바뀌면(구현 수정, 지적 수정, rebase): 새 대상에서 impl이 필수 수용 기준을 **전부** 다시 돌리고, rev는 `scope: review` 시도로 **전부** 다시 돌리며 코드 검토 결론을 낸다.
- `B`가 바뀌면: 관리자가 rebase를 맡긴다. 그러면 `H`도 바뀌므로 위와 같다.
- 수용 기준 버전만 바뀌고 `H`가 그대로면: 그 수용 기준을 두 역할이 다시 돌린다(rev는 `rerun-only` 가능). 그 결정을 구현하느라 `H`가 바뀌면 위 첫 항목을 따른다.
- `patch_id`는 기록만 한다. 같아도 재사용 근거가 아니다.

비용이 커지는 것은 알고 받아들인다(첫 버전). 재사용 최적화는 시범에서 비용을 측정한 뒤 계약 버전을 올려 정한다.

## 막힘과 해당 없음

- `막힘`은 자동 통과하지 않는다. 원인이 환경·인프라면 관리자가 환경을 고치거나 새 시도를 맡긴다. 원인이 제품·요구 결정이면 관리자가 사용자에게 묻는다.
- 필수 수용 기준에 작업자가 `해당 없음`을 쓸 수 없다. 쓰면 그 기록은 유효하지 않다. 수용 기준을 바꾸거나 필수에서 빼려면 관리자가 승인하고(제품 결정이면 사용자가) 수용 기준 버전을 올린다.

## 원칙 위반

원칙 위반은 자동 차단이 아니다. 검토자가 `중요`/`사소`로 적고, 관리자가 orchestra 5단계 규칙(지금 고침 / 다른 이슈로 넘김 / 사용자에게 물음)으로 판정한다. 그 판정 결과는 병합 관문의 G3이 본다.
