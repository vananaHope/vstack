# 작업 파일과 새로 시작

## 위치

vstack 작업의 파일은 메인 저장소의 `.local/vstack/<작업 이름>/`에 둔다.

- 프로젝트 설정(`docs/agents/orchestration.md` 또는 `.local/orchestration/settings.md`)과 `common-findings.md`는 vstack이 읽는다. `.local/orchestration/`은 agent-orchestra(아카이브됨) 때의 폴더 이름이고, 이미 있는 프로젝트의 설정을 옮기지 않으려고 그대로 쓴다(ADR 0007). vstack은 설정을 읽기만 하고, 형식을 바꾸지 않는다.
- 맡김 기록은 `.local/vstack/assign-log.md`에 따로 쌓는다(레시피·검토자·증거 판정 열 포함).
- 실창 잠금은 `~/.agent-orchestra/desktop.lock`을 쓴다. 이것도 agent-orchestra 때의 이름이다(ADR 0007). 데스크톱은 컴퓨터에 하나이므로 프로젝트에 관계없이 같은 파일이다.

## state.md 형식

```
<단계>                      ← 첫 줄. orchestra 단계 이름 + `병합 대기`
등급: standard · 작업자: codex@high
workflow: vstack · contract: vstack-contract@4 · recipe: bug-fix@7 · 소유: vstack
막힘: <풀릴 조건>            ← 막혔을 때만

## 수용 기준
| ID | 필수 | 내용 |

## 시도
| 시도 ID | 역할 | 작업 종류 | scope | 맡은 수용 기준 | 실행기 | 세션 | dispatch ID | 배정 대상 H·B | 결과 대상 H·B | 상태 | 보관 경로 | manifest sha256 | 비고 |

## 관문
| 시각 | H | B | G1 | G2 | G3 | G4 | G5 | 결과 |

## 게시
| 시각 | 브랜치 | 게시한 SHA | 방법(첫 게시 / push / force-with-lease(확인받음) / 원격 일치 확인) |
```

- `배정 대상`은 맡길 때의 `H`·`B`(새 수정이면 시작 커밋과 `B`), `결과 대상`은 완료 보고를 받고 manifest와 worktree를 확인해 관리자가 적는 `H`·`B`다. 수용 기준 집계(evidence.md)는 결과 대상을 쓴다.
- `세션`은 Orca 작업자 터미널 핸들, `dispatch ID`는 전체 값이다. 둘 다 띄운 뒤 `worker-start`·`send` 결과에서 읽어 채운다. 시도 ID의 세션 키는 관리자가 띄우기 전에 정한 것이고, manifest의 `session`도 이 키다(작업자는 터미널 핸들을 모른다). 이 표가 세션 키와 터미널 핸들을 잇는다. 역할 자격(evidence.md)과 집계를 재시작 뒤에도 판정하려고 남긴다.
- `비고`에는 `impl 인계(<이유>)`, `취소(<제출 확인 실패 또는 시작 실패의 근거>)`, 정산 이유 등을 적는다.

## 소유권

- `소유: vstack`인 작업은 vstack 관리자만 진행한다. 그 밖의 소유 값(`포기(…)` 등)인 작업은 진행하지 않는다.
- `.local/orchestration/*/state.md`는 agent-orchestra 때의 작업 파일이다. vstack 관리자는 그 작업을 이어받지 않는다. 끝나지 않은 것이 있으면 사용자에게 알린다.

## 새로 시작

지휘 중인 작업의 PR을 버리고 같은 이슈를 처음부터 다시 할 때다. 사용자가 고른다. 다시 하는 것도 vstack 지휘다.

1. vstack 관리자가 그 작업의 작업자를 모두 정지하고 정지를 확인한다. 확인되지 않으면 아래를 하지 않고 사용자에게 알린다.
2. 시도를 모두 정산한다.
3. 열린 PR이 있으면 닫을지 사용자에게 묻는다. 열어 두면 그 이슈는 "진행 중"으로 보여 다시 맡겨지지 않는다(orchestra `SKILL.md` 1단계).
4. **worktree는 지우지 않고 보존한다.** orchestra의 worktree 지우기 규칙은 병합된 worktree만 허용하므로 미병합 worktree에는 쓸 수 없다. 대신 그 worktree의 브랜치를 `vstack-abandoned/<작업 이름>-<날짜>`로 이름을 바꿔, 다시 맡길 때 새로 만들 `<작업 이름>-<slug>` 브랜치와 겹치지 않게 한다. 보존한 경로와 브랜치를 사용자에게 알린다.
5. 보존한 worktree를 지우는 것은 미병합 변경의 삭제이므로 안전 멈춤([priority.md](priority.md))에 든다. 사용자가 폐기를 명시적으로 고르고, 작업자 정지가 확인되고, 시도가 정산됐을 때만 지운다. 지우기 전에 브랜치를 원격에 백업할지 사용자에게 묻는다.
6. `state.md` 첫 줄을 `끝`, 소유를 `소유: 포기(<날짜>, 새로 시작)`로 바꾼다.
7. 열린 PR이 없으면 그 이슈를 새 작업으로 다시 맡길 수 있다. 아래 "다시 맡길 때의 작업 이름"을 따른다.

### 다시 맡길 때의 작업 이름

포기한 작업(`소유: 포기(…)`)의 이슈를 다시 맡기면 새 작업은 **새 작업 이름** `<원래 작업 이름>-r<k>`를 쓴다(`k`는 2부터, 그 이슈에서 이미 쓴 이름과 겹치지 않는 가장 작은 수. 예: `issue-42-r2`). 그래서 작업 파일 폴더(`.local/vstack/<작업 이름>/`), 증거 폴더, worktree, 브랜치(`issue-42-r2-<slug>`)가 모두 새로 생긴다.

- 포기한 작업의 폴더는 이름을 바꾸거나 옮기지 않는다. 그 `state.md`의 보관 경로와 manifest 포인터가 그 폴더를 가리키기 때문이다. 기록으로 그대로 남는다.
- 새 작업의 `state.md`는 새로 쓴다(시도 표, 관문, 게시 절은 비어 있다). 넷째 줄 아래에 `이전 작업: <포기한 작업 이름>(포기 <날짜>)`를 적는다. 포기한 작업의 시도와 증거는 새 작업의 판정 입력이 아니다(새 작업의 대상은 새 시작 커밋이다).
- 이슈 표시(명세 제목, PR 제목, 보고)는 그대로 `#<n>`이다. 진행 중 판정(orchestra `SKILL.md` 1단계)의 브랜치 접두사 `<원래 작업 이름>-`도 새 브랜치에 맞는다.
- orchestrate-issues의 "그만둘 때"로 포기한 작업을 다시 맡길 때도 같다.
