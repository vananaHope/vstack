# 맡기기

맡기기 갈래의 일 하나(티켓으로 나누지 않는 한 단위)를 Claude Code 관리자가 작업자에게 맡기는 절차다. v-mode "맡기기"가 이 파일로 보낸다. 레시피가 있든 없든 같다. Claude 구현자가 새 worktree에서 구현하고, Codex 검토자가 같은 worktree에서 검토하고, 관리자가 마지막에 확인한다. 관리자는 사용자가 `/vstack:v-mode`를 실행한 대화다. 관리자는 맡기고, 답하고, 검토를 맡기고, 확인하고, 사용자가 정한 방법으로 반영한다. 제품 코드를 쓰지 않고, 검증 수단을 만들지 않고, 충돌을 풀지 않는다. 그 일들도 작업자에게 맡긴다.

이 파일은 `<vstack>/skills/v-mode/delegate.md`다. 아래 경로는 이 파일 기준 상대 경로다.

**검증 범위**: 이 구조(Claude 구현자, Codex 검토자)로는 Orca에서 `bug-fix` 정상 경로를 한 번 돌렸다(저장소의 `docs/pilot-delegate.md`). 관리자가 이 절차의 초안을 직접 따랐고 라우터는 거치지 않았다. 작업자 질문 한 번, 첫 검토 통과, 범위를 넓히는 후속 요구 한 번, 같은 검토자의 재검토 한 번, 마지막 확인, 정리까지 갔다. 돌려 보지 않은 것: 검토 지적을 고친 뒤의 재검토, 확인 실패, 재검토 상한, Codex를 쓸 수 없을 때, 서브에이전트를 부르는 경우, 시작 실패(앞선 omp 구조에서만 돌려 봤다. `docs/pilot-omp.md`), 관리자 재시작, 중단, 보고 없이 끝난 작업자, `feature`(omp 구조에서 한 번), `refactoring`, 레시피 없는 일, 검증 수단을 먼저 맡기는 경우, 맡길 수 없을 때의 갈림, 라우터를 거친 실행. 돌려 보지 않은 경우를 만나면 그렇다고 사용자에게 알리고 진행한다.

## 경계

- **계약 밖이다.** 구현자와 검토자는 Orca가 감독하는 작업자이지만 계약의 구현자(impl)·검토자(rev)가 아니다. 계약 명세 양식(intake), 증거 폴더, manifest, 시도 정산을 쓰지 않는다.
- 관리자의 확인과 Codex 검토는 계약의 교차 검토나 병합 관문을 대신하지 않는다. 결과를 계약에 올리려면 새 지휘 작업(티켓, vstack 절)으로 시작한다.
- 지휘 중인 작업은 이 경로로 내려보내지 않는다.
- 관리자는 맡긴 worktree의 파일을 고치지 않는다. 고칠 것은 "보내기"로 구현자에게 보낸다. 읽기와 검증 명령 실행은 한다. 예외는 하나다: 구현자를 띄우기 전에, Git이 무시하는 환경 파일을 worktree에 두는 것("맡기기 전에" 7).
- **한 worktree에서 한 번에 한 작업자만 일한다.** 한 역할을 띄우거나 깨우기 전에, 다른 역할의 마지막 Dispatch가 끝났는지(`worker-show`의 `state`)를 본다.
- 모델: 구현자는 `--model opus`로 띄운다. 검토자는 모델 옵션 없이 띄운다(Codex 설정의 기본값). 서브에이전트는 [subagents.md](subagents.md)를 따른다.

## 작업자 다루기

Run, worktree 만들기, 띄우기, 제출 확인, 기다리기, 답하기, 보내기, 정지, 정리, worktree 지우기는 [../orchestrate-issues/backends/orca.md](../orchestrate-issues/backends/orca.md)의 같은 이름 절을 따른다. 이 파일에는 다른 점만 적는다.

- 그 문서의 `state.md`·시도 표는 아래 "기록"으로 읽는다.
- 그 문서가 계약 정산으로 보내는 곳(시작 실패의 `취소` 정산 등)은 따르지 않는다. 그 대신 기록을 `확인 필요`로 두고 멈춘 뒤 사용자에게 알린다. 시작 실패는 아래 "시작 실패"를 따른다.
- 결과가 불명확한 명령(응답 없음, `outcome_unknown`, `stop_unknown`, `release_unknown`)은 되풀이하지 않는다. 조회(`worker-show`, `worker-list`, `inbox --full`, `orca worktree show`)로 이미 효과가 났는지 먼저 본다.
- 끝난 작업자를 다시 쓸 때는 그 작업자의 **마지막 Dispatch**에 "보내기"를 한다. 결과의 새 Dispatch를 기록한다. 구현자와 검토자의 마지막 Dispatch는 기록에 따로 적는다.
- 작업자 터미널의 해제("정리")는 검토를 맡기는 조건이 아니다. "절차" 15에서 한다.

## 맡기기 전에

두 묶음을 차례로 본다. 어느 조건 때문에 맡기지 않는지를 사용자에게 알린다. 어느 경우에도 관리자가 대신 구현하지 않는다.

**맡겨도 되는 일인가.** 아니면 멈추고 지휘를 권하거나(v-mode 고르기 1), 3이면 입력부터 정한다.

1. 틀리면 비싼 일(인증, 데이터 변경·삭제, 공용 API, 보안)이 아니다.
2. 한 단위의 일이다. 여러 티켓으로 나눌 일이나 동시에 진행할 일이 아니다.
3. 수용 기준과 검증 명령을 정할 수 있다. 정할 수 없으면 사용자에게 물어 먼저 정한다. 검증 수단이 없으면 아래 "검증 수단이 없을 때"를 먼저 한다.

**지금 맡길 수 있는가.** 아니면 아래 "맡길 수 없을 때".

4. 실행 환경이 Orca다(`orca orchestration run-current`가 답한다).
5. 작업 유형을 정했다: 레시피 하나(v-mode 고르기 2), 또는 레시피 없음(아래 "절차 범위"의 레시피 없는 일). `ui-polish`는 아래 "`ui-polish` 맡기기"도 따른다.
6. 이 저장소에 진행 중인 지휘 작업(`.local/vstack/*/state.md` 첫 줄이 `끝`이 아님)이 없다. 진행 중인 맡기기(아래 "기록")가 있으면 아래 "여러 맡기기"의 조건이 맞는다. 한 저장소의 관리자는 하나다.
7. 맡길 기준이 정해진다. 관리자 작업 트리의 `git status`와 브랜치를 본다. 작업자는 기준 커밋에서 새 worktree로 시작하므로 커밋되지 않은 변경은 넘어가지 않는다.
   - 이 일에 필요한 것(사용자가 하던 수정, 방금 만든 검증 수단, 검증 명령이 쓰는 테스트 러너·verify 시나리오)이 커밋되지 않았거나 기준 브랜치에 없으면, 어떻게 할지 사용자에게 묻는다: 기준 브랜치에 먼저 커밋한다, 그것이 있는 브랜치를 기준으로 삼는다, 기다린다.
   - Git이 무시하는 파일(`.env.local` 같은 환경 파일, 설치한 의존성)도 새 worktree로 넘어가지 않는다. 검증 명령이 그런 파일을 쓰는지 본다(프로젝트의 verify 스킬과 검증 스크립트). 쓰면 맡기기 전에 정한다: 프로젝트의 verify 스킬이 누가 그 파일을 두는지 정해 놓았으면 그대로 따른다. 관리자가 두기로 돼 있거나 정해진 것이 없으면, 사용자에게 확인한 뒤 "절차" 4에서 worktree를 만든 직후(작업자를 띄우기 전)에 관리자가 둔다. 둘 수 없으면 사용자에게 묻는다: 준비한 뒤 다시 한다, 그 명령을 수용 기준에서 빼고 명세에 "이 명령은 이 worktree에서 돌리지 않는다"고 적는다, 기다리거나 그만둔다.
   - 이 일과 상관없는 변경은 건드리지 않고 알린다.

### 맡길 수 없을 때

"맡겨도 되는 일인가"의 판정(위험, 여러 단위, 수용 기준 없음)은 위 그대로다. "지금 맡길 수 있는가"가 아니면 조건별로 이렇게 한다. 어느 칸에도 관리자가 직접 하는 선택지는 없다.

| 조건이 안 맞음 | 할 일 |
| --- | --- |
| Orca가 아니다(4) | "맡기기는 Orca에서 v-mode를 실행해야 한다"고 알리고 끝낸다 |
| 작업 유형이 정해지지 않는다(5) | 사용자에게 묻는다. 두 유형에 걸치면 하나만 고르고 나머지는 다음 요청으로 나눈다 |
| 이 저장소에 진행 중인 지휘 작업이 있다(6) | 지휘가 끝난 뒤에 하거나, 그 작업에 속한 일이면 지휘 절차로 보낸다고 알린다 |
| 진행 중인 맡기기와 겹치거나, 이미 셋이 진행 중이다(6, 아래 "여러 맡기기") | 그 맡기기가 끝난 뒤에 맡긴다고 알린다 |
| 맡길 기준이 정해지지 않는다(7) | 사용자에게 묻는다: 기준 브랜치에 먼저 커밋한다, 그것이 있는 브랜치를 기준으로 삼는다, 기다린다 |
| 준비할 수 없다(7, 검증 명령이 쓰는 환경 파일을 둘 수 없다 등) | 사용자에게 묻는다: 준비한 뒤 다시 한다, 사용자가 그 검증을 수용 기준에서 빼기로 정한다, 기다리거나 그만둔다 |
| 시작 실패 뒤 다시 띄우지 않기로 했다 | 기다리거나 그만둔다(`끝(중단)`, 아래 "시작 실패") |

사용자가 "여기서 해"라고 명시하면 v-mode "맡기기"의 마지막 줄을 따른다.

## 입력

"절차" 1에서 대화에 먼저 적는다. 필수 수용 기준과 각 검증 명령, seam, 준비·정리, 범위 밖, 건드리지 말 곳은 공통이다. 레시피별로:

- `bug-fix`: 증상과 기대 동작, 수용 기준(증상 해소, 회귀 테스트), 재현 경로, 간헐 반복 횟수.
- `feature`: 바뀔 동작, 수용 기준(동작, 테스트), 데이터 모양, 범위 밖. 새 도메인 개념·공용 인터페이스·설계안 고르기가 걸리면 사용자에게 묻는다(지휘 경로를 권할 신호이기도 하다).
- `refactoring`: 원래 동작 기준 `S`(보통 기준 커밋 `B`), 고정 명령(pin), 목표 구조, 전환 방식, 수용 기준(동작 보존, 구조), 영향 범위, 사본 입력(scratch 사본에 넣을 Git이 무시하는 파일과 그 출처. 없으면 "없음"). 영향 범위가 넓어 expand–contract가 필요하면 맡기기가 아니다. 지휘 경로를 권한다.
- `ui-polish`: 대상 화면과 볼 상태, 다듬을 항목(항목마다 관찰 가능한 문장), 비교 화면(바뀌면 안 되는 화면 하나 이상. 사용자가 짚은 화면은 필수, 관리자가 더한 화면은 추가로 나눠 적는다), 스크린샷 수단, 수용 기준(다듬기, 다른 화면 보존, 기존 검사), 디자인 기준, 범위 밖. "더 깔끔하게" 같은 요청은 항목으로 풀어 사용자에게 확인받는다(아래 "`ui-polish` 맡기기"). 요청이 지금 상태를 말하고 있으면("높이가 안 맞아 보인다") 항목으로 적기 전에 필요한 값만 재서 확인하고, 잰 값이 요청의 말과 다르면 고치지 않고 잰 것을 보이며 묻는다. 사용자가 정한 값과 문구는 글자 그대로 쓴다. 스크린샷 수단이 없으면 고정 규칙 7이 먼저다(레시피 "새 다듬기" 3의 임시 수단으로 되는 일이면 그것으로 한다). 무엇이 좋은 모양인지가 정해지지 않았으면(새 시각 방향) 레시피를 시작하지 않고 사용자와 먼저 정한다. 시안을 만들어 볼 수단이 있으면 안내한다(mattpocock-skills가 설치돼 있으면 `/mattpocock-skills:prototype`).
- 레시피 없음: 바뀔 것(관찰 가능한 결과), 수용 기준, 범위 밖, 후보 원칙(v-mode "후보 원칙"의 표에서 이 일에 맞는 것).

코드와 실행으로 알 수 있는 것은 관리자가 읽기 전용으로 조사해 정하고(서브에이전트는 [subagents.md](subagents.md)), 제품 동작처럼 사용자만 정할 것은 묻는다. 코드가 이미 정한 정의(예: 다른 함수가 쓰는 "빈 값"의 기준)를 따르는 것은 조사로 본다. 이 기록이 레시피가 말하는 "명세"다. 물을 것이 없으면 확인을 기다리지 않고 진행한다.

## 절차 범위

구현 명세의 "따를 절차"에 적는 범위다. 레시피의 첫 구현 절차를 따르되, 증거 만들기와 계약 완료 보고 단계는 뺀다. 완료 보고는 명세의 "완료 보고"로 한다.

- `bug-fix`: "구현자: 새 수정" 1~7.
- `feature`: "구현자: 새 구현" 1~7.
- `refactoring`: "구현자: 새 리팩토링" 1~9. 10의 증거 만들기 대신 명세의 완료 보고에 원래 동작 기준 `S`, 고정 확정 커밋 `P`, 고정이 바꿀 코드를 지나가는지 본 결과(scratch에서 코드를 틀리게 바꿔 본 결과), `S`·`P`·`H`에서 고정을 돌린 결과, 더한 고정 테스트를 싣는다. 레시피가 scratch 사본을 요구하는 단계는 구현자가 worktree 밖 OS 임시 폴더의 새 폴더에 `git archive <커밋>`으로 풀어 한다. 명세의 "사본 입력"대로 무시 파일을 넣는다. 작업 폴더의 파일을 덮지 않고, 끝나면 그 폴더를 지운다.
- `ui-polish`: "구현자: 새 다듬기" 1~7. 8의 보고는 명세의 완료 보고에 싣는다. 역할과 순서는 아래 "`ui-polish` 맡기기".
- **레시피 없는 일**: 따를 레시피가 없다. 명세의 "따를 절차"에 "레시피 없음"을 적는다. 구현자는 수용 기준, 범위 밖, 건드리지 말 곳, 명세에 적힌 후보 원칙만 따른다. 검토는 같은 검토 명세를 쓴다.

레시피의 "관리자"는 이 일의 관리자다. 레시피가 `막힘`으로 관리자에게 물으라는 곳(seam이 맞지 않음, 설계 결정, 고정 테스트를 바꿔야 함 등)에서 구현자는 `ask`로 묻는다.

## 검증 수단이 없을 때

요구 동작을 검증할 수단이 없으면(v-mode 고정 규칙 7) 그 수단을 만드는 일을 **먼저 따로 맡긴다**. 레시피 없는 일로 맡긴다.

- 구현자가 [../create-verification-skill/SKILL.md](../create-verification-skill/SKILL.md)를 따르거나, 프로젝트에 verify 스킬이 이미 있으면 그 스킬과 스크립트에 시나리오를 더한다.
- 수용 기준은 만든 것이 실제로 돌고(시작 커밋에서 기대한 결과를 낸다. 고칠 결함을 재현하는 시나리오면 지금 실패한다) 산출물을 남기는 것이다.
- 그 결과를 사용자가 정한 방법으로 기준 브랜치에 반영한 뒤에 제품 변경을 맡긴다.
- `ui-polish`의 임시 촬영 수단(레시피가 OS 임시 폴더에 두라고 한 것)은 따로 맡기지 않고 그 맡기기 안에서 만든다.

## 여러 맡기기

서로 독립인 맡기기는 함께 진행할 수 있다. 기록, worktree, 작업자는 맡기기마다 따로다.

- **동시에 셋까지**다. 검증된 값이 아니다.
- **서로 독립인 요청만 함께 맡긴다.** 예약할 때("절차" 2) 진행 중인 맡기기마다 두 가지를 본다.
  - 쓰는 곳: 새 일의 **예정 쓰기 영역**(명세의 할 일, seam, 바꿀 파일과 모듈)이 진행 중인 맡기기의 예정 쓰기 영역과 겹치는가. 비교하는 것은 두 쓰기 영역의 교집합이다. "건드리지 말 곳"은 겹침 판정에 쓰지 않는다(작업자가 범위를 지켰는지 볼 때 쓴다). 지금까지 커밋된 변경 파일은 참고로만 본다(커밋되지 않은 작업은 거기에 없다).
  - 검증이 쓰는 자원: 검증 명령이 포트, DB, 데이터 폴더, 브라우저 프로필 같은 것을 함께 쓰는가. worktree가 달라도 이것들은 나뉘지 않는다. 맡기기마다 나눌 수 있으면(임시 데이터 파일, 다른 포트) 명세에 그렇게 적는다.
  - 겹치거나 나눌 수 없으면 그 맡기기가 끝난 뒤에 맡긴다. 판정과 근거를 두 기록의 사건에 적는다.
- **범위가 넓어질 때 다시 본다.** 범위를 넓히는 질문에 답하기 전, 후속 요구를 보내기 전("절차" 12), `ui-polish`의 항목을 확정하기 전, 기준을 맞추는 일을 보내기 전에 위 확인을 다시 한다. 겹치게 되면 넓히지 않고 사용자에게 알린다.
- 한 요청을 여러 개로 쪼개 동시에 맡기지 않는다. 여러 단위로 나눠야 하는 일은 지휘다.
- **Run은 관리자 세션에 하나를 함께 쓴다**("절차" 3). Orca의 `run-use`는 이름을 준 Run 하나만 남기므로(`orca skills get orchestration --reference references/coordinator-loop.md` "Several Runs"), 맡기기마다 Run이 다르면 관리자가 다시 시작했을 때 하나밖에 이어받지 못한다. 맡기기는 그 Run 안에서 Task와 Dispatch로 가린다.
- **깨우는 메시지의 주인을 가린다.** 작업자의 보고와 질문은 Dispatch로 어느 기록의 것인지 가린다. 어느 기록의 Dispatch 이력에도 없는 메시지는 처리하지 않고 사용자에게 알린다.
- **사용자의 말이 어느 맡기기의 것인지 가린다.** 이름, 브랜치, 하는 일로 가리고, 가릴 수 없으면 묻는다. "병합해"처럼 되돌리기 어려운 지시는 어느 맡기기인지 이름으로 확인한다.
- **반영은 한 번에 하나다**("절차" 15).

## `ui-polish` 맡기기

`ui-polish`도 맡긴다. 역할과 순서는 `ui-polish@3`에서 정한다.

## 절차

1. **입력을 정한다.** 위 "입력"의 입력 전체를 대화에 적는다(필수 수용 기준과 검증 명령, seam, 준비·정리, 레시피별 입력, 건드리지 말 곳). 사용자만 정할 것은 맡기기 전에 묻는다.
2. **예약한다.** 이름(끝난 기록과도 겹치지 않게), 기준 브랜치(보통 기본 브랜치, "맡기기 전에" 7에서 달리 정했으면 그것)와 그 SHA `B`, 작업 브랜치 이름, 예정 쓰기 영역과 검증이 쓰는 자원을 정해 기록을 `예약`으로 쓴다. 현재 확인 기준 `C`는 처음에 `B`다(아래 "기준을 맞추는 일"). 진행 중인 맡기기가 있으면 "여러 맡기기"의 확인을 이때 한다.
3. **Run을 정한다.** backends/orca.md "준비". 같은 저장소에 진행 중인 맡기기가 있으면 새로 만들지 않고 그 기록의 Run을 쓴다. 없으면, 이 세션에 묶인 Run이 이 저장소 맡기기의 것일 때 그것을 쓰고, 아니면 새로 만든다(`--objective "<저장소> 맡기기"`). Run을 기록에 적고, Run을 받는 orchestration 명령에 `--run <run>`을 붙인다.
4. **worktree를 만든다.** backends/orca.md "worktree 만들기"에 `--branch <작업 브랜치> --base-branch <기준 브랜치>`를 준다. 다른 저장소의 worktree면 `--no-parent`도 준다. 작업자를 띄우기 **전에** 그 worktree의 HEAD가 `B`이고 `git status --porcelain=v1 --untracked-files=all`이 빈지 본다. 아니면 띄우지 않고 기록을 `막힘`으로 둔다.
5. **명세를 쓰고 구현자를 띄운다.** [delegate-spec.md](delegate-spec.md)를 채워 기록 옆에 `spec.md`로 둔다. backends/orca.md "띄우기"의 기존 worktree 형태로 `--agent claude --model opus --spec-file <명세> --worktree path:<worktree> --run <run>`.
6. **제출 확인.** 결과의 Task·Dispatch·터미널을 기록하고 `배정됨`으로 바꾼다. 결과의 `state`가 `ready`인지 본다(backends/orca.md "제출 확인"). 시작이 의심스러우면 `worker-show`(살아 있음)와 `worker-read`(명세를 읽고 일하는 출력)로 본다.
7. **기다리고 답한다.** 턴을 끝낸다. 질문이 오면(구현자든 검토자든) 그 메시지 ID를 기록하고, 사용자만 정할 것은 사용자에게 물은 뒤 "답하기"로 답한다. 범위를 넓히는 답을 하기 전에 "여러 맡기기"의 확인을 다시 한다. 범위가 한 단위를 넘었다는 질문이면 "정지"로 정지를 확인하고, worktree를 남긴 채 기록을 `끝(지휘로 넘김)`으로 닫고 지휘를 권한다.
8. **구현 확인.** 구현자의 `worker_done`을 받을 때마다 한다.
   - 그 Dispatch가 끝났는지(`worker-show`의 `state`), 보고한 HEAD `H`가 실제 HEAD인지, 작업 트리가 깨끗한지 본다.
   - `C..H`의 커밋을 본다(기준을 맞춘 적이 없으면 `C`=`B`). 건드리지 말 곳이 바뀌었으면 통과로 치지 않는다.
   - 그 worktree에서 명세의 필수 수용 기준 명령을 모두 직접 다시 돌린다. 산출물은 OS 임시 폴더로 보낸다.
   - 작업자나 검토자가 환경 때문에 돌리지 못했다고 보고한 필수 검증이 있으면 통과로 치지 않는다. "표에 없다"는 이유로 빼지도 않는다. 명세가 필수라고 한 것이면 `확인 필요`로 두고 사용자에게 알린다(환경을 갖춰 다시 돌린다, 그 조건을 뺀다).
   - 다시 돌린 뒤 HEAD와 status가 처음 본 것과 같은지 본다. 다르면(작업자가 아직 쓰는 중이었다) 처음부터 다시 확인한다.
   - 명령·결과·확인한 HEAD를 확인 기록에 적는다. **구현 확인의 통과는 상태 `확인 통과`가 아니다.**
   - 실패: 상태를 `확인 실패`로 적고 사용자에게 알린 뒤 12로 간다(검토로 보내지 않는다).
   - 명령을 돌릴 수 없거나 무결성을 판정할 수 없음: `확인 필요`로 두고 사용자에게 알린다.
   - 통과: 쓸 수 있는 첫 검토 결과를 아직 받지 않았으면 9로, 받았으면 13으로 간다. 첫 구현의 확인이 실패해 고친 경우도 검토를 받은 적이 없으므로 9로 간다.
9. **첫 검토를 맡긴다.** 검토할 HEAD `H`와 그때의 `git status`를 기록한다. [delegate-review-spec.md](delegate-review-spec.md)를 채워 기록 옆에 `review-spec.md`로 둔다. 같은 worktree에 검토자를 새로 띄운다: `--agent codex --spec-file <검토 명세> --worktree path:<worktree> --run <run>`. 모델 옵션은 주지 않는다. 결과의 Task·Dispatch·터미널을 기록하고 상태를 `검토 중`으로 바꾼다. 턴을 끝낸다.
10. **검토 결과를 받는다.** 검토자의 `worker_done`을 받으면:
    - 그 Dispatch가 끝났는지 본다.
    - 지금 HEAD와 `git status`가 검토를 맡길 때 적어 둔 것과 같은지 대조한다. 다르면 그 검토 결과를 쓰지 않는다. 적어 둔 `H`와 status를 기준으로 그 뒤의 커밋, 추적 파일 diff, 추적되지 않는 파일을 기록하고, `확인 필요`로 둔 뒤 사용자에게 알린다.
    - 같으면 보고서를 읽고 검토 이력 표에 적는다.
    - **재검토 상한**: 재검토는 두 번까지다. 사용자의 추가 요구 때문에 맡긴 재검토도 센다. 두 번째 재검토의 결론도 `수정 필요`면 11로 가지 않는다. `확인 필요`로 두고 사용자에게 묻는다(더 돌린다, 지휘로 넘긴다, 그만둔다).
11. **지적을 판정한다.** 지적마다 `지금 고침` 또는 `안 고침(이유)`을 기록에 적는다. 차단·중요 지적을 고치지 않으려면 사용자에게 이유를 알리고 확인받는다. 사소한 지적은 관리자가 정한다. 고칠 것이 없으면 14로 간다.
12. **고치게 한다.** 사용자의 추가 요구면 보내기 전에 "여러 맡기기"의 확인을 다시 한다. 고칠 것(확인 실패, `지금 고침` 지적, 사용자의 추가 요구)을 구현자의 마지막 Dispatch에 "보내기"로 보낸다. 규칙은 처음 명세 그대로라고 적는다. 범위를 넓히는 요구면 무엇이 달라지는지와 새 수용 기준을 함께 적는다. 결과의 새 Task·Dispatch를 기록하고 상태를 `배정됨`으로 바꾼다. 완료 보고를 그 Dispatch와 맞춰 본 뒤 8로 간다.
13. **수정 뒤 갈림.** 검토를 받은 뒤의 수정이다. 여기서 "이전 `H`"는 검토자가 마지막으로 본 HEAD다.
    - 이전 `H` 뒤에 고친 것이 사소한 검토 지적뿐이면 재검토하지 않는다. 관리자가 `git diff <이전 H>..<새 H>`를 직접 읽고 14로 간다.
    - 그 밖의 수정(차단·중요 지적, 검토 뒤에 난 확인 실패의 수정, 사용자의 추가 요구)이 하나라도 있으면 **재검토**를 맡긴다. 재검토를 이미 두 번 받았으면 세 번째를 맡기지 않는다. `확인 필요`로 두고 사용자에게 묻는다(10의 상한과 같다). 아니면 검토자의 마지막 Dispatch에 "보내기"로 delegate-review-spec.md "재검토 요청"을 채워 보낸다. 새 `H`와 status, 새 Dispatch를 기록하고 상태를 `검토 중`으로 바꾼 뒤 10으로 간다.
14. **마지막 확인.** 마지막 HEAD에서 한다.
    - `C..H` 전체 diff를 읽는다.
    - `지금 고침`으로 정한 지적이 모두 처리됐는지 본다.
    - 그 HEAD에서 구현 확인이 이미 통과했고 그 뒤 HEAD와 status가 그대로면 수용 기준을 다시 돌리지 않는다. HEAD나 실행 조건이 달라졌거나 관리자와 검토자의 결과가 어긋나면 다시 돌린다.
    - 통과: 상태를 `확인 통과`로 바꾸고 사용자에게 알린다(검토 결론, 지적 처분, 수용 기준 결과). 검토 보고서의 "범위 밖에서 본 것"과 "사람이 직접 확인해야 할 것"도 그대로 전한다. 관리자가 그것을 고칠 일로 바꾸지 않는다. 고칠지는 사용자가 정한다.
    - 실패(다시 돌린 수용 기준이 실패했다, diff에서 빠진 수정이나 새 결함을 찾았다): 상태를 `확인 실패`로 적고 사용자에게 알린 뒤 12로 간다. 고친 뒤에는 8을 거쳐 13의 "그 밖의 수정"으로 재검토를 받는다.
    - 명령을 돌릴 수 없거나 무결성을 판정할 수 없음: `확인 필요`로 두고 사용자에게 알린다.
15. **끝낸다(반영).** 결과를 어떻게 반영할지(PR, 기준 브랜치에 로컬 병합, 그대로 둠)는 사용자가 정한다. push·PR·병합은 사용자 지시로만 한다(v-mode 고정 규칙 5). 기준 브랜치에 반영하는 일은 **한 번에 하나만** 한다. 한 맡기기의 반영이 끝나기 전(아래 실패 처리 포함)에는 다른 맡기기를 반영하지 않는다.
    - **반영 전에 기준을 본다.** 기준 브랜치의 지금 SHA(tip)와 현재 확인 기준 `C`를 견준다. 견준 tip과 실제로 반영에 쓴 tip을 기록한다.
      - tip이 `C`와 같으면 그대로 반영한다.
      - tip이 `C`와 다르고 `C`의 자손도 아니면(되돌려졌거나 다른 계통으로 갈라졌다) 반영하지 않고 사용자에게 알린다.
      - tip이 `C`의 자손이면(다른 것이 먼저 반영됐다) 먼저 작업 유형을 가린다. `ui-polish`면 충돌이 있든 없든 "`ui-polish` 맡기기"의 "기준이 움직였을 때"로 간다. 그 밖의 일이면 `git merge-tree --write-tree <기준 브랜치> <작업 브랜치>`로 충돌이 나는지 본다. 이 명령은 작업 폴더를 건드리지 않는다. 관리자의 기준 checkout에서 실제 병합을 시도해 충돌을 남기지 않는다. 충돌이 없으면 사용자에게 "기준이 움직였고 충돌은 없다"를 알리고, 사용자가 정한 방법으로 반영한다. 충돌이 있으면 관리자가 풀지 않고 아래 "기준을 맞추는 일"을 맡긴다.
    - 반영했으면 기준 브랜치에서 이 맡기기의 수용 기준 명령을 모두 다시 돌린다. 앞서 반영한 다른 맡기기가 있으면 그 맡기기들의 수용 기준도 함께 돌린다.
    - **반영한 뒤 수용 기준이 실패하면** `끝`으로 닫지 않는다. 실패한 통합 SHA와 명령·결과를 기록하고 `확인 실패`로 둔 뒤 사용자에게 알린다. 사용자가 정한다: 반영을 되돌린다, 구현자에게 고치게 한다(작업 브랜치를 기준에 맞춘 뒤 고치고, 구현 확인과 재검토를 거쳐 다시 반영한다). 그동안 다른 맡기기의 반영은 멈춘다.
    - 반영이 끝나면 두 작업자의 모든 Dispatch에 "정리"를 한다. 후속 지시로 터미널을 넘겨준 앞선 Dispatch는 `worker-release`가 `retained`·`ownership_transferred`로 답한다. 그 터미널의 마지막 Dispatch가 `released`면 끝난 것이다. worktree를 지울지 남길지 사용자에게 묻고, 지우면 "worktree 지우기". 기록을 `끝`으로 바꾼다.

### 기준을 맞추는 일

반영 전에 충돌이 보였을 때 구현자의 마지막 Dispatch에 "보내기"로 맡긴다. 보내기 전에 "여러 맡기기"의 확인을 다시 한다.

- `bug-fix`·`feature`·`refactoring`이면 그 레시피의 `rebase` 절차를 따르게 한다. 빼는 것은 계약의 증거 폴더, manifest, 계약 보고 양식뿐이다. **rebase한 마지막 HEAD에서 필수 수용 기준을 모두 다시 돌리는 단계는 남긴다**(새 빌드와 새 서버로). 그 결과는 완료 보고에 싣는다. 레시피가 없으면 `git rebase <기준 브랜치>` 뒤 수용 기준을 모두 다시 돌리게 한다. `ui-polish`는 rebase하지 않는다("`ui-polish` 맡기기").
- 구현자의 권한에 "이 worktree의 작업 브랜치를 기준 브랜치 위로 rebase한다"를 이 후속 지시에 한해 더한다. 원격에 올린 브랜치면 force-push가 따르므로 v-mode 고정 규칙 5대로 사용자 확인을 받는다.
- **기준을 둘로 나눠 적는다.** 최초 기준 `B`는 이력으로 남긴다. 현재 확인 기준 `C`는 기준을 맞출 때마다 새 기준 SHA로 바꾼다. 구현 확인(8), 마지막 확인(14), 검토가 "이 맡기기의 변경"으로 읽는 범위는 `C..H`다. `B..H`로 읽으면 다른 맡기기가 기준에 넣은 변경까지 이 작업자의 변경(건드리지 말 곳 위반 포함)으로 보게 된다.
- `refactoring`: 관리자가 후속 지시에 옛 `S`와 옛 `P`, 새 원래 동작 기준(새 `C`)을 적는다. 그 기준에 대응하는 새 `P`는 구현자가 레시피대로 찾아 확인하고 보고한다. 관리자는 보고된 새 `P`를 기록에 적을 뿐, 스스로 정하지 않는다.
- 그 뒤 구현 확인(8)을 하고 재검토를 맡긴다([delegate-review-spec.md](delegate-review-spec.md) "재검토 요청"의 기준을 맞춘 뒤 줄). 재검토의 범위는 `git range-diff <직전 C>..<옛 H> <새 C>..<새 H>`와 `git diff <새 C>...<새 H>`다. 두 번째로 기준을 맞출 때의 "직전 `C`"는 최초 `B`가 아니라 바로 앞의 `C`다. 재검토 상한에 센다.

사용자가 중단하면 일하는 중인 작업자를 "정지"로 멈추고 정지를 확인한 뒤, worktree를 남긴 채 `끝(중단)`으로 닫는다. 정지나 해제를 증명하지 못하면 `확인 필요`로 두고 사용자에게 알린다.

### Codex를 쓸 수 없을 때

검토자를 띄울 수 없거나(아래 "시작 실패") 한도가 떨어져 검토가 끝나지 않으면, 검토 없이 `확인 통과`로 넘어가지 않는다. `확인 필요`로 두고 사용자에게 묻는다.

- 기다렸다가 다시 맡긴다.
- 교차 검토 없이 끝낸다. 기록과 사용자 보고에 "교차 검토 없음"을 적고 14로 간다.
- 지휘로 넘긴다(`끝(지휘로 넘김)`).

### 읽기 전용의 한계

Orca에는 작업자를 읽기 전용으로 띄우는 옵션이 없다(`worker-start --help`, Orca 1.4.257). 검토자의 읽기 전용은 검토 명세의 지시와 10의 대조로 지킨다. 이 대조는 보는 시점의 Git 상태가 같다는 것만 보인다. Git이 무시하는 파일에 쓴 것, 고쳤다가 되돌린 것은 잡지 못한다.

쓰면 안 되는 쪽의 쓰기를 찾으면:

- 검토자가 worktree 안을 바꿨으면 10을 따른다.
- 검토자가 worktree 밖의 허용되지 않은 곳(보고서 경로와 OS 임시 폴더가 아닌 곳)에 썼으면, 검토자의 정지를 확인하고 영향을 본 뒤 사용자에게 알린다.
- 조사 서브에이전트가 썼으면 기록한다. 아직 쓰는 중이거나 맡긴 worktree 밖에 썼으면 구현자의 정지를 확인하고 영향을 본 뒤 사용자에게 알린다. 맡긴 worktree 안에서 이미 끝난 쓰기면 기록하고 이어 간다(커밋에 들어갔는지는 8과 14의 diff에서 본다).
- 누가 언제 썼는지 판정할 수 없으면 `확인 필요`다.

## 시작 실패

`worker-start`가 실패했거나(결과의 `failedStage`가 `agent_readiness` 등), 터미널은 떴지만 에이전트가 명세를 받기 전에 끝난 경우다. 구현자와 검토자 모두 여기를 따른다.

1. 같은 명령을 되풀이하지 않는다. `worker-show`와 `worker-read`로 상태와 터미널 출력을 읽어 원인을 본다.
2. 에이전트가 끝난 것을 확인한 뒤 그 Dispatch를 "정리"로 해제한다. worktree가 띄우기 전과 같은지 본다(구현자면 HEAD가 `B`이고 status가 비어 있다. 검토자면 9에서 적어 둔 `H`와 status와 같다). 아니면(작업자가 무엇인가 썼다) 시작 실패로 다루지 않는다. 다시 띄우지 않고 `확인 필요`로 둔 채 사용자에게 알린다. 이 경우는 돌려 보지 않았다.
3. 기록을 `확인 필요`로 두고, Dispatch 이력 표에 실패한 단계와 오류를, 사건에 원인을 적은 뒤 사용자에게 알린다. 원인이 이 PC의 설정(OS 보안 정책, 에이전트 설치·설정·로그인)이면 관리자가 바꾸지 않는다. 사용자가 정한다.
4. 사용자가 고른다.
   - **원인을 고친 뒤 다시 띄운다.** "맡기기 전에" 4와 위 2의 worktree 확인을 다시 한다. 그다음 같은 Task로 띄운다: `orca orchestration worker-start --task <Task> --retry-of <실패한 Dispatch> --worktree path:<worktree> --agent <claude 또는 codex> --run <run>`. 구현자면 `--model opus`도 붙인다. 명세는 그 Task의 것이 그대로 간다(`--spec-file`을 다시 주지 않는다). 새 Dispatch를 이력 표에 더하고 "절차" 6(검토자면 9의 기록)부터 이어 간다.
   - **맡기지 않는다.** 구현자였으면 worktree를 지울지 남길지 묻고 기록을 `끝(중단)`으로 닫는다. 관리자가 대신 구현하지 않는다. 검토자였으면 위 "Codex를 쓸 수 없을 때"의 선택으로 간다. 이 길은 돌려 보지 않았다.

## 기록

- 위치: 메인 저장소(기본 checkout)의 `.local/vstack-delegate/<이름>/state.md`. 같은 폴더에 구현 명세 `spec.md`, 검토 명세 `review-spec.md`, 검토 보고서 `review-<k>.md`를 둔다. 지휘의 `.local/vstack/`과 섞지 않는다. 쓰기 전에 `git check-ignore .local/x`로 Git에서 빠졌는지 보고, 아니면 [../orchestrate-issues/setup.md](../orchestrate-issues/setup.md)의 방법으로 뺀다.
- `state.md`의 첫 줄은 상태다. `끝`으로 시작하지 않으면 진행 중이다.

  | 상태 | 뜻 |
  | --- | --- |
  | `예약` | 이름과 기준을 정했다. 아직 띄우지 않았다 |
  | `배정됨` | 구현자가 일하는 중이다(첫 구현, 수정) |
  | `질문 중` | 작업자의 질문에 답을 기다린다 |
  | `검토 중` | 검토자가 일하는 중이다(첫 검토, 재검토) |
  | `확인 실패` | 구현 확인이나 마지막 확인이 실패했다. 고치게 하면 `배정됨`으로 간다 |
  | `확인 필요` | 관리자가 혼자 판정할 수 없다(명령 실행 불가, 불명확한 명령 결과, 시작 실패, 검토자가 worktree를 바꿈, Codex를 못 씀, 재검토 상한) |
  | `확인 통과` | 마지막 확인이 통과했다. "절차" 14에서만 쓴다 |
  | `막힘` | 띄우기 전에 worktree가 기준과 다르다 등, 사용자에게 물어야 풀린다 |
  | `끝`, `끝(중단)`, `끝(지휘로 넘김)` | 닫혔다 |

- 내용: 소유 `vstack-delegate`, 관리자(Orca 세션 식별자), Run, 기준 브랜치와 `B`, 현재 확인 기준 `C`와 그 이력, 예정 쓰기 영역과 검증 자원, 작업 브랜치, worktree 경로, 레시피, Dispatch 이력 표(차례, 역할(구현·검토), Task, Dispatch, 터미널, 보낸 지시, 결과), 구현자와 검토자 각각의 마지막 Dispatch, 확인 기록(HEAD, 명령, 결과), 검토 이력 표(차례, 대상 `H`, 보고서, 결론, 지적마다의 처분), 재검토를 받은 횟수, 반영 기록(견준 tip, 반영에 쓴 tip, 통합 SHA, 그 뒤 수용 기준 결과), 사건(질문·답·중단, 겹침 판정, 계획과 다르게 한 것).
- 앞선 구조의 기록에 있는 "지휘자" 칸은 관리자와 같은 뜻이다.

## 관리자가 다시 시작했을 때

v-mode 고르기 0이 진행 중인 기록을 찾으면 여기로 온다.

1. backends/orca.md "준비"의 `run-use`로 기록의 Run에 묶는다. 진행 중인 맡기기가 여럿이면 모두 같은 Run이다("여러 맡기기"). 기록마다 `worker-show`와 `inbox --terminal run:<run> --full`로 두 작업자의 상태와 놓친 보고를 읽고, 메시지를 Dispatch로 기록에 나눈다.
2. 사용자에게 상태를 알리고 이어받을지 묻는다. 기록의 관리자와 지금 세션이 다르다는 것, 이 경로는 돌려 보지 않았다는 것도 알린다.
3. 승인받으면 기록의 관리자 칸을 바꾸고 "절차"의 남은 단계를 이어 간다. 작업자를 다시 띄우지 않는다. 작업자가 사라졌으면 `막힘`으로 두고 사용자에게 묻는다.
