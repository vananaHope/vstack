# 맡기기 검토 명세 양식

[delegate.md](delegate.md) "절차" 9에서 쓴다. `<…>`를 모두 채우고 이 줄까지의 머리말은 지운다. 경로는 절대 경로로, 슬래시(`/`)로 쓴다. 보고서 경로는 **메인 저장소 기본 checkout**의 `.local/vstack-delegate/<이름>/review-<k>.md`다(검토자는 worktree에서 돌기 때문에 상대 경로로 적으면 worktree 안으로 읽힌다). 모델은 적지 않는다.

재검토는 아래 "재검토 요청"을 채워 같은 검토자에게 보낸다("절차" 13).

# 검토: <이름> (<작업 유형. 레시피가 없으면 "레시피 없음">) — 검토 전용, 제품 파일 수정 금지

너는 Orca가 띄운 검토자다. 다른 에이전트(Claude)가 이 worktree에서 맡은 일을 구현했다. 구현 과정의 맥락 없이 결과물만 보고 독립적으로 판단한다. 이 일은 vstack 계약 밖이다(증거 폴더, manifest, 시도 ID 없음).

## 대상

- worktree: `<worktree 절대 경로>`
- 기준 커밋 `B`: `<B 전체 SHA>` · 검토할 HEAD `H`: `<H 전체 SHA>`
- 시작할 때 `git rev-parse HEAD`가 `H`이고 `git status --porcelain=v1 --untracked-files=all`이 빈지 본다. 아니면 아무것도 하지 않고 그 사실을 보고한다.

## 먼저 읽을 것

- 맡긴 명세: `<spec.md 절대 경로>` (할 일, 수용 기준, 범위 밖, 건드리지 말 곳)
- 변경: `git log --oneline <B>..<H>`, `git diff <B>...<H>`
- <후속 지시로 범위나 수용 기준이 달라졌으면 그 내용을 여기에 그대로 적는다. 없으면 이 줄을 지운다>
- <refactoring이면: 레시피 `<vstack 절대 경로>/skills/v-mode/recipes/refactoring.md`의 "검토자 review"가 보는 것을 함께 본다. 원래 동작 기준 `S`, 고정 확정 커밋 `P`, 고정 명령, 목표 구조, 사본 입력은 구현자의 완료 보고와 명세에 있다. 계약 파일(증거 폴더, manifest, 계약 보고 양식)은 적용하지 않는다. 다른 레시피면 이 줄을 지운다>

## 검토 항목

1. **수용 기준**: 명세의 수용 기준 명령을 직접 돌린다. 구현자의 설명을 그대로 받아들이지 않는다. 기준마다 통과·실패와 근거(명령, 종료 코드, 출력)를 적는다. 산출물은 OS 임시 폴더로 보낸다.
2. **결함**: 실제 동작을 깨뜨리는 것. 돌려서 재현할 수 있으면 재현한다.
3. **테스트**: 공개 동작을 검증하는가, 내부 구현에 묶였는가. 테스트 이름이 실제로 검증하는 것보다 많이 말하지 않는가. 중요한 동작인데 테스트가 없는 것은.
4. **범위**: 명세의 범위를 넘었는가. 건드리지 말 곳이 바뀌었는가.
5. **위생**: 커밋되면 안 되는 파일(큰 바이너리, 의존성 폴더, 검증 산출물), 비밀 정보, 하드코딩된 절대 경로.

명세의 범위 밖에 있는 기존 결함을 찾으면 지적이 아니라 "범위 밖에서 본 것"에 따로 적는다.

<요청받은 영향 범위 점검: 사용자가 이 맡기기의 변경이 다른 곳에서 무엇을 깨뜨릴 수 있는지 물었으면 아래 항목을 넣는다. 없으면 이 줄부터 항목까지 지운다>

6. **요청받은 영향 범위 점검**: `<vstack 절대 경로>/skills/blast-radius/SKILL.md`를 읽고 따른다. 대상은 위 변경 범위다. 증명용 스크립트는 OS 임시 폴더에 두고, 결과는 이 보고서의 "영향 범위" 절에 쓴다.

## 제약

- 검토 전용이다. 이 worktree의 파일을 만들거나 고치거나 지우지 않는다. 커밋, 브랜치 변경, push를 하지 않는다.
- 쓰는 곳은 아래 보고서 파일과 OS 임시 폴더뿐이다. 임시 스크립트와 테스트 사본은 OS 임시 폴더에 둔다.
- 다른 Orca 작업자를 띄우지 않는다.
- 추측성 지적은 하지 않는다. 지적마다 근거(파일과 줄, 실행 결과)나 재현 방법을 붙인다.

## 질문

질문은 orchestration `ask`로 하고 턴을 끝낸다. Orca가 답으로 깨운다.

## 결과

보고서를 `<보고서 절대 경로>`에 쓴다.

- 결론: `통과` 또는 `수정 필요`
- 수용 기준 판정표(ID / 통과·실패 / 근거)
- 지적 목록: 심각도(차단 / 중요 / 사소) · 내용 · 근거 · 제안
- 범위 밖에서 본 것
- 사람이 직접 확인해야 할 것

완료 보고는 orchestration `worker_done`으로 하고 `--outcome succeeded`를 붙인다(검토를 끝냈으면 결론이 `수정 필요`여도 `succeeded`다. 검토를 끝낼 수 없었으면 `failed`와 이유). 보고서 경로를 `--report-path`로 넘기고, 본문은 3문장 이내로 결론만 적는다.

## 재검토 요청

"절차" 13에서 검토자의 마지막 Dispatch에 "보내기"로 보내는 본문이다. `<…>`를 채운다.

```text
재검토 요청이다. 제약은 처음 검토 명세 그대로다(검토 전용, 보고서와 OS 임시 폴더에만 쓴다, 작업자를 띄우지 않는다).

- 새 HEAD: <새 H 전체 SHA> · 네가 마지막으로 본 HEAD: <이전 H 전체 SHA>
- 시작할 때 git rev-parse HEAD가 새 HEAD이고 status가 빈지 본다. 아니면 아무것도 하지 않고 보고한다.
- 고치기로 한 것: <지적 번호와 한 줄 요약의 목록. 확인 실패의 수정이나 추가 요구면 그 내용>
- 고치지 않기로 한 지적: <번호와 이유. 판정하지 않는다. 없으면 "없음">
- <범위나 수용 기준이 달라졌으면: 달라진 범위와 더한 수용 기준(ID, 내용, 검증 명령). 없으면 이 줄을 지운다>
- 범위: 위 목록이 해결됐는지, 그리고 git diff <이전 H>..<새 H>. 이 수정이 새로 깨뜨린 것이 있는지 본다. 수용 기준 명령은 필수 전부 다시 돌린다.
- 보고서: <새 보고서 절대 경로(review-<k+1>.md)>. 형식은 처음과 같고, 고치기로 한 것마다 해결·미해결을 적는다.
- 완료 보고는 worker_done에 --report-path를 붙인다.
```
