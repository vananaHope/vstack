- worktree: `<worktree 절대 경로>`
- 기준 커밋 `C`: `<현재 확인 기준 C 전체 SHA. 기준을 맞춘 적이 없으면 최초 기준 B>` · 검토할 HEAD `H`: `<H 전체 SHA>`

- 변경: `git log --oneline <C>..<H>`, `git diff <C>...<H>`
- <후속 지시로 범위나 수용 기준이 달라졌으면 그 내용을 여기에 그대로 적는다. 없으면 이 줄을 지운다>
- <refactoring이면: 레시피 `<vstack 절대 경로>/skills/v-mode/recipes/refactoring.md`의 "검토자 review"가 보는 것을 함께 본다. 원래 동작 기준 `S`, 고정 명령, 목표 구조, 사본 입력은 명세에 있다. 고정 확정 커밋 `P`(`<P 전체 SHA>`), 고정이 바꿀 코드를 지나가는지 본 결과, `S`·`P`·`H`에서 고정을 돌린 결과, 더한 고정 테스트는 위 완료 보고에 있다. 계약 파일(증거 폴더, manifest, 계약 보고 양식)은 적용하지 않는다. 다른 레시피면 이 줄을 지운다>

## 검토 항목

1. **수용 기준**: 명세의 수용 기준 명령을 직접 돌린다. 구현자의 설명을 그대로 받아들이지 않는다. 기준마다 통과·실패와 근거(명령, 종료 코드, 출력)를 적는다. 산출물은 OS 임시 폴더로 보낸다.
2. **결함**: 실제 동작을 깨뜨리는 것. 돌려서 재현할 수 있으면 재현한다.
3. **테스트**: 공개 동작을 검증하는가, 내부 구현에 묶였는가. 테스트 이름이 실제로 검증하는 것보다 많이 말하지 않는가. 중요한 동작인데 테스트가 없는 것은.
4. **범위**: 명세의 범위를 넘었는가. 건드리지 말 곳이 바뀌었는가.
5. **위생**: 커밋되면 안 되는 파일(큰 바이너리, 의존성 폴더, 검증 산출물), 비밀 정보, 하드코딩된 절대 경로.

명세의 범위 밖에 있는 기존 결함을 찾으면 지적이 아니라 "범위 밖에서 본 것"에 따로 적는다.

<correct면 위 1~5에 아래 6을 더한다. 다른 레시피면 이 줄부터 6까지 지운다>

6. **막는 장치**(레시피 `<vstack 절대 경로>/skills/v-mode/recipes/correct.md`): 유형마다 완료 보고의 재현 증명을 다시 한다. OS 임시 폴더의 새 폴더에 `git archive <H>`로 풀고, 명세의 사본 입력을 넣고, 보고된 재현점을 넣어 검사 명령을 돌린다. 그 유형의 오류로 실패하는지, 오류가 고칠 곳을 말하는지, worktree의 `H`에서는 통과하는지 본다. 끝나면 그 폴더를 지운다. 그리고 본다: 더 높은 층이 정말 안 됐는가, 검사가 정상 코드까지 막지 않는가, 기준선이 새로 늘어난 것만 막는가, 예외에 이유·만료일·승인이 있는가, 규칙 표의 줄이 실제 장치를 가리키는가, 지우거나 약하게 한 테스트가 있는가와 그 이유.

<ui-polish면 위 1~5 대신 아래 1~6을 둔다. 다른 레시피면 이 줄부터 한계 줄까지 지운다>

1. **동작**: diff가 동작, 데이터, 문구의 뜻을 바꾸지 않았는가. 사용자가 정한 문구는 글자 그대로인가.
2. **항목**: 지금 유효한 수용 기준 표(`<spec.md 절대 경로>`)의 항목마다, 관찰 가능한 문장(숫자, 상태)이 마지막 사진과 잰 값에서 성립하는가. 모양이 더 나은지(취향)는 판정하지 않는다. 사용자가 본다. 사용자가 거둔 항목이 되돌려진 것은 실패가 아니라 "요청대로 되돌려짐"이다.
3. **다른 화면 보존**: 지금 유효한 기준 폴더는 `<기준 기록의 현재 기준 폴더 절대 경로. 수단을 바꿔 다시 확정했으면 baseline-2 등>`이다. `python -I <vstack 절대 경로>/skills/v-mode/recipes/scripts/image_diff.py <현재 기준 폴더> <마지막 촬영 폴더> --expect <사진 폴더>/keep.txt`를 다시 돌려 종료 코드와 출력을 적는다. `keep.txt`가 비었으면 건너뛰고 그렇게 적는다.
4. **다른 확인**: `keep-other.txt`의 화면마다, 명령으로 하는 확인이면 다시 돌리고, 눈으로 하는 확인이면 사용자의 판정이 기록에 있는지 본다.
5. **기존 검사**: 명세의 수용 기준에 있는 프로젝트 검사를 다시 돌린다.
6. **기준 대조**: 목록 파일의 내용, 현재 기준 폴더의 경로와 그 안의 파일 이름과 SHA-256, 촬영 수단의 설정이 관리자의 기준 기록(`<state.md 절대 경로>`의 "기준 기록", 승인된 변경 포함)과 같은가.

- 한계: 검토자는 판정에 쓰는 사진을 사진 폴더에 다시 찍지 않는다(5의 기존 검사가 화면을 찍으면 그 출력은 OS 임시 폴더에 두고 종료 코드로만 판정한다). 사진이 그 커밋에서 제대로 찍혔는지는 구현자의 촬영 기록(대상 SHA, 종료 코드)과 기준 해시 대조까지만 본다. 보고서에 이 한계를 적는다.

<요청받은 영향 범위 점검: 사용자가 이 맡기기의 변경이 다른 곳에서 무엇을 깨뜨릴 수 있는지 물었으면 아래 항목을 넣는다. 없으면 이 줄부터 항목까지 지운다>

- **요청받은 영향 범위 점검**(검토 항목에 더한다): `<vstack 절대 경로>/skills/blast-radius/SKILL.md`를 읽고 따른다. 대상은 위 변경 범위다. 증명용 스크립트는 OS 임시 폴더에 두고, 결과는 이 보고서의 "영향 범위" 절에 쓴다.

## 제약

- 검토 전용이다. 이 worktree의 파일을 만들거나 고치거나 지우지 않는다. 커밋, 브랜치 변경, push를 하지 않는다.
- 쓰는 곳은 아래 보고서 파일과 OS 임시 폴더뿐이다. 임시 스크립트와 테스트 사본은 OS 임시 폴더에 둔다. `ui-polish`의 사진 폴더는 읽기만 한다.
- 다른 Orca 작업자를 띄우지 않는다.
- 추측성 지적은 하지 않는다. 지적마다 근거(파일과 줄, 실행 결과)나 재현 방법을 붙인다.

## 질문

질문은 orchestration `ask`로 하고 턴을 끝낸다. Orca가 답으로 깨운다.

## 결과

## 재검토 요청

"절차" 13에서 검토자의 마지막 Dispatch에 "보내기"로 보내는 본문이다. `<…>`를 채운다.

```text
재검토 요청이다. 제약은 처음 검토 명세 그대로다(검토 전용, 보고서와 OS 임시 폴더에만 쓴다, 작업자를 띄우지 않는다).

- 새 HEAD: <새 H 전체 SHA> · 네가 마지막으로 본 HEAD: <이전 H 전체 SHA>
- 시작할 때 git rev-parse HEAD가 새 HEAD이고 status가 빈지 본다. 아니면 아무것도 하지 않고 보고한다.
- 구현자의 이번 완료 보고: <기록 폴더의 impl-report-<k>.md 절대 경로>
- 고치기로 한 것: <지적 번호와 한 줄 요약의 목록. 확인 실패의 수정이나 추가 요구면 그 내용>
- 고치지 않기로 한 지적: <번호와 이유. 판정하지 않는다. 없으면 "없음">
- <범위나 수용 기준이 달라졌으면: 달라진 범위와 더한 수용 기준(ID, 내용, 검증 명령). 없으면 이 줄을 지운다>
- 범위: 위 목록이 해결됐는지, 그리고 git diff <이전 H>..<새 H>. 이 수정이 새로 깨뜨린 것이 있는지 본다. 수용 기준 명령은 필수 전부 다시 돌린다.
- <기준을 맞춘 뒤의 재검토면 위 범위 줄을 이것으로 바꾼다: 기준이 <직전 C 전체 SHA>에서 <새 C 전체 SHA>로 바뀌었다. git range-diff <직전 C>..<이전 H> <새 C>..<새 H>로 rebase가 바꾼 것을 보고, git diff <새 C>...<새 H>로 이 맡기기의 변경 전체를 본다. 새 기준에 들어온 다른 변경은 이 맡기기의 변경으로 보지 않는다. 수용 기준 명령은 필수 전부 다시 돌린다. refactoring이면 옛 S·P와 새 P를 함께 적는다>
- <사용자가 이 재검토에 영향 범위 점검을 요청했으면: 요청받은 영향 범위 점검: <vstack 절대 경로>/skills/blast-radius/SKILL.md를 읽고 따른다. 대상은 위 범위다. 증명용 스크립트는 OS 임시 폴더에 두고, 결과는 새 보고서의 "영향 범위" 절에 쓴다. 처음 검토 명세에 그 항목이 없었어도 이 줄대로 한다. 없으면 이 줄을 지운다>
- 보고서: <새 보고서 절대 경로(review-<k+1>.md)>. 형식은 처음과 같고, 고치기로 한 것마다 해결·미해결을 적는다.
- 완료 보고는 worker_done에 --report-path를 붙인다.
```
