# 성능 개선

id: perf · version: 1 · contract: vstack-contract@3

pstack의 `playbooks/perf-issue.md`를 따른다. 고치는 일마다 측정을 붙이고, 소스를 읽는 것으로 측정을 대신하지 않는다. 측정이 믿을 만한지는 [benchmark-checklist](../../benchmark-checklist/SKILL.md)로 본다. 성능 회귀의 원인을 좁힐 때는 [diagnosing-bugs](../../diagnosing-bugs/SKILL.md)의 Phase 4 "Perf branch"(기준 측정 뒤 이분 탐색)를 쓴다. 원본의 하위 에이전트 구현 위임, 모델 지정, `how`·`architect` 단계, PR 단계, 지표를 오래 올리는 hillclimb는 뺐다. 가져온 것과 뺀 것은 저장소의 `UPSTREAM.md`에 있다.

**맡기기 갈래에서 작업자에게 맡긴다.** 지휘에는 연결하지 않았다. 그래서 검토자 절차, 지적 수정·rebase·재검증 절차, 증거 만들기 단계가 없다. 검토는 맡기기의 Codex 검토자가 하고, 맡기는 절차는 [delegate.md](../delegate.md)에 있다. 아래 "구현자"는 맡기기의 구현자(Orca 작업자)이고 "관리자"는 맡기기의 관리자다. "사용자에게 묻는다"는 구현자가 `ask`로 관리자에게 묻고, 관리자가 사용자에게 물어 답을 보낸다는 뜻이다.

## 언제

이미 동작하는 사용자 경로가 느린 것을 측정해 빠르게 하는 일. "목록이 느려", "이 요청이 2초 걸려", "지난 버전보다 느려졌어".

쓰지 않을 때:

- 결과가 틀린 것: 버그 수정(`bug-fix`). 느림 때문에 시간 제한에 걸려 실패하는 것도 결과가 틀린 것이면 그쪽이다.
- 무엇이 얼마나 느린지 정해지지 않은 요청("전체적으로 빠르게"): 레시피를 시작하지 않는다. 관리자가 사용자와 대상 경로와 목표를 먼저 정한다.
- 하나의 지표를 여러 번에 걸쳐 계속 올리는 일: 한 번의 맡기기로 끝나지 않는다. 여러 단위로 나눠 지휘하거나 단위마다 따로 맡긴다.
- 구조를 크게 바꿔야 빨라지는 일(여러 모듈의 소유를 옮김, 공용 인터페이스 변경): 리팩토링을 먼저 따로 맡긴다. 하다가 그렇게 되면 묻는다.

## 입력

관리자가 맡기기 전에 정한다([delegate.md](../delegate.md) "입력").

1. **대상 경로와 증상**: 어느 사용자 경로가 어떤 데이터 크기와 동시성에서 얼마나 걸리는지. 회귀면 빨랐던 커밋이나 버전.
2. **측정 명령**: 그 경로를 재는, 저장소에 있는 명령(벤치마크 스크립트, 부하 도구, 프로젝트의 측정 하네스). 결과를 숫자와 단위로 내고, 오류 수와 일이 실제로 일어났다는 표시(처리한 행 수, 응답 수)를 낸다. 없으면 v-mode 고정 규칙 7이 먼저다(delegate.md "검증 수단이 없을 때"로 측정 명령을 먼저 맡긴다).
3. **목표**: 관찰 가능한 숫자("20000건 `list`의 p50이 200 ms 아래"). 사용자가 정한다. 숫자가 없으면 묻는다.
4. **동작 보존 검사**: 바뀌면 안 되는 동작을 보는 명령(기존 테스트, verify 시나리오).
5. **측정 환경**: 데이터(시드, 크기), 빌드 방식(운영과 같은 설정), 다른 맡기기와 함께 쓰는 자원. 측정은 같은 기계의 다른 일에 흔들린다. 다른 맡기기가 같은 기계에서 돌면 그 사실을 명세에 적는다.
6. **사본 입력**: `B`를 재는 사본에 넣을, Git이 무시하는 파일(설치한 의존성, 환경 파일)과 그 출처. 없으면 "없음".
7. **수용 기준**:
   - **목표**: "측정 명령으로 기준 커밋 `B`와 마지막 커밋 `H`를 번갈아 5번 이상 돌려, `H`의 중앙값이 목표를 채우고 두 쪽의 차이가 실행마다의 흔들림보다 크다. 오류 수는 0이고 일이 실제로 일어났다." 검증 절차는 이 문장과 측정 명령으로 맡길 때 정한다. 구현 뒤에 정해지는 `H`만 완료 보고로 받는다.
   - **동작 보존**: 동작 보존 검사가 `H`에서 통과한다.

## 실행 조건

- 맡기기의 구현 명세가 정한 권한을 따른다.
- `B`를 재는 사본은 worktree 밖 OS 임시 폴더의 새 폴더에 `git archive <B>`로 풀어 만든다. 명세의 "사본 입력"대로 무시 파일(설치한 의존성 등)을 넣는다. 끝나면 지운다.
- 프로파일러와 추적 도구는 결과를 늦추므로 보고하는 측정과 따로 돌린다(benchmark-checklist 1). 그 출력은 OS 임시 폴더에 둔다.

## 구현자: 새 개선

1. **기준을 잰다.** [benchmark-checklist](../../benchmark-checklist/SKILL.md)의 "Before you run anything"을 하고, 보고할 문장을 적는다. 측정 명령을 `B`의 사본에서 5번 이상 돌려 중앙값, 범위, 오류 수, 일이 일어났다는 표시를 적는다. 체크리스트 질문 1~7로 이 기준을 검증한다. 입력의 증상이 재현되지 않으면(이미 목표보다 빠르다, 측정이 그 경로를 지나지 않는다) 고치지 말고 관리자에게 묻는다.
2. **한계 요인을 찾는다.** 체크리스트 질문 1. 보고하지 않는 실행에서 프로파일러를 돌려 뜨거운 곳을 소스에 대응시킨다. 회귀면 diagnosing-bugs Phase 4 "Perf branch"대로 빨랐던 커밋과 느린 커밋 사이를 이분 탐색한다. 측정 없이 "여기가 느릴 것"이라고 정하지 않는다. 한계 요인이 설정(디버그 빌드, 행마다 커밋, 빠진 색인)이면 그것부터 본다(질문 2).
3. **싼 것부터 고른다.** 한계 요인에 대해 아래 순서로 보고, 앞의 것이 목표를 채우면 멈춘다.
   1. 하지 않는다. 결과를 아무도 쓰지 않는 일은 싸게 만들지 말고 없앤다.
   2. 하되, 다시 하지 않는다.
   3. 덜 한다.
   4. 나중에 한다.
   5. 보이지 않을 때 한다.
   6. 동시에 한다.
   7. 싸게 한다.
4. **한 번에 하나씩 바꾸고 잰다.** 시도 하나를 바꾸고, 동작 보존 검사를 돌리고, 측정 명령을 돌린다. 나아지지 않았거나 동작 보존이 깨지면 그 시도를 전부 되돌린다. 남기는 시도마다 커밋 하나를 만들고, 커밋 본문에 한계 요인과 숫자(전·후 중앙값)를 적는다. 시도마다 한 줄씩 기록한다(무엇을 바꿨나, 전·후 숫자, 남김·되돌림). 함수 경계를 넘는 바꿈이 예정 쓰기 영역 밖에 닿거나 공용 인터페이스를 바꾸면 하지 말고 관리자에게 묻는다.
5. **끝에 다시 잰다.** 마지막 커밋 `H`와 `B`를 번갈아(B, H, B, H …) 5번 이상씩 돌린다. 체크리스트 질문 3(한계를 넘는 결과인가), 4(오류), 5(재현), 6(사용자가 기다리는 경로 전체에서 얼마인가), 7(일이 실제로 일어났나)을 본다. 결론은 체크리스트 "Report"의 넷 가운데 하나다(빨라짐, 느려짐, 차이 없음, 판단 못 함). 목표를 채우지 못했으면 거기서 멈추고 그대로 보고한다. 기준을 바꾸거나 측정을 고쳐 통과시키지 않는다.
6. **동작 보존 검사를 `H`에서 다시 돌린다.**

## 레시피 예외

없다. 계약과 지휘에 연결하지 않았다.

## 완료 증거

맡기기라 증거 폴더를 쓰지 않는다. 아래 완료 보고가 증거다. 관리자(구현 확인)와 검토자는 명세의 측정 절차를 `B`와 `H`로 다시 돌린다.

## 완료 보고

맡기기 구현 명세의 "완료 보고"에 더해:

- 결론(빨라짐 / 느려짐 / 차이 없음 / 판단 못 함)과 목표를 채웠는지.
- 기준과 마지막 숫자: 단위, 측정 명령, 실행 횟수, 중앙값, 범위, 오류 수, 일이 일어났다는 표시. `B`와 `H`를 번갈아 돈 기록.
- 한계 요인과 그 근거(프로파일 출력의 요약, 소스 위치), 고른 순서(단계 3의 몇 번)와 앞의 것이 안 된 이유.
- 시도 기록(무엇을 바꿨나, 전·후 숫자, 남김·되돌림)과 남긴 커밋.
- 체크리스트 질문 1~7의 답(한 줄씩).
- 동작 보존 검사의 결과.
- 측정 환경(기계의 부하, 함께 돈 일, 빌드 방식). 흔들림을 줄이려고 한 것.
