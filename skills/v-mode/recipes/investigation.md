# 조사

id: investigation · version: 2 · contract: vstack-contract@3

pstack의 `playbooks/investigation.md`(조사는 읽기 전용이고, 고치지 않고 근거가 붙은 설명이나 추천을 낸다)를 따른다. 설명의 형식과 복잡도 나누기는 pstack `how`에서, 동기를 찾는 순서(코드 기준점 → 근거 범주 → 신뢰 단계)는 pstack `why`에서 가져왔다. 원본의 모델 지정, MCP마다 조사 에이전트를 하나씩 띄우는 구조, 종합 에이전트, Cursor 전용 설정은 뺐다. 가져온 것과 뺀 것은 저장소의 `UPSTREAM.md`에 있다.

**바로 갈래에서 관리자가 따른다.** 읽기 전용이라 작업자에게 맡기지 않는다(ADR 0010). 계약과 지휘에는 연결하지 않았다. 그래서 검토자 절차와 증거 만들기 단계가 없다. 아래 "관리자"는 v-mode를 돌리는 대화다.

## 언제

코드가 지금 어떻게 도는지, 왜 이렇게 됐는지, 무엇을 어디에 둬야 하는지를 묻는 일. 바꾸기 전에 구조를 이해하려는 질문도 여기다.

- **어떻게**: "X는 어떻게 동작해", "이 흐름을 설명해 줘", "이 기능은 어디에 있어야 해", "어느 모듈이 이걸 맡아".
- **왜**: "왜 이렇게 했지", "이 값은 어디서 나왔어", "언제부터 이랬어", "이 방어 코드는 왜 있어".
- 둘 다일 수 있다. 어떻게를 먼저 하고 왜로 간다.

쓰지 않을 때:

- 고칠 결함이 이미 정해졌다: 버그 수정(`bug-fix`). 원인을 찾는 진단은 그 레시피가 `diagnosing-bugs`로 한다.
- 바깥의 1차 자료(라이브러리 공식 문서, API 명세)를 모아 문서로 남기는 일: 사용자가 mattpocock-skills를 쓰면 `/mattpocock-skills:research`를 안내한다. 이 레시피는 이 저장소의 코드와 기록을 본다(두 스킬의 겹침은 `UPSTREAM.md`).
- 느린 것을 재고 고치는 일: 성능 개선 레시피(`perf`)로 맡긴다.
- 조사하다가 고쳐야 할 것이 정해지면 고치지 않는다. 결론에 적고, 고칠 일은 갈래를 다시 고른다(맡기기 또는 지휘).

## 입력

- 질문(사용자의 말 그대로)과 종류(어떻게 / 왜 / 둘 다).
- 대상: 파일, 기능, 심볼, 값. 대상이 모호하면 대화의 맥락(방금 본 파일, 앞선 요청)으로 가장 그럴듯한 대상을 정하고, 그 해석을 답의 첫머리에 적는다. 사용자가 바로잡을 수 있게 하려는 것이다. 묻고 기다리지 않는다.
- 조사가 변경의 전 단계인지(그러면 끝에 지킬 것과 바꿀 것을 적는다).

## 실행 조건

- 읽기 전용이다. 파일을 만들거나 고치지 않는다. 증명용 스크립트가 필요하면 OS 임시 폴더에 둔다.
- 서브에이전트는 [subagents.md](../subagents.md)를 따른다(조사 에이전트 `vstack:explorer`, 한 번에 셋까지). 조사 에이전트는 셸이 없으므로 git과 `gh` 조회는 관리자가 직접 한다.

## 단계

1. **크기를 본다.** 모듈 하나, 작은 함수, 좁은 질문이면 "단순"이다. 여러 파일이나 서비스에 걸친 흐름, 여러 곳에 퍼진 기능, 구조 전체면 "복잡"이다. 애매하면 단순으로 한다.
2. **어떻게(읽기).**
   - 단순: 관리자가 직접 읽는다.
   - 복잡: 질문을 서로 다른 각도 2~4개(한 흐름의 앞과 뒤, 데이터와 제어, 쓰는 쪽과 읽는 쪽 등)로 나누고, 각도마다 조사 에이전트를 하나씩 띄운다. 요청문에는 질문, 그 각도, 볼 곳, 이미 배제한 것을 적는다. 받은 답은 단서다. 설명에 쓸 주장은 관리자가 그 파일과 줄을 직접 다시 읽어 확인하고, 각도끼리 어긋나면 코드로 가린다.
3. **왜(근거 찾기).** 왜를 묻는 질문일 때만 한다.
   1. **코드 기준점**을 먼저 만든다: 대상 파일과 줄 범위, 핵심 심볼, `git blame -L <시작>,<끝> <파일>`로 마지막으로 손댄 커밋, `git log --follow -- <파일>`로 그 파일의 이력, 병합 커밋 제목의 PR 번호(`(#123)`)와 그 PR(`gh pr view`), 연결된 이슈(`gh issue view`).
   2. **근거 범주**를 차례로 본다. 소스 이력(커밋, PR 설명과 리뷰, 코드 주석, 테스트)과 이슈 저장소는 늘 본다. 그 밖의 범주(긴 문서, 팀 대화, 운영 관측, 오류 추적, 제품 분석)는 이 세션에 그 도구가 있을 때만 보고, 없으면 "도구가 없어 찾지 못함"으로 적는다. 방어 코드(null 검사, 재시도, 시간 제한, 속도 제한, 기능 플래그)가 대상이면 사건 기록(장애, 되돌린 커밋, 긴급 수정)을 따로 찾는다.
   3. 최근 커밋 하나를 답으로 삼지 않는다. 지금 모양은 여러 결정이 쌓인 결과인 경우가 많다. 처음 그 모양이 생긴 커밋까지 거슬러 간다.
4. **신뢰 단계를 붙인다.** 이유와 의도에 대한 주장(왜 이렇게 했나, 무엇을 노렸나)마다 하나를 고른다. 지금의 동작이나 위치처럼 코드를 직접 읽거나 돌려 본 사실에는 단계를 붙이지 않고 v-mode 고정 규칙 2의 표시만 쓴다.

   | 단계 | 뜻 | 쓰는 말 | 고정 규칙 2 |
   | --- | --- | --- | --- |
   | 직접 | 누군가 이유를 글로 적었다(PR 설명, 이슈, 코드 주석, 문서, 대화). 인용한다 | "X 때문이다" | (측정) |
   | 뒷받침 | 직접 말한 곳은 없지만 여러 근거가 한 결론으로 모인다. 근거를 하나씩 든다 | "근거가 X를 강하게 가리킨다: …" | (측정)한 근거 + (추론)한 결론 |
   | 추론 | 맥락에서 읽어 낸 해석이다. 추론의 고리를 적는다 | "A와 B로 보아 C일 가능성이 높다. D 때문이다" | (추론) |
   | 추측 | 근거가 얇고 다른 설명도 똑같이 맞는다 | "X일 수도 있지만 직접 근거는 없다" | (추측) |
   | 모름 | 찾았지만 찾지 못했다. 어디를 무엇으로 찾았는지 적는다 | "A, B, C를 찾았고 이유는 나오지 않았다" | (측정)한 탐색 |

   - 코드를 그 코드의 의도에 대한 근거로 쓰지 않는다("이렇게 동작하니 이걸 원했을 것"은 추론이다). 지저분한 이력에 깔끔한 이유를 덧씌우지 않고, 근거가 없다는 것을 "그런 이유는 없었다"의 근거로 쓰지 않는다.
   - 사용자의 질문에 든 가설은 결론이 아니라 후보로 보고 따로 확인한다.
   - 기록끼리 다른 이유를 말하면(예: 이슈는 고객 요구라 하고 PR은 정리라 함) 둘 다 인용해 나란히 적는다. 이야기가 깔끔해지는 쪽을 고르거나 코드로 어느 쪽인지 가리지 않는다. 둘 다 맞을 수도 있다. 판단은 사용자에게 맡긴다.
   - 답하기 전에 이유에 대한 주장마다 출처가 있는지 본다. 없으면 단계를 내린다(추론이나 추측으로). "모르는 것"이 비었으면 근거가 정말 다 있었는지 다시 본다.
5. **답한다.** 아래 "답의 형식". 질문의 전제가 근거와 다르면 그것을 먼저 말한다. "확실해?"라는 질문에는 근거와 함께 자기 판단을 말한다.
6. **변경으로 이어지면** 고치지 않는다. 조사가 변경의 전 단계였으면 답 끝에 "지킬 것 / 바꿀 것 / 피할 것 / 위험"을 적고, 고칠 일은 v-mode 고르기로 다시 보낸다.

## 답의 형식

맞지 않는 절은 뺀다.

- **어떻게**: 개요(이것이 무엇이고 왜 있는지, 한두 단락) → 핵심 개념(뒤를 따라가는 데 필요한 타입, 모듈, 추상화) → 동작(무엇이 시작하고, 차례로 무엇이 일어나고, 데이터가 어디로 가고, 어디서 갈리는지. 가장 긴 절. 파일과 함수를 가리킨다. 여러 부분이 주고받으면 그림 하나) → 위치(일을 시작할 사람에게 필요한 파일과 폴더만) → 함정(겉보기와 다른 동작, 지난 사정).
- **왜**: 질문(한두 문장) → 대상 코드(파일, 줄, 심볼) → 찾은 것(직접, 뒷받침. 서로 다른 기록은 나란히) → 읽어 낸 것(추론) → 경쟁 가설(추측, 둘 이상이면 나란히) → 모르는 것 → 찾아본 곳(근거 범주마다 한 줄. 찾지 못한 범주와 도구가 없던 범주도 적는다) → 신뢰 요약.
- **둘 중 고르는 질문**("A와 B 중 어디에 둘까"): 추천과 대안 표(대안마다 얻는 것, 드는 것).
