# 기능

id: feature · version: 2 · contract: vstack-contract@3

흐름은 pstack `playbooks/feature.md`(데이터 모양을 먼저 정하고 → 작은 단위로 만들고 검증하며 커밋 → 맞는 화면에서 확인)를 따른다. 원본의 하위 에이전트 위임, `how`·`architect`·`arena`·`interrogate` 호출, 작업 흐름 점검표, PR 단계는 vstack에서 관리자가 맡거나(지휘·검토) 첫 버전에서 뺐다. 설계 결정은 정렬 단계(사용자와 관리자)에서 하고 티켓에 싣는다.

## 언제

새 동작을 더하거나 기존 동작을 바꾸는 일. 바뀐 동작이 수용 기준으로 적혀 있고, 동작을 테스트할 seam(공개 인터페이스)이 정해져 있다.

쓰지 않을 때:

- 기존 동작이 기대와 다르게 깨진 것: 버그 수정 레시피(`bug-fix`). 관리자가 고른다.
- 동작은 그대로 두고 구조만 바꾸는 일: 리팩토링 레시피(`refactoring`). 관리자가 고른다.
- 새 도메인 개념, 여러 모듈이 쓰는 공용 인터페이스, 여러 설계안 중 하나를 고르는 일이 티켓에 정해져 있지 않은 것: 레시피를 시작하지 않는다. 관리자가 정렬 단계로 돌려 사용자와 정한다.

## 입력

관리자의 배정 전 입력 검사([intake.md](../contracts/intake.md))가 이 목록을 본다.

- **작업 종류**(아래 "작업 종류" 표의 하나)와 대상 `H`·`B`(새 구현이면 기준 커밋).
- **역할**(`구현자` 또는 `검토자`)과, 검토자면 `scope`(`review` 또는 `rerun-only`).
- **맡은 수용 기준**: 이 시도가 실행할 `AC-<n>@<버전>` 목록. 새 구현의 수용 기준에는 다음 둘이 필수로 들어 있다.
  - **동작**: 바뀐 동작이 사용자 경로(CLI 출력, 화면, API 응답 등)에서 관찰된다. 동작이 여럿이면 동작마다 하나씩 둔다.
  - **테스트**: seam에서 그 동작을 보는 테스트가 통과한다.
- seam: 동작을 테스트할 공개 인터페이스.
- 데이터 모양: 이 기능이 다루는 데이터와 상태를 어떤 구조로 둘지. 티켓에 정해져 있으면 그것을 쓴다. 정해져 있지 않으면 아래 "새 구현" 2를 본다.
- 범위 밖: 이번에 만들지 않을 것(이어지는 티켓의 기능 등).
- 검증 명령: 수용 기준마다. 앱을 띄워야 하면 verify 스킬 경로 또는 준비·정리 절차.
- 지적 수정이면: 고칠 지적 목록과 검토 보고서 경로.

## 실행 조건

- 무인 실행을 가정한다(TTY 없음). 사람의 입력을 기다리는 명령을 돌리지 않는다.
- 실창이 필요한 수용 기준은 명세의 잠금 명령으로만 띄운다.

## 작업 종류

명세의 작업 종류를 보고 해당 절차로 들어간다. 어느 쪽이든 먼저 [worker-contract.md](../contracts/worker-contract.md)와 [evidence.md](../contracts/evidence.md), 명세가 준 후보 원칙을 읽는다.

| 작업 종류 | 역할 | 커밋을 만드나 | 절차 | 실행할 수용 기준 |
| --- | --- | --- | --- | --- |
| 새 구현 | 구현자 | 예 | "새 구현" 1~9 | 맡은 수용 기준 전부 |
| 지적 수정 | 구현자 | 예 | "지적 수정" | 필수 수용 기준 전부(대상이 바뀐다) |
| rebase | 구현자 | 예(rebase) | "rebase" | 필수 수용 기준 전부(대상이 바뀐다) |
| 재검증 | 구현자(impl 인계 포함) | **아니오** | "재검증" | 맡은 수용 기준만 |
| 검토 | 검토자 `review` | 아니오 | "검토자 review" | 필수 수용 기준 전부 |
| 재실행 | 검토자 `rerun-only` | 아니오 | "검토자 rerun-only" | 맡은 수용 기준만 |

지휘 절차(명세 양식, 결과 대상 확인, 복구)의 공통 이름 `새 수정`은 이 레시피의 `새 구현`이다.

## 구현자: 새 구현

1. **대상을 읽는다.** 명세가 가리킨 영역의 코드와 테스트를 읽고, 이 기능이 바꿀 공개 인터페이스(seam)와 그 호출자를 적는다. 명세의 seam이 이 동작을 볼 수 없으면 다른 seam을 고르지 않는다. 그 사실과 이유를 적어 `막힘`으로 관리자에게 보고하고 기다린다.
2. **데이터 모양을 정한다.** 티켓에 정해져 있으면 그것을 쓴다. 정해져 있지 않으면 이 기능의 데이터와 상태를 하나의 구조로 이름 붙인다(후보 원칙 `model-the-domain`). 흩어진 불리언보다 상태 하나, 이어지는 분기보다 표, 여러 파일에 반복되는 모양 가정보다 타입 하나를 고른다. 그 결정이 새 도메인 개념이나 여러 모듈이 쓰는 공용 인터페이스를 만들면 설계 결정이다. 정하지 말고 그 사실과 후보를 적어 `막힘`으로 관리자에게 묻는다. 고른 모양과 이유는 완료 보고에 적는다.
3. **동작 하나씩 수직으로 만든다.** [tdd](../../tdd/SKILL.md)의 순서를 따른다. 수용 기준의 동작 하나를 seam에서 보는 테스트를 쓰고 실패를 본다(red) → 그 테스트를 통과시키는 가장 작은 구현(green) → 커밋. 다음 동작으로 넘어간다. 테스트를 먼저 다 쓰고 구현을 몰아 하지 않는다([tdd](../../tdd/SKILL.md) "Anti-patterns"의 수평 조각).
4. **green일 때만 정리한다.** 중복을 걷어 내는 정리는 테스트가 모두 통과할 때만 한다. 지금 쓰지 않는 추상화, 계층, 설정값을 미리 더하지 않는다(후보 원칙 `laziness-protocol`). 경계에서만 입력을 검증하고 안쪽에서는 타입을 믿는다(후보 원칙 `boundary-discipline`).
5. **맞는 화면에서 확인한다.** 동작 수용 기준의 검증 명령을 사용자 경로로 돌려 바뀐 동작을 본다. 결과가 모호하거나 다른 화면에서 본 것이면 통과가 아니다. 그렇게 적는다.
6. **범위를 지킨다.** "범위 밖"에 든 것과, 이 동작에 필요 없는 정리는 하지 않는다. 하다가 버그나 다른 빠진 기능을 찾으면 고치지 말고 완료 보고에 적는다.
7. **정리한다.** 임시 코드와 로그를 지운다. 커밋 메시지 본문에 무엇을 왜 바꿨는지와 고른 데이터 모양을 한두 줄로 적는다.
8. **증거를 만든다.** 마지막 커밋(`H`)에서 `git status`가 깨끗한 상태로, 실행할 수용 기준을 실행한다. 서버·빌드는 이 시도에서 `H`로 새로 띄운다. 새 구현일 때만, 3의 red→green 출력을 과정 증거로 그 폴더의 `process/` 아래에 둔다.
9. **완료 보고**를 보낸다(아래).

## 구현자: 지적 수정

1. 명세의 검토 보고서에서 고칠 지적을 읽는다. 고치지 않을 지적은 건드리지 않는다.
2. 지적이 빠진 동작이나 틀린 동작을 가리키면 "새 구현" 3으로 그 동작의 테스트부터 만든다. 지적이 데이터 모양을 바꾸라고 하면 "새 구현" 2를 다시 하고, 설계 결정이면 `막힘`으로 묻는다. 그 밖의 지적은 그대로 고친다.
3. 고친 것을 커밋한다. 이제 대상이 바뀌었다.
4. "새 구현" 7·8·9. 수용 기준은 필수 전부.

## 구현자: rebase

1. 명세의 기준 브랜치 tip 위로 rebase한다. 충돌이 나면 양쪽 의도를 모두 지키는 쪽으로 푼다. 같은 동작이 양쪽에서 바뀌어 의도를 고를 수 없으면 rebase를 되돌리고 관리자에게 보고한다.
2. 충돌을 풀면서 테스트의 assertion을 약하게 바꾸지 않는다. 바꿔야 한다면 그 이유를 완료 보고에 적는다(검토자가 본다).
3. "새 구현" 8·9. 수용 기준은 필수 전부.

## 구현자: 재검증

impl 인계(변경 작성자 세션이 사라짐)나, 같은 대상에서 증거를 다시 만드는 일(예: dirty tree로 만든 증거를 깨끗한 상태로 다시)이다.

1. 지금 `HEAD`가 명세의 `H`이고 기준 브랜치가 명세의 `B`인지 확인한다. 다르면 아무것도 하지 않고 `막힘`으로 보고한다.
2. 커밋을 만들지 않는다. 코드를 고칠 일이 보이면 고치지 말고 완료 보고에 적는다.
3. "새 구현" 8을 맡은 수용 기준에 대해서만 한다.
4. 완료 보고를 보낸다. 데이터 모양·만든 동작 항목은 쓰지 않는다.

## 검토자: review

1. 새 상태에서 앱을 준비한다(verify 스킬 또는 명세의 준비 절차). 구현자가 띄운 서버를 쓰지 않는다.
2. 필수 수용 기준 전부를 실행하고 증거를 만든다.
3. 코드를 검토한다. 대상은 명세가 준 범위(새 구현이면 브랜치 전체, 지적 수정이면 지적 해결 + 수정 diff + 브랜치 전체, rebase면 rebase diff + 브랜치 전체).
   - 수용 기준의 동작이 모두 있고, 범위 밖의 것을 만들지 않았는가.
   - 데이터 모양이 티켓(또는 완료 보고의 이유)과 맞는가. 같은 상태를 흩어진 불리언이나 반복되는 분기로 들고 있지 않은가. 티켓에 없던 설계 결정을 구현자가 혼자 내렸는가.
   - 지금 쓰지 않는 추상화·계층·설정이 늘었는가. 안쪽 코드에 경계 검증이 반복되는가.
   - 테스트가 seam의 공개 동작을 보는가, 내부 구현에 묶였는가([tdd](../../tdd/SKILL.md) "Anti-patterns"). 동작마다 테스트가 있는가. 테스트가 실패하는 경우가 실제로 있는가(명세가 준 scratch에서 구현을 되돌린 사본으로 확인할 수 있으면 한다. 제품 파일은 고치지 않는다).
   - 후보 원칙에 비춰 걸리는 곳(`중요`/`사소`).
   - 지적 수정이면 지적마다 해결됐는지.
4. 결론(`통과`/`수정 필요`)과 지적을 보고한다.

## 검토자: rerun-only

1. 새 상태에서 앱을 준비한다.
2. **맡은 수용 기준만** 실행하고 증거를 만든다.
3. 수용 기준별 판정만 보고한다. 코드 검토와 결론은 하지 않는다.

## 레시피 예외

[priority.md](../contracts/priority.md) "알려진 충돌과 답" 가운데 이 레시피에 해당하는 것.

- seam: 티켓의 seam을 쓴다. 맞지 않으면 관리자에게 묻고 기다린다.
- 설계 결정(새 도메인 개념, 공용 인터페이스, 설계안 고르기)은 작업자가 내리지 않는다. 관리자에게 묻는다.
- 사용자에게 물으라는 원문 지시는 관리자에게 묻는 것으로 읽는다.
- PR을 만들지 않는다. 커밋 여부는 "작업 종류" 표를 따르고, 어느 종류든 완료 보고로 끝난다.
