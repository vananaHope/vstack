# 교차 검토 명세 양식

`<...>`를 채워 검토자에게 보낸다. `{설정: ○○}`는 프로젝트 설정의 해당 절 내용을, `{실행 환경: 완료 보고}`는 실행 환경 문서 "작업자가 보고하는 방법"의 검토자용 문장을 그대로 옮긴다. 보고서 경로는 `.local/vstack/<작업 이름>/`의 절대 경로로 쓴다(검토자는 worktree에서 실행된다). "vstack 계약" 절은 [vstack.md](vstack.md) "배정 전"·"교차 검토 배정"대로 채운다.

이 양식은 `scope: review` 검토다. 수용 기준 재실행만 맡길 때(`rerun-only`)는 아래 "재실행 전용"을 쓴다.

```markdown
# 작업: 이슈 <이슈 표시> 구현의 교차 검토 (검토 전용, 제품 파일 수정 금지)

당신은 교차 검토자입니다. 다른 에이전트(<구현 에이전트>)가 이 worktree에서 이슈 <이슈 표시>를 구현했습니다. 구현 과정의 맥락 없이 결과물만 보고 독립적으로 판단하세요.

## vstack 계약

- 역할: 검토자 · scope: review · 시도 ID: <rev-<세션 키>-<n>>
- 대상: `H`=<SHA>, `B`=<SHA>. 시작할 때 `git rev-parse HEAD`가 `H`인지 확인하고, 다르면 아무것도 하지 않고 `막힘`으로 보고한다.
- 먼저 읽을 계약: `<vstack>/skills/v-mode/contracts/worker-contract.md`, `<vstack>/skills/v-mode/contracts/evidence.md`, `<vstack>/skills/v-mode/contracts/priority.md`, `<vstack>/skills/v-mode/contracts/reference-policy.md`
- 레시피: `<vstack>/skills/v-mode/recipes/<id>.md`(<id>@<버전>)의 "검토자: review" 절차를 따른다.
- 후보 원칙(이것만 읽는다): <`<vstack>/skills/principle-<이름>/SKILL.md` 목록>
- 맡은 수용 기준(필수 전부):

  | ID | 필수 | 내용 | 검증 명령 |
  | --- | --- | --- | --- |
  | <AC-1@1> | <예> | <관찰 가능한 결과> | <명령> |

- seam: <테스트가 있어야 할 공개 인터페이스>
- 레시피별 입력(구현 명세와 같은 값. 다른 레시피의 줄은 지운다):
  - `bug-fix`: 재현 경로 <…> · 간헐 반복 <…>
  - `feature`: 데이터 모양 <티켓의 결정 또는 "구현자 완료 보고에 있음"> · 범위 밖 <…>
  - `refactoring`: [vstack.md](vstack.md) "리팩토링 기준" 줄의 값: 원래 동작 기준 `S` <SHA> · 고정 확정 커밋 `P` <SHA> · 후속 고정 테스트 <목록과 근거 보관 경로, 또는 "없음"> · 고정 명령(pin) <명령> · 목표 구조 <…> · 전환 방식 <…> · 사본 입력 <구현 명세와 같은 값>. 이번 시도의 구현자 보고에 새 후속 고정 테스트가 있으면 그것도 확인한다. 구현 명세가 레시피의 비교·고정 의무를 줄였으면 그 문장을 여기에 옮긴다
- 실행 조건: <레시피의 실행 조건> · 실창: <잠금 명령(desktop.md) 또는 "해당 없음">
- 검토 범위: <첫 구현(새 수정·새 구현·새 리팩토링)이면 "브랜치 전체(`git diff <B>...<H>`)". 지적 수정이면 "고칠 지적 <목록>의 해결 + 수정 diff(`git diff <이전 H>..<H>`) + 브랜치 전체". rebase면 "rebase diff(`git range-diff <rebase 전 H>...<H>`) + 브랜치 전체">
- 깨뜨릴 범위 점검: <[vstack.md](vstack.md) "교차 검토 배정"의 조건에 들면 "`<vstack>/skills/blast-radius/SKILL.md`를 읽고 검토 항목 9에서 따른다". 아니면 "해당 없음">
- 준비·정리: <verify 스킬 절대 경로 또는 명세의 절차>. 구현자가 띄운 서버·포트·DB를 재사용하지 않고 새 상태에서 시작한다.
- git 무시: 관리자가 이 worktree git의 `info/exclude`에 `.vstack/`(Codex fast를 쓰면 `/.codex/`도)를 넣었다. 증거 폴더와 scratch에 써도 `git status`는 비어 있어야 한다. 무시 규칙을 정하는 파일(`.gitignore`, `info/exclude`)은 만들거나 고치지 않는다. 실행 환경 입력(예: `.env.local`)을 만들거나 고쳐도 되는지는 명세의 실행 조건이 정한다.
- 증거 폴더: `<worktree>/.vstack/evidence/<작업 이름>/<시도 ID>/`
- scratch: `<worktree>/.vstack/scratch/<시도 ID>/`(빌드 산출물, 임시 데이터, 테스트 사본)
- manifest 값: `task` = `<작업 이름>`, `attempt` = `<시도 ID>`, `role` = `rev`, `scope` = `review`, `executor` = `<opencode/codex/claude>`, `session` = `<세션 키>`, `recipe` = `<id>@<버전>`. 과정 증거는 `process/` 아래에 두고 `files`에만 올린다. 보고서에서 증거를 가리킬 때는 시도 ID와 증거 폴더 기준 상대 경로로 쓴다.
- 구현자의 완료 보고와 증거: `<보관된 구현자 시도 폴더의 절대 경로>`(`.local/vstack/<작업 이름>/evidence/<impl 시도 ID>/`. 관리자가 보관한 뒤의 위치다)
- 권한: 증거 폴더, 보고서 경로, scratch에만 쓴다. 제품 소스·테스트 수정, 커밋, 다른 시도의 증거 폴더, ignore 파일 수정은 하지 않는다.

## 먼저 읽을 것

- 이슈 내용과 앞선 이슈에서 넘어온 지적: <GitHub면 `gh issue view <n> --json title,body,comments`. 다른 저장소면 구현 명세의 "이슈 본문"을 그대로 옮긴다.>
- 완료 기준(판정 기준): <구현 명세의 "완료 기준"과 같은 위치나 같은 목록>
- {설정: 스펙과 먼저 읽을 문서}
- 변경 내용: `git log --oneline main..HEAD`, `git diff main...HEAD`

## 검토 항목

1. **완료 기준**: 항목마다 충족 / 미충족 / 자동 확인 불가(사람이 봐야 함)를 판정하고 근거(파일·테스트 이름)를 단다. <해당하면: {설정: 추가 완료 조건}도 같은 방식으로 판정한다.>
2. **수용 기준과 테스트 실제 실행**: 위 "맡은 수용 기준"을 모두 새 상태에서 돌려 증거 폴더에 증거를 만든다(evidence.md). 구현자의 증거나 설명을 그대로 받아들이지 않는다. 그 밖에는 변경과 관련된 테스트만 한 번 돌려 결과를 기록한다. {설정: 테스트} 전체 테스트는 돌리지 않는다(관리자가 Release 직전 `main`에서 돌린다).
3. **자주 나온 지적**: `<common-findings.md 절대 경로>`의 유형을 먼저 확인한다. 구현자의 완료 보고(위 "vstack 계약"의 보관 위치)에 있는 자기 점검 결과가 맞는지도 확인한다.
4. **구현 제약**: {설정: 구현 제약}을 지키는가. ADR이나 프로젝트 문서와 어긋나는 곳이 있는가.
5. **테스트 품질**: 공개 동작을 검증하는가, 내부 구현에 묶였는가. 중요한 동작인데 테스트가 없는 것은.
6. **용어**: 도메인 이름이 프로젝트 용어집(있으면)과 맞는가. 용어집에 없는 개념이 생겼거나 피하라고 한 단어를 쓰는가.
7. **범위**: 다른 이슈의 기능을 미리 만들었는가(과잉). 그것들이 들어올 자리를 막는가.
8. **위생**: 큰 바이너리, 가상 환경·의존성 폴더, 검증 기록 파일이 커밋되지 않았는가. 커밋 메시지가 프로젝트 작성 규칙의 언어인가. 비밀 정보나 하드코딩된 절대 경로가 없는가.
9. **버그**: 위와 별개로 실제 동작을 깨뜨리는 결함. 실제 외부 도구나 자료로 재현해 볼 수 있으면 재현한다. {설정: 확인 자료} <"깨뜨릴 범위 점검"이 스킬을 가리키면: 그 스킬의 방법으로 이 변경이 diff 밖에서 깨뜨릴 수 있는 것을 본다. 변경이 안전한 근거가 되는 사실을 찾아 scratch에서 실제 코드를 돌려 증명하고, 명령과 출력을 증거 폴더 `process/`에 둔다. 증명하지 못한 사실은 지적이나 "사람이 직접 확인해야 할 항목"에 적는다.>

## 제약

검토 전용. 제품 소스·테스트를 수정하거나 커밋하지 않는다. 쓰기는 위 "vstack 계약"의 권한(증거 폴더, 보고서, scratch)대로만 한다. 임시 스크립트와 테스트 사본은 scratch에서 돌린다. 추측성 지적은 하지 않고, 지적마다 재현 방법이나 근거(파일과 줄, 실행 결과)를 붙인다. 실창이 필요한 수용 기준은 명세의 잠금 명령으로만 띄우고, 띄울 수 없으면 그 수용 기준을 `막힘`으로 보고한다(`통과`로 적지 않는다).

멈춘 명령의 프로세스를 강제 종료할 때는 이 작업에서 시작한 것인지 확인하고 그 PID를 지정한다. 이름으로 한꺼번에 종료하지 않는다(`taskkill /IM python.exe` 등). 자식 프로세스도 같은 범위만 종료한다. 대상을 확인할 수 없으면 종료하지 말고 관리자에게 묻는다.

맡은 수용 기준의 검증 명령은 한 번에 하나씩 끝낸 뒤 다음 명령을 돌린다. 그동안 다른 시험·빌드·화면 검사·실험 스크립트를 따로 실행하지 않는다. 명세가 정한 명령 내부의 병렬 실행과 동시성 검증 절차는 그대로 따른다. 시간 초과나 실패는 원인 추정과 구분해 기록하고, 임의로 재시도하지 말고 관리자에게 보고한다.

## 결과

상세 결과를 `<보고서 절대 경로>`에 쓴다. {실행 환경: 완료 보고}

- 결론: 통과 / 수정 필요
- 시도 ID와 증거 폴더
- 수용 기준 판정표 (ID / 판정 `통과`·`실패`·`막힘` / 근거)
- 완료 기준 판정표 (항목 / 판정 / 근거)
- 테스트 실행 결과
- 지적 목록: 심각도(차단 / 중요 / 사소) · 내용 · 근거 · 제안
- 사람이 직접 확인해야 할 항목
```

## 재검토

수정으로 대상이 바뀌었으므로 재검토는 새 대상에 대한 `scope: review` 시도다([vstack.md](vstack.md) "대상이 바뀌면"). 차단·중요 지적을 고쳤을 때도, 사소한 지적만 고쳐 관리자가 확인했을 때도 한다.

재검토는 남겨 둔 같은 검토자에게(역할 자격이 맞으면) 위 양식으로 맡긴다. 바꿀 곳:
- 시도 ID의 `n`을 올리고, 대상 `H`를 새 커밋으로.
- 검토 범위: "지금 고침"으로 정한 지적의 해결 판정 + `git diff <이전 H>..<H>` + 브랜치 전체. 넘긴 지적은 판정하지 않는다.
- 맡은 수용 기준: 필수 전부(대상이 바뀌었으므로 이전 증거를 쓰지 않는다).

보고서는 `rereview-<k>.md`로 따로 쓴다.

## 재실행 전용(rerun-only)

대상이 그대로인 채 일부 수용 기준만 다시 돌릴 때(환경 원인 막힘 뒤 등) 쓴다. 대상이 바뀐 뒤의 첫 rev 시도에는 쓰지 않는다.

위 양식에서:
- 제목: `# 작업: 이슈 <이슈 표시>의 수용 기준 재실행 (제품 파일 수정 금지)`
- scope: `rerun-only`(manifest 값의 `scope`도). 레시피의 "검토자: rerun-only" 절차를 따른다.
- 맡은 수용 기준: 다시 돌릴 것만.
- 깨뜨릴 범위 점검: "해당 없음"으로 쓴다(이 점검은 `review`에서만 한다).
- "검토 항목"을 빼고, 결과는 시도 ID·증거 폴더·수용 기준 판정표만 쓴다. 결론과 지적은 쓰지 않는다.
