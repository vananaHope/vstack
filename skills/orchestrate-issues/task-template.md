# 구현 작업 명세 양식

`<...>`를 채워 구현 작업자에게 보낸다. `{설정: ○○}`는 프로젝트 설정의 해당 절 내용을, `{실행 환경: ○○}`는 실행 환경 문서 "작업자가 보고하는 방법"의 해당 문장을 그대로 옮긴다. 이슈별로 바뀌는 곳은 Change, 범위 밖 목록, "vstack 계약" 절이다. "vstack 계약" 절은 [vstack.md](vstack.md) "배정 전"대로 채운다. 경로는 모두 절대 경로로 쓴다.

작업 종류 이름은 [vstack.md](vstack.md) "작업 종류 이름"을 따른다(레시피의 첫 구현 종류: `bug-fix`는 `새 수정`, `feature`는 `새 구현`, `refactoring`은 `새 리팩토링`). 첫 구현이 아닌 일(지적 수정, rebase, 재검증)도 이 양식을 쓴다. 그때는 "작업 종류"와 Change를 그 일에 맞게 바꾼다. **재검증**이면 "권한" 줄을 "제품 소스·테스트를 고치지 않고 커밋하지 않는다. 증거 폴더와 scratch에만 쓴다"로 바꾸고, Constraints의 커밋 문장을 지운다. 적용되지 않는 칸은 지우지 말고 "해당 없음"으로 적는다.

```markdown
# 작업: 이슈 <이슈 표시> "<이슈 제목>" <작업 종류>

당신은 이 작업의 구현 담당입니다. 끝나면 관리자(Claude)가 별도 에이전트로 교차 검토합니다.

## vstack 계약

- 역할: 구현자 · 작업 종류: <레시피의 첫 구현(새 수정 / 새 구현 / 새 리팩토링) / 지적 수정 / rebase / 재검증> · 시도 ID: <impl-<세션 키>-<n>>
- 대상: <첫 구현이면 "기준 브랜치 `main`의 `<B>` 위에서 시작". 그 밖이면 "`H`=<SHA>, `B`=<SHA>">
- 먼저 읽을 계약: `<vstack>/skills/v-mode/contracts/worker-contract.md`, `<vstack>/skills/v-mode/contracts/evidence.md`, `<vstack>/skills/v-mode/contracts/priority.md`, `<vstack>/skills/v-mode/contracts/reference-policy.md`
- 레시피: `<vstack>/skills/v-mode/recipes/<id>.md`(<id>@<버전>). 이 레시피의 "작업 종류" 표에서 위 작업 종류의 절차를 따른다.
- 후보 원칙(이것만 읽는다): <`<vstack>/skills/principle-<이름>/SKILL.md` 목록>
- 맡은 수용 기준:

  | ID | 필수 | 내용 | 검증 명령 |
  | --- | --- | --- | --- |
  | <AC-1@1> | <예> | <관찰 가능한 결과> | <명령> |

- seam: <테스트를 둘 공개 인터페이스>
- 레시피별 입력(그 레시피의 "입력"을 따른다. 다른 레시피의 줄은 지운다):
  - `bug-fix`: 재현 경로 <사용자가 증상을 보는 순서> · 간헐 반복 <횟수 또는 "결정적 버그">
  - `feature`: 데이터 모양 <티켓이 정한 구조, 또는 "정해지지 않음: 구현자가 정해 보고한다. 새 도메인 개념·공용 인터페이스·설계안 고르기면 막힘으로 묻는다"> · 범위 밖 <이번에 만들지 않을 것>
  - `refactoring`: [vstack.md](vstack.md) "리팩토링 기준" 줄의 값: 원래 동작 기준 `S` <SHA> · 고정 확정 커밋 `P` <SHA 또는 "미정: 구조를 바꾸기 전에 정한다"> · 후속 고정 테스트 <목록과 근거 보관 경로, 또는 "없음"> · 고정 명령(pin) <명령> · 목표 구조 <끝난 뒤 모듈 배치·타입·호출 관계> · 전환 방식 <`한 번에 전환` 또는 `expand–contract`의 이 티켓 단계> · 영향 범위 <바꿀 이름·API와 호출자를 찾는 방법> · 사본 입력 <scratch 사본에 넣을 무시 파일과 출처(예: "이 worktree의 `.env.local`을 그대로 복사"), 또는 "없음">
- 실행 조건: <레시피의 실행 조건. 예: bash(Git Bash), TTY 없음> · 실창: <잠금 명령(desktop.md) 또는 "해당 없음">
- 건드리지 말 영역: <파일·영역 또는 "해당 없음">
- 이어받기: <첫 구현을 이어받는 경우 "worktree에 남은 커밋과 변경을 이어받는다. 레시피 첫 구현 절차의 1부터 지금 상태에서 다시 확인한다". 아니면 "해당 없음">
- 지적 수정이면: 고칠 지적 <목록>, 검토 보고서 <경로>
- 준비·정리: <verify 스킬 절대 경로 또는 명세의 절차>
- git 무시: 관리자가 이 worktree git의 `info/exclude`에 `.vstack/`(Codex fast를 쓰면 `/.codex/`도)를 넣었다. 증거 폴더와 scratch에 써도 `git status`는 비어 있어야 한다. 무시 규칙을 정하는 파일(`.gitignore`, `info/exclude`)은 만들거나 고치지 않는다. 실행 환경 입력(예: `.env.local`)을 만들거나 고쳐도 되는지는 명세의 실행 조건이 정한다.
- 증거 폴더: `<worktree>/.vstack/evidence/<작업 이름>/<시도 ID>/`(이 폴더에만 증거를 쓰고, 커밋하지 않는다) · scratch: `<worktree>/.vstack/scratch/<시도 ID>/`
- manifest 값: `task` = `<작업 이름>`, `attempt` = `<시도 ID>`, `role` = `impl`, `executor` = `<opencode/codex/claude>`, `session` = `<세션 키>`, `recipe` = `<id>@<버전>`. 과정 증거는 `process/` 아래에 두고 `files`에만 올린다. 완료 보고를 파일로도 남기면 증거 폴더의 `report.md`에 둔다. manifest와 `report.md`에서 증거 파일을 가리키는 경로는 증거 폴더 기준 상대 경로로 쓴다(`results[].cwd` 같은 실행 위치는 절대 경로 그대로).
- 권한: worktree 안의 제품 소스·테스트를 고치고 커밋할 수 있다. push, PR, 병합, worktree 밖 쓰기, 다른 시도의 증거 폴더, ignore 파일 수정은 하지 않는다.

## 먼저 읽을 것 (필수)

- 이슈 내용과 앞선 이슈에서 넘어온 지적(댓글): <GitHub면 `gh issue view <n> --json title,body,comments`. 다른 저장소면 "아래 '이슈 본문'".>
- 완료 기준: <이슈에 있으면 "이슈 본문의 <위치>". 없으면 관리자가 뽑은 체크리스트를 여기에 그대로 적는다.> 이것이 기준이다.
- {설정: 스펙과 먼저 읽을 문서}

<GitHub가 아니면 이 절을 넣는다:
## 이슈 본문

(이슈 파일·문서의 본문과 댓글을 그대로 옮긴다.)
>

## Target

현재 worktree(`main`에서 분기한 이 작업 전용 브랜치). <이 이슈가 주로 건드릴 영역>

## Change

이 이슈의 완료 기준을 모두 만족시킨다. <기준을 짧게 요약하고, 이슈 댓글로 넘어온 지적이 있으면 함께 처리하라고 적는다.>
<해당하면: {설정: 추가 완료 조건}>

## Constraints

- {설정: 구현 제약}
- 범위 밖(다른 이슈가 맡음, 만들지 않는다): <이슈 번호와 기능 목록>. 그것들이 들어올 자리를 막는 구조로도 만들지 않는다.
- 커밋 메시지는 <프로젝트 작성 규칙의 언어>. 의미 단위로 여러 번 커밋해도 된다. push, PR 생성, `main` 병합은 하지 않는다.
- 이 worktree 밖의 파일은 건드리지 않는다. 시스템 수준 설치나 업그레이드가 필요하면 하지 말고 관리자에게 요청한다(질문). 증거는 저장소에 커밋하지 말고 위 "증거 폴더"에 둔다.
<실창 검사 절이 있으면: desktop.md의 세 가지(잠금 명령은 스킬 폴더 절대 경로로)와 {설정: 실창 검사}.>

## Ownership

이 worktree 안의 파일만 편집한다. <다른 작업자가 동시에 진행 중인 이슈가 있으면: "#<m>이 동시에 진행 중이며 <영역>을 건드린다. 공용 부분을 바꿀 때는 그 사실을 완료 보고에 적는다.">

## 테스트 실행

- 위 "맡은 수용 기준"의 검증 명령은 모두 돌려 증거를 만든다(레시피와 evidence.md대로).
- 그 밖에는 바꾼 모듈과 직접 관련된 테스트만 돌린다. {설정: 테스트}
- **전체 테스트는 돌리지 않는다.** 전체 테스트는 관리자가 Release 직전 `main`에서 한 번 돌린다.
- 동시 실행 반복, 결함 주입 반복, 전후 시간 비교 같은 추가 측정은 명세가 요구할 때만 한다.
- 부하 때문에 시간 초과가 나면 다시 돌리지 말고 보고에 적는다.

## 제출 전 자기 점검

`<common-findings.md 절대 경로>`(자주 나온 검토 지적)를 읽는다. 이번 변경에 해당하는 유형마다 그 "점검"을 실제로 해 본다. 완료 보고에 유형별로 "해당 없음 / 확인함(방법) / 남김(이유)"을 한 줄씩 적는다.

## Observable acceptance

- 위 "완료 기준"이 모두 충족된다.
- 맡은 수용 기준마다 증거 폴더에 `manifest.json`과 산출물이 있다(evidence.md "manifest.json"). 승인 증거는 마지막 커밋에서, `git status`가 깨끗한 상태로 만든다.
- 환경은 {설정: 환경 준비}로 준비한다.
- 바꾼 모듈과 관련된 테스트가 통과한다. 전체 테스트는 관리자가 Release 직전에 돌린다.
- 자기 점검 결과가 완료 보고에 있다.
- 끝나면 완료 보고를 한다. {실행 환경: 완료 보고} 보고에는 다음을 담는다: 결론(`완료` 또는 `막힘: <이유와 풀릴 조건>`), 시도 ID와 증거 폴더, 수용 기준별 판정, 커밋 해시, 테스트 결과(통과 수), 설치하거나 바꾼 시스템 구성 요소, 사람이 직접 확인해야 할 항목, 충족하지 못했거나 판단이 필요했던 항목, 그리고 레시피 "완료 보고" 표에서 이 작업 종류에 해당하는 항목.
- 막히거나 스펙이 모호하면 추측하지 말고 관리자에게 질문한다. {실행 환경: 질문} 질문한 뒤에는 답을 기다리고, 답 전에는 완료 보고를 보내지 않는다.
```
