# vstack 계약 연결

[SKILL.md](SKILL.md)의 단계마다 vstack 계약(`<vstack>/skills/v-mode/contracts/`)을 어떻게 적용하는지 모았다. SKILL.md는 해당 위치에서 이 문서의 절을 가리킨다. 계약과 이 문서가 다르면 계약이 이긴다.

`<vstack>`은 vstack 플러그인 루트다. 이 파일 기준으로 `../..`이다. 명세에 넣을 때는 절대 경로로 바꾼다.

## 첫 버전에서 하지 않는 것

- **레시피가 없는 작업**: vstack 지휘는 레시피가 있는 작업만 맡는다. 레시피는 `bug-fix`(버그 수정, [bug-fix.md](../v-mode/recipes/bug-fix.md)), `feature`(기능, [feature.md](../v-mode/recipes/feature.md)), `refactoring`(리팩토링, [refactoring.md](../v-mode/recipes/refactoring.md))이다. 맞는 레시피가 없는 이슈(성능, 프로토타입, 조사 등)는 맡기지 않고, 사용자에게 "레시피 없음: 기존 agent-orchestra로 하거나 레시피를 먼저 만든다"고 알린다.
- **앞부분 선행 병합**: SKILL.md 1단계 "앞부분 착수"는 하지 않는다. 앞부분은 이슈의 수용 기준을 다 채우지 못해 관문 G1에서 막히고, 범위를 줄여 통과시키면 이슈가 너무 일찍 닫힌다. 프런티어가 비면 그대로 기다린다.
- **UI 다듬기**: [ui-polish.md](ui-polish.md)는 관리자가 직접 구현하는 일이다. 첫 버전에서 관리자는 작업자 역할을 맡지 않고, 레시피도 없다. 화면 묶음이 모두 병합되면 "UI 다듬기는 vstack 첫 버전 밖: 기존 agent-orchestra로 하거나 나중에 레시피를 만든다"고 알린다.

## 작업 종류 이름

이 문서와 SKILL.md, 명세 양식에서 **`새 수정`은 레시피의 첫 구현 작업 종류**를 뜻한다: `bug-fix`는 `새 수정`, `feature`는 `새 구현`, `refactoring`은 `새 리팩토링`다. "레시피 1부터"는 그 첫 구현 절차의 1단계부터다(`bug-fix`는 재현, `feature`는 대상 읽기, `refactoring`은 고정 명령 돌리기). 명세에는 레시피의 이름(예: `새 구현`)을 그대로 적는다. `지적 수정`·`rebase`·`재검증`·`review`·`rerun-only`는 세 레시피에서 이름이 같다.

## 리팩토링 기준

`refactoring` 작업이면 관리자가 `state.md`의 입력 검사 줄 아래에 이 줄을 두고, 작업이 끝날 때까지 갱신한다. 작업자의 기억이나 이전 보고를 찾게 하지 않고, 모든 후속 구현·검토 명세에 이 값을 그대로 넣는다.

```
리팩토링 기준: S=<SHA> · P=<SHA 또는 "미정"> · 후속 고정 테스트=<파일·테스트 이름 목록 또는 "없음"> · 사본 입력=<scratch 사본에 넣을 무시 파일과 출처 또는 "없음"> · 근거=<각 값을 보고한 시도 ID와 보관 경로>
```

- `사본 입력`은 첫 배정 때 티켓과 프로젝트 설정 "환경 준비"로 정해 적는다(레시피 "입력"의 사본 입력). 바뀌면 이 줄을 먼저 고치고 명세에 옮긴다.
- `S`는 첫 배정 때 시작 커밋으로 적는다. 이어받기·지적 수정·재검증에서는 바꾸지 않는다. 새 시도의 시작 `HEAD`는 `S`가 아니다.
- `P`는 첫 구현의 완료 보고(보관 확인 뒤)로 적는다. 이미 적힌 `P`는 다시 정하지 않는다. 구현이 끝나지 않은 채 이어받은 시도에서 `P`가 아직 미정이면, 이어받은 작업자가 구조를 바꾸기 전에 정하게 한다. 구조 변경이 이미 들어 있으면(이전 시도가 `P` 없이 바꿨다) `P`를 정할 수 없으므로 `막힘`으로 사용자에게 알린다(그 변경을 되돌리고 다시 시작할지 정한다).
- 후속 고정 테스트는 지적 수정의 완료 보고에 나올 때마다 목록에 더한다(이미 검증된 것을 다시 미보고 추가로 다루지 않게).
- 명세에서 레시피의 비교·고정 의무를 줄이면(예: 명세 새 눈 점검에 답하며 "새 리팩토링" 7의 전·후 출력 비교를 pin 통과로 갈음) 그 문장과 이유를 `state.md`의 이 줄 아래에 적고, 뒤따르는 검토 명세에도 옮긴다. 검토자가 줄어든 확인을 따로 하게 하려는 것이다(다섯 번째 시범에서 이렇게 줄인 비교 밖의 결함이 첫 검토를 지나갔다).
- 앞 명세를 바꿔 써서 새 명세를 만들면, 다 쓴 뒤 명세의 `refactoring` 줄(`S`, `P`, 후속 고정 테스트, 사본 입력)을 이 줄과 한 칸씩 대조한다(다섯 번째 시범에서 옛 "없음"이 남았다).
- **rebase로 기준 브랜치가 바뀌면** 원래 동작 기준을 옮긴다. 새 `S`는 rebase 목표 기준 브랜치 tip이다. 새 `P`는 rebase가 만든 커밋이라 맡길 때는 아직 없다. 순서:
  1. rebase를 맡길 때 줄을 `S=<새 S> · P=rebase 뒤 작업자가 찾음(옛 P=<옛 P>) · 확인 대기(rebase <시도 ID>)`로 고친다. 명세에는 새 `S`, 옛 `S`·옛 `P`, 누적 후속 고정 테스트를 넣는다.
  2. rebase 작업자가 레시피 "rebase" 3대로 새 `P`를 찾아(`git range-diff <옛 S>..<옛 P> <새 S>..HEAD`로 옛 특성화 테스트 커밋에 대응하는 새 커밋. 특성화 테스트를 더하지 않았으면 새 `P` = 새 `S`), 새 `S..P`가 테스트 파일만 바꾸는지 보고, 새 `P`의 scratch 사본(제품 코드가 새 `S`와 같다)에서 pin 전부와 누적 후속 고정 테스트를 돌려 결과와 새 `P` SHA를 보고한다.
  3. 관리자는 "완료 보고를 받으면" 2(결과 대상 확정)에서 보고된 새 `P`를 직접 대조한다: 같은 range-diff 대응, `git diff --stat <새 S>..<새 P>`가 테스트 파일만.
  4. 결과를 나눠 본다. 테스트 파일이 없거나 환경 때문에 못 돌린 것은 동작 차이가 아니다. 그 확인만 다시 맡긴다(같은 대상의 재검증. 아래 예외). 실제 assertion이 실패했으면 기준 브랜치 변경이 고정하는 동작을 바꾼 것이다. 사용자에게 묻는다(원래 동작 기준과 수용 기준 버전을 다시 정한다).
  5. 모두 맞으면 `확인 대기`를 지우고 새 `S`·`P`를 확정한다. 근거에 rebase 시도 ID를 더한다.
  - 확인 대기인 동안에는 이 기준으로 다른 시도(검토, 지적 수정 등)를 맡기지 않는다. 예외는 4의 확인을 다시 맡기는 시도 하나뿐이다. 관리자가 다시 시작해도 확인부터 한다.

## 기록 두 가지

- **시도 표**(`state.md` "시도"): 계약의 판정 입력이다. 구현·검토·재검증·지적 수정·rebase의 모든 시도를 적는다([state-and-rollback.md](../v-mode/contracts/state-and-rollback.md)). 관리자만 고친다.
- **맡김 기록**(`.local/vstack/assign-log.md`): 등급과 배치가 맞았는지 보려는 기록이다([tiers.md](tiers.md) "맡김 기록"). 시도 표를 대신하지 않는다. 검토와 재검증도 한 줄씩 남기고 `레시피`·`검토자`·`증거 판정` 열을 채운다.

## 배정 전

작업자를 띄우는 모든 곳(새 수정, 검토, 지적 수정, rebase, 재검증) 앞에서 이 순서로 한다. worktree가 있어야 보관 준비를 할 수 있으므로 **worktree를 먼저 만든다**.

1. **입력 검사**: [intake.md](../v-mode/contracts/intake.md) 표를 채운다. 빠지면 맡기지 않는다. 첫 시범 티켓은 사람이 손으로 채운다.
2. **worktree 확보**: worktree를 만드는 것은 작업 종류와 따로 정한다. **이 작업의 첫 배정일 때만** 실행 환경 문서의 **worktree 만들기**로 먼저 만든다(Orca면 `orca worktree create --name <작업 이름>-<slug> --branch <작업 이름>-<slug> ...`). 결과의 경로와 브랜치를 `state.md`에 적는다. 그 밖의 모든 배정(검토, 지적 수정, rebase, 재검증, 멈춘 구현을 이어받는 새 수정)은 그 작업의 기존 worktree를 쓴다. 이어받기면 그 worktree에 남은 커밋과 변경(`git -C <worktree> log --oneline <B>..HEAD`, `git -C <worktree> status --porcelain`)을 명세의 "이어받기" 칸에 적는다. vstack 지휘에서는 `worker-start`가 worktree를 만들게 하지 않는다(`--worktree new-top-level` 대신 `--worktree path:<경로>`).
3. **시도 정하기**: 역할(`impl`/`rev`), 작업 종류(레시피의 "작업 종류" 표), `scope`(rev면), 맡은 수용 기준, **배정 대상**(새 수정이면 시작 커밋과 `B`, 그 밖에는 지금의 `H`·`B`). 새 세션이면 세션 키(8자 16진수)를 새로 만든다. 시도 표에 이미 있는 키와 겹치지 않게 한다. 같은 세션에 다시 맡기면 그 키를 쓰고 `n`을 올린다. 시도 ID는 `<역할>-<세션 키>-<n>`이다([evidence.md](../v-mode/contracts/evidence.md) "용어").
4. **역할 자격 확인**(rev): evidence.md "역할 자격". 그 대상에 커밋한 세션도, impl 세션도 아니어야 하고, 계열이 변경 작성자와 달라야 한다. 다를 수 없으면 [tiers.md](tiers.md) "검토자 고르기" 2의 같은 계열 조건을 모두 채운다.
5. **보관 준비**: [archive.md](../v-mode/contracts/archive.md) "준비" 1~3(ignore 설정, 시도 표에 `배정됨`).
6. **명세 채우기**: [task-template.md](task-template.md) 또는 [review-template.md](review-template.md)의 "vstack 계약" 절을 채운다. 증거 폴더는 `<worktree>/.vstack/evidence/<작업 이름>/<시도 ID>/`, scratch는 `<worktree>/.vstack/scratch/<시도 ID>/`.
7. **띄우기**: 바로 전에 archive.md "준비" 5(띄우기 직전 `HEAD`·status 기록)를 한다. 그다음 `--worktree path:<worktree 경로>`. 결과의 `dispatchId`, `terminal`(세션)을 시도 표에 적는다.

`state.md`는 state-and-rollback.md "state.md 형식"으로 쓴다(셋째 줄 `workflow: vstack · contract: vstack-contract@3 · recipe: <id>@<버전> · 소유: vstack`, 수용 기준·시도·관문 절).

## 완료 보고를 받으면

`worker_done`이 오면(성공·실패 모두):

1. **보관**: archive.md "보관 순서" 1~5. 보관되지 않은 시도의 기록은 판정에 쓰지 않는다(evidence.md 유효 조건 5). 시도 표 상태를 `보고됨` → `보관됨` → `정리됨`으로 고친다.
2. **결과 대상 확정**: manifest의 `target`을 확인해 시도 표의 그 시도 줄에 **결과 대상**(`H`, `B`)을 적는다. 배정 대상과 따로 둔다. 확인할 것:
   - `git -C <worktree> rev-parse HEAD`가 manifest의 `target.head`와 같다.
   - `git -C <worktree> status --porcelain=v1 --untracked-files=all`이 비었다.
   - 작업 종류에 따라:

     | 작업 종류 | 확인 |
     | --- | --- |
     | 새 수정, 지적 수정 | 배정 대상에서 결과 대상까지의 커밋이 이 시도의 것이다(`git log <배정 H 또는 시작 커밋>..<결과 H>`). 결과 `B`는 배정 `B`와 같다 |
     | rebase | 결과 `B`가 rebase 목표 기준 브랜치 tip이고, `git range-diff <배정 B>..<배정 H> <결과 B>..<결과 H>`가 충돌 해결분 말고는 같다([opencode.md](opencode.md) "rebase") |
     | 재검증, 검토(`review`·`rerun-only`) | 결과 대상이 배정 대상과 같다(커밋을 만들지 않았다) |

   어긋나면 그 시도의 기록(수용 기준 기록과 `review`의 코드 검토 결론 모두)은 판정에 쓰지 않고 아래 "검토 보고를 받으면"의 무효 증거처럼 다시 맡긴다. status가 비지 않은 것은 배정 전부터 있던 변경이어도(띄우기 직전 기록과 같아도) 어긋난 것이다. 작업자가 본 코드가 `H`와 같다는 보장이 없기 때문이다. 관리자가 남은 변경을 치우고(지울지 사용자에게 물어야 하는 변경이면 묻는다) 깨끗한 상태에서 다시 맡긴다. 띄우기 직전 기록과 다르면 작업자가 worktree를 바꾼 것이므로 그 사실도 판정에 적는다. 집계(evidence.md)의 "대상"은 이 결과 대상이다.
3. **다음 단계**: 역할에 따라 갈린다.
   - **구현자 시도**: 결론이 `완료`면 SKILL.md 4단계로. `막힘`이면 4단계로 가지 않고 아래 "복구"로.
   - **검토자 시도**(`review`·`rerun-only` 모두): 결론 값과 관계없이 아래 "검토 보고를 받으면"으로. `review`의 결론(`통과`/`수정 필요`)은 거기서 지적 판정과 G3에 쓰고, `rerun-only`는 결론이 없으므로 수용 기준 집계에만 쓴다.

## 검토 보고를 받으면

SKILL.md 5단계 판정 **전에** 한다. 병합 직전 관문에서 처음 알게 되지 않게 하려는 것이다.

1. **수용 기준 집계**: 지금 대상에 대해 [evidence.md](../v-mode/contracts/evidence.md) "수용 기준 집계"를 한다. 입력은 역할·수용 기준마다 **가장 나중에 배정된 시도의 기록**이다. 그보다 앞선 기록(예: 나중 시도가 다시 돌려 통과한 예전의 막힘)은 다시 다루지 않는다.
2. 집계가 `실패`인 필수 수용 기준은 5단계에서 `지금 고침`의 **차단** 지적으로 다룬다.
3. 집계가 `막힘`이거나 `증거 없음`인 필수 수용 기준은 아래 "복구".
4. 이번 보고가 `review`면 그 지적을 5단계 규칙대로 판정한다. `rerun-only`면 판정할 지적이 없다. 집계가 모두 `통과`가 됐으면 5단계의 나머지(이미 판정한 지적의 처리)를 이어 간다.

## 복구

막힘, 유효하지 않은 증거, 보고 없는 멈춤을 **역할과 진행 상태**로 나눠 다시 맡긴다. 다시 맡길 때도 "배정 전"을 한다.

| 상황 | 다시 맡길 것 |
| --- | --- |
| impl 기록이 막힘, 원인이 환경 | 환경을 고친 뒤 같은 impl 세션(없으면 impl 인계)에 **재검증**. 막힌 수용 기준만 맡긴다 |
| impl 기록이 유효하지 않음(dirty tree, 빌드 출처, 결과 대상 불일치) | 같은 impl 세션(없으면 impl 인계)에 **재검증**. 그 시도가 맡았던 수용 기준 전부를 맡긴다(evidence.md 유효 조건은 시도 전체에 걸린다) |
| rev 기록이 막힘, 원인이 환경 | 대상이 그대로면 자격 있는 rev 세션에 **rerun-only**(막힌 수용 기준만) |
| rev 기록이 유효하지 않음 | 자격 있는 rev 세션에 새 rev 시도. 코드 검토 결론도 잃었으면 `review`, 수용 기준만이면 `rerun-only`. 작업 트리가 깨끗하지 않아 무효가 된 `review` 시도(위 "결과 대상 확정")는 결론도 쓰지 않으므로 `review`다 |
| 막힘 원인이 제품·요구 결정 | 사용자에게 묻는다. 답에 따라 수용 기준 버전을 올리면 evidence.md "최신성" |
| impl이 보고 없이 멈춤, **구현은 끝났다**(커밋이 있고 원인·수정이 완료 보고 직전이었음을 worktree와 `worker-read`로 확인) | 실행 환경 문서의 **정지**로 정지를 확인 → archive.md "증거 없음 정산" → 같은 세션이나 impl 인계에 **재검증** |
| impl이 보고 없이 멈춤, **구현이 끝나지 않았다** | 정지 확인 → 증거 없음 정산 → 새 impl 시도에 **새 수정**을 **같은 worktree에서**(새로 만들지 않는다, 위 "배정 전" 2). 명세의 "이어받기" 칸에 남은 커밋과 변경을 적고 "레시피 첫 구현 절차의 1부터 지금 상태에서 다시 확인한다"를 적는다(위 "작업 종류 이름") |
| rev가 보고 없이 멈춤 | 정지 확인 → 증거 없음 정산 → 자격 있는 rev 세션에 같은 scope로 새 시도 |
| 작업자가 시작하지 못함(제출 실패, 또는 에이전트가 명세를 받기 전에 끝남) | archive.md "시작 실패"의 확인을 모두 한 뒤 `취소` → 원인을 고치고, 고친 것이 도구 설정이면 그 도구가 설정을 읽는지 확인한다 → 새 세션 키로 같은 작업 종류의 새 시도 |

정지가 확인되지 않으면 아무것도 정산하지 않고 사용자에게 "정지 미확인"을 알린다.

정지를 확인하는 과정에서 작업자 터미널이 해제되면(Orca `exited`·`released`, 두 번째 시범에서 자동 해제로 그랬다) 그 세션은 다시 쓰지 않는다. 위 표의 "같은 impl 세션(없으면 impl 인계)"은 이때 impl 인계가 되고, 새 세션 키로 시도를 만든다. 보고를 마치고 남겨 둔(`retained`) 상태만으로는 정지가 확인된 것이 아니다.

## 관리자 재시작

관리자 세션이 바뀌었거나 다시 시작했을 때, 끝나지 않은 작업마다 이 순서로 이어 간다. 이전 관리자의 대화는 쓰지 않는다. 쓰는 것은 `state.md`, 작업 파일, 보관 증거, 실행 환경의 기록뿐이다.

1. 실행 환경 문서의 **준비**로 이전 관리자의 Run에 묶는다(Orca: `state.md`의 `Run:` 줄로 `run-use`).
2. 정산된 시도(`취소`·`정리됨`·`증거없음`·`손상정산`, [archive.md](../v-mode/contracts/archive.md) "시도의 상태")는 다시 보관하거나 정산하지 않는다. 그 기록은 판정 입력으로 그대로 쓴다. 단 `정리됨`인데 결과 대상이 비었으면(이전 관리자가 보관 뒤 결과 대상 확정 전에 끊겼다) 보관 확인을 한 뒤 위 "완료 보고를 받으면" 2부터 한다. 보관 확인이 실패하면 archive.md "보관 손상"으로 간다.
3. 정산되지 않은 시도 가운데 보관이 시작된 것은 archive.md "중단 복구"로 간다. 상태가 `보관됨`·`원본정리대기`·`격리대기`이거나, `배정됨`·`보고됨`인데 `.local/vstack/<작업 이름>/evidence/` 아래에 그 시도의 staging·보관·`.void`·`.damaged` 폴더가 있는 시도다. 복구가 `정리됨`으로 끝나면 위 "완료 보고를 받으면" 2부터, `증거없음`·`손상정산`으로 끝나면 위 "복구"로 간다.
4. 나머지 가운데 상태가 `배정됨`·`보고됨`인 시도는 실행 환경에서 그 dispatch의 작업자 상태와 받은 편지함을 본다(Orca: `worker-show --dispatch <id>`, `inbox --terminal run:<run> --full`). 받은 편지함의 읽음·처리 표시로 판단하지 않는다. 이전 관리자가 보고에 무엇을 했는지는 시도 표와 보관 폴더(`evidence/<시도 ID>/`, `evidence/.staging/<시도 ID>/`)가 정본이다.

   | 작업자 상태 | 할 일 |
   | --- | --- |
   | 실행 중(살아 있고 settled가 아님) | 아무것도 정산하지 않고 기다린다 |
   | 끝났고, 그 시도의 Task·Dispatch ID가 든 `worker_done`이 있다 | 그 보고를 위 "완료 보고를 받으면"의 입력으로 쓴다. 이 관리자가 받은 보고가 아니어도 된다. 증거의 유효 조건은 누가 보고를 받았는지를 보지 않는다. 상태를 `보고됨`으로 고치고 "보관"(보관 순서 1)부터 한다 |
   | 끝났는데 보고가 없다 | 위 "복구"의 보고 없이 멈춤(정지 확인 → 증거 없음 정산 → 재검증 또는 새 수정) |
   | 정지를 확인하지 못함 | 정산·격리·재시작·worktree 삭제를 하지 않고 사용자에게 "정지 미확인"을 알린다 |

5. 이어 갈 단계를 정한다. 위 2~4를 마친 뒤 이 작업에서 **가장 나중에 배정된 시도**의 상태로 정한다(정산 처리는 다시 하지 않지만, 정산 뒤에 할 일을 했는지는 따로 본다).

   | 가장 나중 시도 | 할 일 |
   | --- | --- |
   | `배정됨`이고 실행 중 | 기다린다(위 4) |
   | `정리됨`이고 결과 대상 확정까지 끝났다 | "완료 보고를 받으면" 3(다음 단계) |
   | `증거없음`·`손상정산` | 위 "복구" 표에서 그 상황의 정산 뒤 부분(재검증, 새 수정, 같은 scope의 새 rev 시도)부터 |
   | `취소` | 위 "복구" 표 "작업자가 시작하지 못함"의 원인 해소와 새 시도부터 |

   그 다음 일에 해당하는 시도가 이미 배정돼 있으면(이전 관리자가 맡긴 뒤 끊겼다) 다시 맡기지 않는다. 그 시도가 곧 가장 나중 시도이므로 위 표를 그 시도로 다시 본다. 수용 기준 판정은 evidence.md "수용 기준 집계"(대상·역할·수용 기준별 가장 나중 시도, `취소` 제외)를 그대로 쓴다.
6. 이전 관리자의 기록을 보존한다. 기존 시도 줄의 배정 사실(시도 ID, 역할, 작업 종류, 맡은 수용 기준, 실행기, 세션, dispatch ID, 배정 대상)은 바꾸지 않는다. 상태, 결과 대상, 보관 경로, manifest 해시는 계약대로 채우고, 비고에는 복구 경위를 덧붙인다. 맡김 기록의 기존 줄은 결과가 나오면 결과 칸을 채운다. 새 배정에는 "배정 전" 기록을 모두 새로 만든다.

네 번째 시범(vstack 저장소 `docs/pilot-4.md`)에서는 구현 중에 끊긴 경우(끝났고 보고가 있음)만 돌려 봤다. 나머지 행과 보관 도중 끊김은 아직 돌려 보지 않았다.

## 교차 검토 배정

SKILL.md 4단계에서:

- 첫 버전에서 관리자는 검토자 역할을 맡지 않는다. [tiers.md](tiers.md) 검토 목록의 `관리자` 항목은 건너뛰고 다음 항목을 고른다. `minor-check`(관리자 확인)는 지적 해결 기록으로만 남고 검토 결론이 아니다.
- 대상이 바뀐 뒤의 첫 rev 시도는 `scope: review`다. `rerun-only`는 대상이 그대로이고 일부 수용 기준만 다시 돌릴 때만 쓴다.
- `review`는 필수 수용 기준 **전부**를 맡는다. 대상은 구현자 시도의 결과 대상이다.
- 검토자를 구현자와 같은 worktree에 띄우기 전에 구현자가 멈췄는지 본다(완료 보고를 보냈다). 두 역할이 같은 worktree에 동시에 쓰지 않는다.
- **깨뜨릴 범위 점검**: 다음 가운데 하나면 검토 명세의 "깨뜨릴 범위 점검" 줄에 [blast-radius](../blast-radius/SKILL.md)를 넣는다. 아니면 "해당 없음"으로 둔다.
  - 등급이 `hard`다.
  - 프로젝트 설정의 "간단한 구현에서 뺄 영역"을 건드린다.
  - diff가 작아도, 여러 호출자가 쓰는 함수나 입출력 방식·저장 형식·프로세스 종료 방식을 바꾸거나 공개된 이름을 지운다.
  - 이 점검은 수용 기준 재실행을 대신하지 않는다. 결과는 검토 보고서의 지적으로 들어오고, 5단계 판정에서 다른 지적과 같이 처분한다.

## 대상이 바뀌면

다음 일은 대상 `H` 또는 `B`를 바꾼다: 지금 고침 수정, 사소 수정, rebase, "리뷰 반영해". 그 뒤에는 병합 관문 전에 반드시 **재검증**한다([merge-gate.md](../v-mode/contracts/merge-gate.md) "진입점").

1. 변경을 한 작업자(impl)가 새 대상에서 필수 수용 기준 **전부**를 돌린다(레시피 "지적 수정"·"rebase" 절차의 끝). 같은 시도 안에서 한다. 완료 보고를 받으면 "완료 보고를 받으면" 2로 결과 대상을 확정한다.
2. rev `scope: review` 시도를 새로 배정한다. 대상은 1의 결과 대상. 지적 해결 판정 + 변경 diff + 브랜치 전체 + 필수 수용 기준 전부. 같은 검토자 세션을 다시 써도 된다(역할 자격만 맞으면).
3. 두 시도의 증거를 보관한다.

사소 수정을 관리자가 확인했어도([fixes.md](fixes.md)) 2를 건너뛰지 않는다.

## 원격 반영

작업자는 push하지 않는다. 관리자가 한다. PR을 만들 때(SKILL.md 6단계 1)와 병합 관문 직전에 한다. 게시할 것은 최신 시도들의 결과 대상 `H`다.

1. **로컬 확인**: `git -C <worktree> rev-parse HEAD`가 `H`이고 `git -C <worktree> status --porcelain`이 비었다. 아니면 게시하지 않고 사용자에게 알린다.
2. **원격 확인**: `git ls-remote origin refs/heads/<브랜치>`로 원격 브랜치 head를 읽는다.
   - 원격 브랜치가 있고 그 head가 이 작업의 `state.md` "게시" 기록에도, 시도 표의 결과 대상에도 없는 커밋이면(누군가 PR 브랜치에 직접 push했다) **여기서 멈춘다**. 게시하지도 병합하지도 않는다. 사용자에게 알리고, 사용자가 그 커밋을 받아들이면 그 커밋을 worktree로 가져와 새 대상으로 "대상이 바뀌면"을 한다.
3. **게시**: 원격 상태에 따라:

   | 원격 | 명령 |
   | --- | --- |
   | 브랜치가 없다(첫 게시) | `git -C <worktree> push -u origin HEAD:<브랜치>`(upstream을 설정한다) |
   | head가 `H`다 | push하지 않는다. 4의 기록은 방법 `원격 일치 확인`으로 남긴다 |
   | head가 `H`의 조상이다(수정 커밋을 더함) | `git -C <worktree> push origin HEAD:<브랜치>` |
   | head가 `H`의 조상이 아니다(rebase로 이력이 바뀜) | force-push가 필요하다. **사용자에게 확인받는다**([priority.md](../v-mode/contracts/priority.md) "불변 규칙"의 안전 멈춤). 브랜치, 지금 원격 head SHA, 올릴 `H`, `git range-diff` 요약을 보여 준다. 확인받으면 `git -C <worktree> push --force-with-lease=<브랜치>:<지금 원격 head SHA> origin HEAD:<브랜치>`. 확인받지 못하면 게시하지 않고 `state.md`에 `막힘: force-push 확인 대기`를 적는다 |

4. **다시 확인**: 원격 head를 다시 읽어 `H`와 같은지 본다. 같으면 `state.md` "게시" 절에 한 줄(시각, 브랜치, 게시한 SHA, 방법)을 적는다.

기준 브랜치나 다른 작업의 브랜치에는 어떤 경우에도 push하지 않는다.

## 병합 관문

SKILL.md 6단계에서 **병합 명령을 내리기 바로 전에** 한다. "병합해" 지시, 자동 병합, rebase·수정·리뷰 반영 뒤 모두 같다.

1. 위 "원격 반영"을 한다.
2. 원격의 대상을 읽는다: `H` = `gh pr view <PR> --json headRefOid`, `B` = `git ls-remote origin refs/heads/<기준 브랜치>`.
3. 증거의 결과 대상과 다르면 병합하지 않는다. `B`만 바뀌었으면 rebase를 맡기고(SKILL.md 6단계 2) "대상이 바뀌면"으로 간다.
4. merge-gate.md "판정식" G1~G5를 판정한다. G1·G3에 쓰는 시도는 보관 확인을 다시 한다.
5. `state.md` "관문" 절에 한 줄을 적는다.
6. 모두 통과면 병합한다: `gh pr merge <PR> --<병합 방법> --match-head-commit <H> --subject "<제목> (<이슈 표시>)"`. 원격 브랜치 삭제는 `MERGED`를 확인한 뒤 한다.
7. `gh pr view <PR> --json state,mergedAt,mergeCommit,baseRefName`으로 `MERGED`와 기준 브랜치를 확인한다. 아니면 `state.md` 첫 줄을 `병합 대기`로 두고 다음에 깨어날 때 다시 본다. 확인되면 관문 기록 결과를 `병합 확인`으로 하고, 기준 브랜치 경쟁을 확인한다(merge-gate.md "병합 명령과 확인" 3).

하나라도 실패하면 병합하지 않는다. 실패한 조건과 이유를 관문 기록과 사용자 보고에 적는다.

## 사람이 병합했을 때

"병합됐어" 지시: merge-gate.md "사람이 직접 병합한 경우". `MERGED`가 아니면 아무것도 정리하지 않는다. 마지막 관문 통과 기록의 `H`와 다르거나 기록이 없으면 "관문 미확인 병합"으로 보고하고, 정리는 이어 간다.

## 그만둘 때

사용자가 "그만둬"라고 하면:

1. 이 작업의 작업자를 모두 실행 환경 문서의 **정지**로 멈추고 정지를 확인한다. 확인되지 않은 작업자가 있으면 사용자에게 알리고 그 작업을 정리하지 않는다.
2. 시도를 모두 정산한다(archive.md).
3. PR을 닫을지 사용자에게 묻는다. 닫지 않고 열어 두면, 열린 PR 때문에 그 이슈는 "진행 중"으로 보여 다시 맡겨지지 않는다는 것을 함께 알린다.
4. worktree는 병합되지 않았으므로 지우지 않는다. state-and-rollback.md "되돌리기"의 "새로 시작"처럼 보존하고, 지울지는 사용자가 정한다(미병합 변경 삭제는 안전 멈춤이다).
5. PR을 닫았으면 이슈를 맡길 상태로 되돌린다. `state.md`를 `끝`, 소유를 `소유: 포기(<날짜>, 그만둠)`로 쓴다.

## worktree 지우기 전

SKILL.md 6단계 6의 확인에 둘을 맞춘다.

- "남은 변경이 없다"는 `@{u}`(upstream)로 보지 않는다. 병합 뒤 원격 브랜치를 지우면 upstream이 사라지기 때문이다. 대신 `git -C <worktree> status --porcelain`이 비었고, `git -C <worktree> rev-parse HEAD`가 `state.md` "게시" 절의 마지막 게시 SHA와 같은지 본다(게시하지 않은 커밋이 없다).
- 이 작업의 시도가 모두 **정산됐다**(archive.md "정산"). 정산되지 않았으면 지우지 않는다.

## PR 본문

[pr-template.md](pr-template.md) "검증"에 수용 기준별 판정과 증거 위치(`.local/vstack/<작업 이름>/evidence/`)를 적는다. 증거 파일 자체는 PR에 올리지 않는다.
