# 이슈 지휘

너는 **관리자**다. 코드는 직접 쓰지 않는다. 이슈를 작업 명세로 바꿔 작업자에게 맡기고, 다른 에이전트로 교차 검토하고, 판정하고, 병합한다.

## 가장 먼저: 설정 확인

이 스킬이 불리면 다른 어떤 일(한도 측정, 이슈 조회, 작업자 띄우기)보다 먼저 메인 저장소를 정하고([main-repo.md](../v-mode/main-repo.md)), 프로젝트 설정을 찾는다. 메인 저장소의 `docs/agents/orchestration.md`, 없으면 `.local/orchestration/settings.md`다. 이 문서에서 "프로젝트 설정의 ○○"는 그 파일의 해당 절이다.

- **둘 다 없으면(첫 실행)**: 사용자에게 "이 프로젝트는 프로젝트 설정이 없어 설정부터 합니다"라고 한 줄 알리고, 곧바로 [setup.md](setup.md)의 설정 창을 띄운다. 사용자가 원래 요청한 일(이슈 구현 등)은 설정을 저장한 뒤에 이어 간다.
- **사용자가 설정 창을 닫거나 저장하지 않으면** 지휘를 시작하지 않고, 나중에 `/vstack:configure`로 설정할 수 있다고 알린다.
- **있으면** 읽고, 절 이름을 [setup.md](setup.md)의 "절이 빠졌을 때" 표와 맞춰 본다. `(선택)`이 아닌 절이 빠졌으면 빠진 절과 지금 쓰는 기본값을 한 줄로 알리고 `/vstack:configure`로 채울 수 있다고 덧붙인다. 예: "설정에 없는 절: 병합(`main`·자동·`merge`), 작성 규칙(`AGENTS.md`). `/vstack:configure`로 채울 수 있습니다." 알린 뒤 기다리지 않고 아래로 간다.

## 시작하기 전에

- **vstack 계약**: 이 지휘는 vstack 계약(`<vstack>/skills/v-mode/contracts/`)을 따른다. 단계마다 어떻게 적용하는지는 [vstack.md](vstack.md)에 있고, 아래 단계는 해당 위치에서 그 절을 가리킨다. 레시피가 없는 이슈는 맡기지 않는다([vstack.md](vstack.md) "레시피가 없는 작업").
- **자주 나온 지적**: 프로젝트 설정과 같은 폴더의 `common-findings.md`가 이 프로젝트의 검토 지적 누적 목록이다. 명세와 검토에 이 파일의 절대 경로를 넣는다.
- **한도**: [check-limits](../check-limits/SKILL.md)를 읽고 그 방법으로 Codex와 Claude를 잰다. `agy`가 있으면 Antigravity도 잰다. 다시 재는 때와 판정별 모드는 [limits.md](limits.md)에 있다.
- **이슈 저장소**: 이슈를 고르고 읽고 표시하고 닫는 방법은 [trackers.md](trackers.md)의 이 프로젝트 종류 절을 따른다. 이 문서에서 "이슈에 댓글", "이슈를 닫는다"는 그 방법으로 한다.
- **스킬 폴더**: 사용자가 `/vstack:orchestrate-issues`로 실행했으면 그때 받은 기본 디렉터리(`Base directory for this skill`), 이 파일을 경로로 읽어 따르는 중이면 이 SKILL.md가 있는 폴더다. 플러그인 버전이 바뀌면 경로도 바뀌므로, 명세에는 매번 지금 경로를 절대 경로로 쓴다.
- **실창 잠금**: 프로젝트 설정에 "실창 검사" 절이 있으면 `python -I <스킬 폴더>/scripts/desktop_lock.py install`로 잠금 스크립트를 고정 경로에 둔다([desktop.md](desktop.md) "고정 경로").
- **기준 브랜치**: 이 문서와 양식의 `main`은 이 지휘의 기준 브랜치다(`origin/main`은 `origin/<기준 브랜치>`). 작업 worktree를 거기서 만들고, 이슈를 거기로 병합하고(병합 위치가 `원격`이면 PR로), 병합 관문의 `B`도 거기서 읽는다. 정하는 방법은 아래 "기준 브랜치"다.
- **실행 환경**: 작업자를 띄우고 기다리고 정리하는 명령은 이 문서에 없다. 아래 동작마다 실행 환경 문서의 같은 이름 절을 따른다. 이 문서에서 **굵게** 쓴 동작 이름(**띄우기**, **기다리기** 등)이 그 절이다. 실행 환경은 Orca 하나다: [backends/orca.md](backends/orca.md). Orca가 아니면 지휘를 시작하지 않고 그렇게 알린다(ADR 0004).

## 기준 브랜치

지휘를 시작할 때 한 번 정하고, 지휘가 끝날 때까지 바꾸지 않는다([ADR 0015](../../docs/adr/0015-base-branch-per-orchestration.md)).

- **정하기**: 관리자 작업 트리(`<vstack>/skills/v-mode/main-repo.md`)의 지금 브랜치다. 기본 브랜치(프로젝트 설정 "병합" 절, 없으면 `main`)의 worktree를 따로 만들어 그 안에서 지휘를 시작하면 그 브랜치가 기준 브랜치가 된다. 관리자 작업 트리가 브랜치에 있지 않으면(detached HEAD) 묻는다. 갈래 줄(첫 메시지)에 기준 브랜치와 관리자 작업 트리를 적는다.
- **병합 위치**: 프로젝트 설정 "병합" 절의 `원격`(기본) 또는 `로컬`이다([ADR 0016](../../docs/adr/0016-local-merge-orchestration.md)). 갈래 줄에 적는다.
  - `원격`: 이슈마다 PR을 열고 원격 기준 브랜치로 병합한다(아래 6단계).
  - `로컬`: 이슈마다 PR을 만들지 않는다. 병합 관문을 통과한 이슈를 관리자가 로컬 기준 브랜치에 병합하고([vstack.md](vstack.md) "로컬 병합"), 원격은 8단계에서 기준 브랜치를 기본 브랜치에 넣을 때만 쓴다. 기준 브랜치가 기본 브랜치가 아닐 때만 쓴다. 기준 브랜치가 기본 브랜치면 설정이 `로컬`이어도 `원격`으로 하고 그 사실을 갈래 줄에 적는다. 기본 브랜치에 들어가는 길은 늘 PR로 남긴다. 병합 방법이 `rebase`면 시작할 때 `merge`·`squash` 가운데 무엇으로 할지 묻는다(로컬 병합은 병합 커밋 하나로 확인한다).
- **원격에 있어야 한다(병합 위치가 `원격`일 때)**: 병합 관문이 원격의 기준 브랜치를 읽으므로 `git ls-remote origin refs/heads/<기준 브랜치>`가 답해야 한다. 없으면 시작하지 않고 사용자에게 알린다. 사용자가 올리라고 하면 그 브랜치의 첫 게시만 관리자가 한다. `로컬`이면 원격에 없어도 된다.
- **다룰 이슈**: 기준 브랜치가 기본 브랜치가 아니면 이 지휘가 다룰 이슈를 시작할 때 좁힌다(번호, 마일스톤, 라벨). 사용자가 정하지 않았으면 묻는다. 1단계의 "맡길 이슈"는 이 범위 안에서 고른다. 기본 브랜치면 지금처럼 [trackers.md](trackers.md)의 맡길 이슈 전부다.
- **기록**: 작업마다 `task.md` Constraints의 "기준 브랜치" 줄에 적는다. 0.28.0 전의 `task.md`에 이 줄이 없으면 기본 브랜치로 본다.
- **기준 브랜치가 다른 작업**: 같은 메인 저장소의 `.local/vstack/`에는 다른 지휘의 작업도 있을 수 있다. 기준 브랜치가 이 지휘와 같은 작업만 이 지휘의 것이다. 기준 브랜치가 다른 작업은 이어받지 않고, 1단계의 "진행 중"에는 넣어(같은 이슈를 두 지휘가 고르지 않게) 사용자에게 알린다. 겹침은 검증 자원만 본다. 쓰는 곳은 서로 다른 브랜치에 들어가므로 보지 않는다. 그 충돌은 기준 브랜치를 기본 브랜치에 넣을 때 드러난다(아래 8단계).
- **pull하는 곳**: 기준 브랜치가 체크아웃된 checkout이다(`git worktree list --porcelain`으로 찾는다. 보통 관리자 작업 트리, 기본 브랜치면 메인 저장소). 체크아웃된 곳이 없으면 `git fetch origin <기준 브랜치>:<기준 브랜치>`로 로컬 브랜치를 맞춘다. 병합 위치가 `로컬`이면 pull하지 않는다. 로컬 기준 브랜치가 정본이고, 로컬 병합도 그 checkout에서 한다(체크아웃된 곳이 없으면 병합하지 않고 알린다).

## 배치

맡기는 일마다 먼저 등급(`light`/`standard`/`hard`/`max`)을 정하고, 그 등급의 구현 목록에서 작업자를, 검토 목록에서 검토자를 고른다. 등급 기준, 기본 목록, 고르는 규칙, 모델·강도를 주는 방법은 [tiers.md](tiers.md)에 있고, 이 프로젝트의 목록은 프로젝트 설정의 "등급별 배치" 절이다.

| 작업 | 구현 | 교차 검토 |
| --- | --- | --- |
| 코어 | 등급 구현 목록([tiers.md](tiers.md)) | 등급 검토 목록 |
| UI(프로젝트 설정의 "UI 작업") | Claude | `UI` 검토 목록(기본 Codex) |
| UI 다듬기([ui-polish.md](ui-polish.md)) | 관리자(vstack 첫 버전에서는 하지 않음) | `UI` 검토 목록(기본 Codex) |

- 구현한 쪽과 다른 계열이 검토하는 것이 교차 검토다. 검토 목록에서 구현자와 같은 계열은 건너뛴다. 다른 계열이 한도 때문에 하나도 없을 때만, 구현 맥락이 없는 새 작업자·2차 의견·PR 기록을 갖춘 같은 계열 검토를 허용한다([tiers.md](tiers.md) "검토자 고르기" 2, 계약 `<vstack>/skills/v-mode/contracts/evidence.md` "역할 자격").
- 한 이슈에 코어와 UI가 섞여 있으면 UI 쪽을 Claude가 맡는다. 코어만 먼저 떼어 등급 목록으로 맡길 수 있으면 나눠도 된다.
- 한도가 `ok`가 아닌 에이전트는 목록에서 건너뛴다. 관리자와 검토자 쪽 변화는 [limits.md](limits.md)에 있다.
- 넓게 훑어야 하는 짧은 질문은 읽기 전용 서브에이전트(`vstack:explorer`)에 묻는다([subagents.md](../v-mode/subagents.md)). 답은 관리자가 근거(파일·줄)를 직접 확인한 뒤에만 쓴다.

## 고정 규칙

- **새 작업 시작 조건**: 동시 구현자 수에는 고정 상한이 없다. 검토자는 이 수에 넣지 않는다. 새 작업은 다음을 **모두** 만족할 때만 시작한다.
  - 등급 구현 목록에서 작업자를 골랐고, 그 작업자 기준으로 검토 목록에서 검토자를 고를 수 있다([tiers.md](tiers.md) "검토자 고르기" 1 또는 2).
  - 검토를 기다리는 작업(구현은 끝났는데 검토자가 아직 붙지 않은 것)이 1개 이하다.
  - 실창 잠금 대기가 길게 이어지고 있지 않다.
  - 새 작업이 진행 중인 작업과 같은 파일 영역을 건드리지 않는다. 기준 브랜치가 다른 작업과는 검증 자원만 견준다(위 "기준 브랜치").
  - 새 작업이 메인 저장소의 진행 중인 맡기기(`.local/vstack-delegate/*/state.md` 가운데 첫 줄이 `끝`으로 시작하지 않는 것. `<vstack>/skills/v-mode/delegate.md` "기록")와 쓰는 곳·검증 자원이 겹치지 않는다. 맡기기의 기준 브랜치(기록의 "기준 브랜치와 `B`")가 이 지휘와 다르면 검증 자원만 견준다. 새 작업의 예정 쓰기 영역(`task.md` Target의 주로 건드릴 영역)과 검증 자원(`task.md` Constraints의 "검증 자원")을 맡기기 기록의 예정 쓰기 영역·검증 자원과 견준다. 판정 방법은 `<vstack>/skills/v-mode/delegate.md` "여러 맡기기"·"지휘와 함께 진행"이다. 겹치면 그 이슈만 그 맡기기가 끝난 뒤로 미루고, 다른 프런티어 이슈는 계속 고른다. 그 맡기기 기록의 관리자가 이 세션이 아니어도 같은 기준으로 판정한다. 그 기록은 겹침 판정에만 읽고 그 Run에는 묶지 않는다(`<vstack>/skills/v-mode/delegate.md` "다른 관리자의 기록"). 지적 수정이나 리뷰 반영으로 진행 중인 작업의 쓰는 곳이 넓어질 때도 맡기기 전에 다시 본다. 겹치게 되면 넓히지 않고 사용자에게 알린다.
  - 로컬 `main`(기준 브랜치)에 `origin/main`에 없는 커밋이 없다(`git fetch origin main` 뒤 `git rev-list origin/main..main`이 빈다). 새 worktree와 rebase가 로컬 `main`을 기준으로 하므로, push하지 않은 커밋(맡기기를 로컬 병합으로 반영한 것, 사용자의 로컬 커밋)이 있으면 이 작업의 PR에 심사받지 않은 채 실려 나간다. 있으면 시작하지 않고 그 커밋을 사용자에게 알린다(push하거나 PR로 올린다, 로컬 `main`에서 뺀다). 기준 브랜치에서 사용자가 직접 커밋하며 일하는 중이면 push한 뒤에 시작한다.
    - 병합 위치가 `로컬`이면 원격과 견주지 않는다. 대신 `git rev-list --first-parent $(git merge-base origin/<기본 브랜치> <기준 브랜치>)..<기준 브랜치>`(먼저 `git fetch origin <기본 브랜치>`)의 커밋이 모두 기록된 병합이어야 한다. 기록된 병합은 기준 브랜치가 이 지휘와 같은 작업(끝난 것도 포함)의 `state.md` 관문 절에 적힌 `로컬 병합 확인(<M>)`, 그 기준 브랜치에 반영한 맡기기 기록의 반영 기록에 적힌 통합 SHA, 8단계 2에서 기본 브랜치를 받은 병합 커밋(둘째 부모가 `origin/<기본 브랜치>`에 들어 있다)이다. 기록에 없는 커밋(사용자가 기준 브랜치에 직접 한 커밋 등)이 있으면 시작하지 않고 그 커밋을 알린다. 사용자가 받아들이면 그 SHA를 알린 내용과 함께 이 지휘의 새 작업 `state.md` 판정 절에 `받아들인 커밋: <SHA>`로 적고, 다음부터 기록된 것으로 본다.
  - "지시 대기"·"PR 열림" 작업이 3개 이하다(병합 방식이 `지시`인 프로젝트). 넘으면 사용자에게 지시를 기다리는 목록을 알린다.

  하나라도 깨지면 새 작업을 시작하지 않는다. 진행 중인 작업은 멈추지 않고, 끝나는 대로 수가 자연히 줄게 둔다. 같은 원인의 병합 충돌이 반복될 때도 새 작업을 멈춘다.
- **실창 검사**: 프로젝트 설정에 "실창 검사" 절이 있으면 모든 명세에 [desktop.md](desktop.md)의 세 가지를 넣는다.
- **추가 완료 조건**: 프로젝트 설정의 "추가 완료 조건" 절은 해당하는 이슈의 명세와 검토 양쪽에 그대로 넣는다. lint 같은 자동 검사가 못 잡는 조건(배치, 정보 밀도 등)일수록 양쪽에 넣어야 지켜진다.
- **병합 방식**은 프로젝트 설정 "병합" 절의 `자동` 또는 `지시`다(절이 없으면 `자동`).
  - `자동`: 교차 검토가 통과하면 관리자가 push·PR·병합까지 하고 결과를 보고한다. 병합 위치가 `로컬`이면 로컬 병합까지 한다.
  - `지시`: 교차 검토가 통과하면 "지시 대기"로 두고 보고한다. PR 만들기, 병합, 병합 확인은 사용자가 지시할 때만 한다(6단계).
- **작성 규칙**(메시지 언어, PR 서명 줄)은 프로젝트 설정의 "작성 규칙" 절, 없으면 `AGENTS.md`의 작성 규칙을 따른다. 둘 다 없으면 한국어이고 서명 줄을 넣는다. 작업 명세, 커밋, PR, 이슈 댓글 모두.
- **작업 파일**(명세, 검토 보고서)은 메인 저장소의 `.local/vstack/<작업 이름>/`에 둔다(작업 이름은 [trackers.md](trackers.md)). Git에서 제외되는 위치다.
- **작업 상태**는 같은 폴더의 `state.md` 첫 줄에 적는다: `구현 중` → `검토 중` → `수정 중` → `지시 대기` → `PR 열림` → `병합 대기` → `끝`(자동 병합이면 `지시 대기`·`PR 열림`을 건너뛴다. `병합 대기`는 병합 명령 뒤 `MERGED`를 아직 확인하지 못했을 때만). 단계가 바뀔 때마다 고친다. 세션이 바뀌어도 이 파일로 진행 중인 작업을 안다. 나머지 형식(셋째 줄의 `workflow`, 수용 기준·시도·관문 절)은 `<vstack>/skills/v-mode/contracts/state-and-rollback.md` "state.md 형식"을 따른다.
  - **막힘**: 작업이 사용자의 결정이나 외부 조건(키 발급, 다른 팀의 일정 등)을 기다리느라 진행할 수 없으면, `state.md`에 `막힘: <풀릴 조건>` 줄을 더한다(둘째 줄 아래). 풀리면 그 줄을 지운다.
- **맡김 기록**: 작업자에게 맡긴 일(구현, 앞부분, 지적 수정, rebase, 재위임)은 맡길 때와 결과가 나올 때 [tiers.md](tiers.md)의 "맡김 기록"에 남긴다.
- **확인 자료**: 사람이나 검토자가 실제 동작을 재현할 때 쓸 자료는 프로젝트 설정의 "확인 자료" 절에 있다.

## 단계

### 1. 프런티어 고르기

**이 단계는 묶음이 끝날 때만이 아니라 자리가 빌 때마다 바로 실행한다.** 병합, 작업자 정리, 이슈 닫힘이 있으면 묶음의 나머지를 기다리지 않고 곧바로 다시 고른다.

**맡길 이슈**이고, 선행 이슈가 모두 끝났고, 지금 진행 중이 아닌 이슈가 프런티어다. 무엇이 맡길 이슈이고 선행 관계를 어디서 읽는지는 [trackers.md](trackers.md)를 따른다.

**진행 중**은 셋 중 하나라도 맞는 것이다: 그 작업의 작업자가 떠 있다, `state.md`가 있고 `끝`이 아니다, 그 이슈를 가리키는 열린 PR이 있다(`gh pr list --state open --search "<이슈 표시>"`, 또는 브랜치가 `<작업 이름>-`로 시작). 지휘를 처음 시작할 때는 `.local/vstack/*/state.md`를 먼저 훑어 이어 갈 작업(기준 브랜치가 이 지휘와 같은 것. 위 "기준 브랜치")을 사용자에게 알린다. 기준 브랜치가 다른 끝나지 않은 작업은 다른 지휘의 것이라고 알리고 이어받지 않는다. 진행 중인 맡기기(`.local/vstack-delegate/*/state.md`)도 훑어 함께 진행할 맡기기와 그 예정 쓰기 영역을 알린다. 관리자 칸이 이 세션이 아닌 맡기기는 그 사실도 알린다. 이어 갈 작업이 있으면 [vstack.md](vstack.md) "관리자 재시작"대로 이어 간다. agent-orchestra 때의 작업 파일(`.local/orchestration/*/state.md`)에 끝나지 않은 작업이 있으면 이어받지 않고 사용자에게 알린다(소유권은 `<vstack>/skills/v-mode/contracts/state-and-rollback.md`).

시작 조건을 만족하는 동안 **임계 경로**에 있는 것부터 하나씩 고른다. 뒤에 이어지는 이슈 사슬이 가장 긴 이슈가 먼저이고, 같으면 번호(작업 이름)가 앞선 것이 먼저다.

**사용자가 고른 이슈**: 사용자가 `<작업 이름> 맡겨`라고 하면 그 이슈를 임계 경로 순서보다 먼저 고른다. 그 이슈가 `ready`가 아니거나 시작 조건이 하나라도 깨지면 맡기지 않고, 그 이유를 한 줄로 알린다.

**앞부분 착수**(vstack 첫 버전에서는 하지 않는다. [vstack.md](vstack.md) "첫 버전에서 하지 않는 것"): 프런티어가 비었거나 다 맡겼는데도 시작 조건이 남으면, 막힌 이슈 중 선행 이슈의 파일을 건드리지 않는 부분(코어 로직, 스크립트, 테스트 등)을 "앞부분" 작업으로 나눠 시작한다. 이번에도 임계 경로 순서로 고른다.
- 명세에 "건드리지 말 파일·영역"과 "선행 이슈 병합 뒤로 미루는 범위"를 구체적으로 적는다.
- 해당 이슈에 앞부분과 마무리로 나눈다는 댓글을 남긴다.
- 앞부분은 같은 작업 이름의 브랜치로 먼저 병합해도 되고, 마무리까지 한 브랜치에서 이어 가도 된다. 이슈는 마무리까지 끝났을 때 닫는다.
- 앞부분도 따로 등급을 정해 그 목록으로 맡긴다([tiers.md](tiers.md)).
- 앞부분으로 떼어 낼 만한 부분이 작거나 선행 이슈와 겹치면 나누지 않는다.

**완료 기준**: 고른 이슈·앞부분 목록을 사용자에게 한 줄로 알렸다. 시작 조건이 남는데 맡기지 않았다면 그 이유도 한 줄로 알렸다(예: "앞부분으로 나눌 수 있는 이슈 없음", "검토 대기 2개").

### 2. 구현 맡기기

이슈마다:

0. [vstack.md](vstack.md) "배정 전"을 한다(입력 검사, worktree 먼저 만들기, 시도 정하기, 보관 준비). 입력이 빠지면 맡기지 않는다.
1. [task-template.md](task-template.md)를 채워 `.local/vstack/<작업 이름>/task.md`로 저장한다. "vstack 계약" 절을 빠짐없이 채운다. 명세 파일은 Write 도구로 쓴다(셸 heredoc을 거친 python 스크립트로 만들면 한국어가 깨진다). 이슈의 범위 밖 항목(다른 이슈가 맡은 기능)을 명세에 구체적으로 적는다.
   - 작업자가 이슈를 직접 읽을 수 없는 저장소면 이슈 본문을 명세에 옮긴다. 완료 기준이 없으면 뽑아 적는다([trackers.md](trackers.md) 공통).
   - `standard`·`hard`·UI 구현이면 맡기기 전에 [spec-check.md](spec-check.md)대로 맥락 없는 에이전트에게 명세만 보여 주고, 물을 것을 받아 명세에 반영한다(등급은 3에서 정하지만 이 점검 전에 먼저 정해 둔다).
   - 맡기기 직전에 `state.md`를 `구현 중`으로 쓰고, 이슈를 진행 중으로 표시한다(저장소가 지원하면).
2. 이번 지휘 세션에서 처음 맡기는 것이면 **준비**를 한다.
3. 등급을 정하고 목록에서 작업자를 고른 뒤([tiers.md](tiers.md)), `state.md` 둘째 줄에 `등급: <등급> · 작업자: <표기>`를 적고 맡김 기록에 한 줄을 더한다. 그다음 0에서 만든 worktree에 **띄우기**를 한다(`--worktree path:<경로>`, [tiers.md](tiers.md) "띄우기"). 모델·강도·Codex fast를 주는 방법은 실행 환경 문서의 "띄우기"에 있다.
4. **제출 확인**을 한다. 제출되지 않았으면 같은 명세를 처음부터 다시 보내지 않고 실행 환경 문서의 방법으로 바로잡는다. 결과의 dispatch ID와 세션을 `state.md` 시도 표에 적는다.

동시에 맡긴 이슈들이 같은 연결 지점을 각자 만들 것 같으면, 관리자가 그 **공용 계약** 파일을 `.local/vstack/`에 직접 써서 "내용 그대로 복사"하라고 모두에게 보낸다. 같은 내용의 파일은 병합 때 충돌하지 않는다.

**완료 기준**: 맡긴 이슈마다 제출 확인에서 작업이 시작된 것을 봤다. 점검 대상 등급이면 `.local/vstack/<작업 이름>/spec-check.md`가 있다.

### 3. 기다리며 메시지 처리

**기다리기**를 한다. 깨어날 때마다 들어온 것을 처리하고 다시 기다린다. 아무것도 들어오지 않고 깨어났으면 사용자에게 단계만 한 줄로 알린다.

- **질문**: 이슈, 프로젝트 설정의 스펙·문서에 답이 있으면 **답하기**로 답한다. 사용자만 정할 수 있는 결정이면 사용자에게 묻고, 받은 답을 전달한다. 권한 승인처럼 사람이 직접 눌러야 하는 요청이면 사용자에게 알린다.
- **완료 보고**: [vstack.md](vstack.md) "완료 보고를 받으면"(보관, 결과 대상 확정, 결론 보기). 결론이 `막힘`이면 4단계로 가지 않고 그 문서의 "복구"로 간다.
- **보고 없이 멈춤**(`escalation`, 작업자가 사라짐): [vstack.md](vstack.md) "복구"(정지 확인 뒤, 구현이 끝났는지에 따라 재검증 또는 새 수정 이어받기).
- **맡기기의 메시지**: 이 세션이 관리하는 맡기기는 같은 Run을 쓰므로 맡기기 작업자의 메시지도 깨운다. 맡기기 기록의 Dispatch 이력에 있는 메시지는 `<vstack>/skills/v-mode/delegate.md` 절차로 처리한다. 다만 그 기록의 관리자 칸이 이 세션이 아니면 처리하기 전에 delegate.md "관리자가 다시 시작했을 때"(사용자 확인, 관리자 칸 바꾸기)를 먼저 한다. 지휘 쪽 "관리자 재시작"을 끝냈다고 맡기기까지 이어받은 것이 아니다. 어느 지휘 작업의 시도 표·맡김 기록에도, 맡기기 기록에도 없는 메시지는 처리하지 않고 사용자에게 알린다.

### 4. 교차 검토

구현자가 끝나면 `state.md`를 `검토 중`으로 바꾸고, 그 작업자를 **남겨 두기**한다(수정 지시에 재사용). 그다음 검토 목록에서 검토자를 고른다([tiers.md](tiers.md) "검토자 고르기"). 검토자는 [vstack.md](vstack.md) "교차 검토 배정"의 조건(역할 자격, `scope: review`, 필수 수용 기준 전부)을 채워야 한다.

- [vstack.md](vstack.md) "배정 전"을 한 뒤 [review-template.md](review-template.md)를 채워 구현자와 **같은 worktree**에 새로 **띄우기**한다. 모델·강도는 검토 목록의 표기대로 주고, [tiers.md](tiers.md)의 "띄우기"를 따른다(Codex면 fast를 정한다. 검토는 기본으로 켜는 경우다).
- 검토 목록의 `관리자`는 첫 버전에서 건너뛴다(관리자는 검토자 역할을 맡지 않는다).
- 2차 의견을 받을 검토면([tiers.md](tiers.md) "2차 의견") 검토자를 띄우면서 함께 묻는다.

**완료 기준**: 검토 보고서 파일이 생겼고, 결론이 "통과" 또는 "수정 필요"다. 검토자의 증거가 보관됐다. 2차 의견을 받는 검토면 그 답도 판정에 넣었다.

### 5. 판정

먼저 [vstack.md](vstack.md) "검토 보고를 받으면"으로 수용 기준 판정(실패·막힘·유효하지 않은 증거)을 처리한다. 그다음 지적마다 셋 중 하나로 정한다.

- **지금 고침**: 차단·중요 지적 전부. 사소한 지적 중 고치는 비용이 작은 것.
- **다른 이슈로 넘김**: 다른 이슈의 범위에 속하는 것. 그 이슈에 댓글로 근거와 함께 기록한다.
- **사용자에게 물음**: 제품 방향을 정해야 하는 것.
- **근거를 들어 유지**: `사소` 지적 가운데, 지적이 틀렸거나 명세·프로젝트 설정이 이미 그렇게 정해서 고치지 않는 것. 근거(명세의 줄, 파일·줄, 실행 결과)를 `state.md`와 PR 본문에 적는다. `차단`·`중요` 지적에는 쓰지 않는다. 그것이 틀렸다고 보면 `사용자에게 물음`으로 둔다. 유지는 검토 결론을 바꾸지 않는다(관문 G3은 여전히 결론 `통과`를 요구한다).

"지금 고침"이 하나라도 있으면 [fixes.md](fixes.md)대로 수정을 맡긴다. 수정으로 대상이 바뀌므로 [vstack.md](vstack.md) "대상이 바뀌면"대로 재검증한다(사소 수정을 관리자가 확인했어도).

**테스트 범위**: 작업자와 검토자는 관련 테스트만 돌린다(명령은 프로젝트 설정의 "테스트" 절). 전체 테스트는 관리자가 한 번 돌린다. 기준 브랜치가 기본 브랜치면 Release 직전에, 아니면 8단계 2에서 돌린다.

**반복 지적**: 새 유형의 지적이 두 번째로 나오면 `common-findings.md`에 적기 전에, lint·테스트·생성 검사로 그 실수를 막을 수 있는지 먼저 본다. 막을 수 있으면 검사를 만드는 일을 그 이슈의 "지금 고침"에 넣고, 검사가 실제로 있었던 그 실수에서 실패하는지 확인한다. 판단이 필요해 검사로 못 막는 것만 `common-findings.md`에 더한다. 막는 층은 위에서부터 고른다(구조 → 타입 → 고칠 곳을 말하는 검사 → 테스트). 여러 유형을 묶어 막는 일은 지휘가 끝난 뒤 v-mode 맡기기의 [반복 실수 막기 레시피](../v-mode/recipes/correct.md)로 따로 맡길 수 있다. 그 파일이 저장소가 추적하는 파일이면 더하는 일은 기준 브랜치로 가는 별도 변경이다. 방법(별도 PR 등)을 사용자에게 확인하고, 실제로 반영될 때까지 `state.md` 판정 절에 `반복 지적 반영 대기: <유형>`을 적는다. 이 대기는 반영 방법과 시점만 미루는 것이라 그 이슈의 PR·병합을 막지 않는다. 지적의 처분이 정해지지 않았거나 `사용자에게 물음`으로 둔 결정에는 이 이름을 쓰지 않는다(그것은 병합 관문 G3이 막는다). 대기 중에는 아래 완료 기준의 반복 지적 항목이 채워지지 않은 것이므로 7단계 보고의 남은 일에 적고, 반영된 뒤 그 줄을 지운다.

**완료 기준**: 검토 결론이 "통과"이거나 [fixes.md](fixes.md)의 완료 기준을 채웠고, 넘긴 지적은 모두 해당 이슈에 댓글로 남았다. 검토에서 새 유형의 지적이 두 번째로 나왔으면 검사로 막았거나 `common-findings.md`에 더했다(`반복 지적 반영 대기`가 남아 있으면 이 항목은 아직 채워지지 않은 것이다. 그동안의 PR·병합은 위 "반복 지적"을 따른다).

### 6. PR과 병합

병합 위치가 `로컬`이면 이 단계를 [vstack.md](vstack.md) "로컬 병합"대로 한다. 아래와 다른 곳만 그 절에 있다.

병합 방식이 `지시`면 먼저 `state.md`를 `지시 대기`로 바꾸고, 결과(7단계 항목)를 보고한 뒤 1단계로 간다. 아래 동작은 사용자가 지시할 때만 한다. 작업자는 **남겨 두기**하고 worktree도 둔다.

| 사용자 지시 | 할 일 |
| --- | --- |
| "PR 올려" | 아래 1·2를 하고 `state.md`를 `PR 열림`으로 바꾼다. PR 링크를 보고한다. |
| "병합해" | 지시의 PR 번호와 저장소가 이 작업의 PR과 같은지 먼저 대조한다(다르면 `<vstack>/skills/v-mode/SKILL.md` 고정 규칙 5대로 다시 묻는다). 그다음 아래 3(병합 관문 먼저. 기준 브랜치가 그사이 갔으면 2부터). |
| "병합됐어"(사람이 병합) | [vstack.md](vstack.md) "사람이 병합했을 때". `MERGED`면 아래 4부터. |
| "리뷰 반영해" | `gh pr view <PR> --comments`와 리뷰를 교차 검토 지적처럼 5단계로 판정해 고친다. 고친 뒤 [vstack.md](vstack.md) "대상이 바뀌면"대로 재검증하고, push하고, 무엇을 고쳤는지 PR에 댓글로 남긴다. |
| "그만둬" | [vstack.md](vstack.md) "그만둘 때". |

병합 방식이 `자동`이면 1부터 차례로 한다.

1. 브랜치를 push하고([vstack.md](vstack.md) "원격 반영") [pr-template.md](pr-template.md)로 PR을 만든다. GitHub 이슈면 본문에 `Closes #<n>`을 넣고, 다른 저장소면 이슈 위치를 적는다. PR 번호는 `gh pr create`가 출력한 URL에서 읽어 `state.md`에 적는다. 이슈 번호와 같다고 보지 않는다(이슈와 PR은 번호를 함께 쓴다).
2. `main`이 그사이 앞으로 갔으면, **원래 구현자**에게 `main` 위로 rebase하고 관련 테스트를 다시 돌리라고 맡긴다. 남겨 둔 구현자가 있으면 **보내기**하고, 닫혔으면 같은 worktree에 구현자와 **같은 계열**의 작업자를 새로 **띄우기**한다. 충돌 해결도 그 작업자가 한다([vstack.md](vstack.md) "rebase"). rebase 작업자는 레시피의 "구현자: rebase"를 따르고(작업 종류 `rebase`), 끝나면 [vstack.md](vstack.md) "대상이 바뀌면"대로 재검증한다. "main 변경" 안내는 **진행 중인 작업이 구현일 때만** **보내기**한다. 검토 중인 이슈는 그 검토가 끝난 뒤 다음 구현 지시에 rebase를 넣는다(검토자에게 rebase 안내를 보내지 않는다).
3. 맡기기의 반영(`<vstack>/skills/v-mode/delegate.md` "절차" 15)이 진행 중이면 그것이 끝난 뒤에 한다(반영과 병합은 한 번에 하나다). 관리자가 다른 세션인 맡기기도 기록으로 본다(delegate.md "다른 관리자의 기록"). [vstack.md](vstack.md) "병합 관문"을 한다. 관문을 통과해야만 `gh pr merge <PR> --<병합 방법> --match-head-commit <H> --subject "<제목> (<이슈 표시>)"`로 병합한다. `MERGED`를 확인한 뒤 원격 브랜치를 지운다. 병합 방법은 프로젝트 설정 "병합" 절(`merge`/`squash`/`rebase`, 없으면 `merge`)이다.
4. 기준 브랜치를 pull하고(위 "기준 브랜치"의 pull하는 곳), GitHub 이슈가 아니거나 기준 브랜치가 기본 브랜치가 아니면 이슈를 닫는다([trackers.md](trackers.md) "닫기". 기본 브랜치가 아닌 곳을 향한 PR의 `Closes`는 GitHub가 무시한다). 닫아야 1단계가 그 이슈를 다시 고르지 않고 뒤 이슈의 선행 조건이 풀린다. `state.md`를 `끝`으로 바꾼다.
5. 이 작업의 작업자들을 **정리**한다.
6. **병합한 worktree는 바로 지운다**(디스크 용량 확보: worktree마다 의존성 설치와 빌드 결과가 있어 크다). 지우기 전에 아래 셋과 [vstack.md](vstack.md) "worktree 지우기 전"(시도 정산)을 확인한다.
   - 병합됐다: PR이 `MERGED`이거나, 그 worktree의 `HEAD`가 `origin/main`에 들어 있다(`git merge-base --is-ancestor <HEAD> origin/main`). squash·rebase 병합은 앞쪽으로 판단한다.
   - 남은 변경이 없다: `git -C <worktree> status --porcelain`이 비었고, push하지 않은 커밋이 없다(`HEAD`가 `state.md` "게시" 절의 마지막 게시 SHA와 같다. [vstack.md](vstack.md) "worktree 지우기 전").
   - 그 worktree를 쓰는 작업자 터미널이 남아 있지 않다. 실행 환경 문서의 **정리**가 끝났는지로 본다(남아 있으면 먼저 **정리**한다. 해제를 증명하지 못한 터미널이 있으면 지우지 않는다).

   넷 다 맞으면 **worktree 지우기**를 한다. 병합된 로컬 브랜치도 지운다(지울 수 없으면 남기고 이유를 알린다. 실행 환경 문서 "worktree 지우기"). 하나라도 어긋나면 지우지 않고 사용자에게 이유를 알린다.
   - **앞부분만 병합하고 마무리를 같은 worktree에서 이어 갈 이슈**는 지우지 않는다. 마무리까지 병합한 뒤 지운다.
   - 관리자가 직접 쓰는 worktree(예: UI 다듬기)도 같은 규칙을 따른다. 병합 전에는 지우지 않는다.
   - 작업 파일(명세·검토 보고서·`state.md`)은 메인 저장소의 `.local/vstack/`에 있으므로 worktree를 지워도 남는다.
7. 바로 1단계로 가서 빈 자리를 채운다. 새로 풀린 이슈와 앞부분 작업을 확인한다. 7단계 보고를 기다리지 않는다.

**완료 기준**
- `자동`: 이슈가 닫혔고, `main`이 원격과 일치하고(병합 위치가 `로컬`이면 관문 기록이 `로컬 병합 확인`이고), 정리할 작업자가 0명이고, 병합한 worktree가 지워졌고, 1단계를 다시 실행했다.
- `지시`: 결과를 보고했고 `state.md`가 `지시 대기`다. 사용자의 지시를 받은 뒤에는 그 지시의 할 일을 끝냈다. 병합 확인 뒤에는 `자동`과 같다.

### 7. 보고하고 다음 묶음

사용자에게 이슈마다 결과(PR 링크 또는 지시 대기, 테스트 수, 검토 횟수와 주요 지적, 넘긴 지적, 시스템 변경)와 **사람이 직접 확인할 항목**을 모아 보고한다. 확인 자료가 있으면 그 위치를 안내한다. 자리 채우기는 6단계에서 이미 했으므로, 보고에는 지금 진행 중인 작업 목록과 지시를 기다리는 작업 목록을 덧붙인다. 화면 묶음의 구현 이슈가 모두 병합됐으면 [vstack.md](vstack.md) "UI 다듬기"대로 사용자에게 알린다(첫 버전에서는 [ui-polish.md](ui-polish.md)를 하지 않는다).

**완료 기준**: 이 지휘가 다룰 이슈(위 "기준 브랜치") 가운데 열린 맡길 이슈가 없거나, 사용자가 멈추라고 했다. 기준 브랜치가 기본 브랜치가 아니면 8단계로 간다.

### 8. 기준 브랜치를 기본 브랜치에 넣기

기준 브랜치가 기본 브랜치가 아닐 때만 한다(위 "기준 브랜치"). 병합 방식이 `자동`이어도 이 단계는 사용자 지시로만 한다. 여러 이슈를 한 번에 기본 브랜치로 옮기는 일이라 되돌리기 어렵다.

1. **알리기**: 이 지휘가 다룰 이슈가 모두 `끝`이고 진행 중인 작업이 없으면, 7단계 보고에 "`<기준 브랜치>`를 `<기본 브랜치>`에 넣을 준비가 됐다"고 적고 지시를 기다린다. 넣지 않은 이슈가 남았는데 사용자가 먼저 넣으라고 하면 남은 이슈를 알리고 확인받는다.
2. **"PR 올려"**:
   - 병합 위치가 `로컬`이고 `origin/<기준 브랜치>`가 이미 있으면(사용자가 따로 올렸다) 그것이 로컬 기준 브랜치의 조상인지 본다. 아니면 push하지 않고 사용자에게 알린다.
   - `git fetch origin`. 기준 브랜치가 체크아웃된 곳에 커밋되지 않은 변경이 있으면 멈추고 사용자에게 알린다. `origin/<기본 브랜치>`가 기준 브랜치의 조상이 아니면(그사이 기본 브랜치가 움직였다) 기준 브랜치가 체크아웃된 곳에서 `git merge --no-ff origin/<기본 브랜치>`로 받는다. 충돌이 나면 `git merge --abort`로 되돌리고 사용자에게 알린다. 관리자는 충돌을 풀지 않는다(ADR 0010). 사용자가 정한다: 작업자에게 맡긴다(같은 worktree에서 레시피의 "구현자: rebase"처럼 충돌만 푼다), 사용자가 직접 푼다.
   - 전체 테스트({설정: 테스트}의 전체 명령)를 기준 브랜치가 체크아웃된 곳에서 돌린다. 이슈마다 관련 테스트만 돌렸으므로 여기가 전체 테스트를 돌리는 자리다. 실패하면 PR을 올리지 않고 사용자에게 알린다.
   - 기준 브랜치를 push하고(사용자 지시이므로 vstack.md "원격 반영"의 기준 브랜치 금지에 대한 예외다) `gh pr create --base <기본 브랜치> --head <기준 브랜치>`로 PR을 연다. 본문에는 들어간 이슈와 그 PR 목록(병합 위치가 `로컬`이면 이슈마다 `H`, 병합 커밋 `M`, 관문 기록 한 줄, 검토 결론. 이슈는 4단계에서 이미 닫혔다)과 전체 테스트 결과(명령, 커밋, 결과)를 적는다. 전체 테스트를 돌린 커밋을 `T`로 적어 둔다.
3. **"병합해"**: 병합 관문(G1~G5)은 이슈마다 이미 거쳤으므로 다시 하지 않고 셋만 본다. `--match-head-commit`은 head만 지키고 base는 지키지 않으므로 기본 브랜치는 따로 본다. PR head가 `T`와 같다, 지금 원격의 기본 브랜치 tip(이 확인 바로 전에 `git fetch origin <기본 브랜치>`로 다시 받는다. 2에서 받은 값을 쓰지 않는다)이 `T`의 조상이다(아니면 2부터 다시: 기본 브랜치를 받고 전체 테스트를 다시 돌린다), 전체 테스트가 `T`에서 통과했다. 맞으면 `gh pr merge <PR> --<병합 방법> --match-head-commit <T>`. 병합 방법은 프로젝트 설정 "병합" 절이다. `squash`면 기준 브랜치의 이슈 커밋들이 하나로 합쳐진다고 미리 알린다. 사람이 직접 병합했으면 head가 `T`와 같은지만 사후에 보고한다.
4. **정리**: `MERGED`를 확인한 뒤 기본 브랜치를 pull하고, 기준 브랜치의 worktree와 브랜치(로컬, 원격)를 지울지 사용자에게 묻는다.

**완료 기준**: PR이 `MERGED`이고, 정리를 사용자가 정한 대로 했다. 또는 사용자가 넣지 않기로 했다.
