# 관리자는 관리만: 동작이 바뀌는 일은 모두 작업자에게

0.13.0에서 한 세션 갈래의 `bug-fix`와 `feature`를 작업자에게 맡기게 했다([design.md](design.md) 13절). 이 계획은 남은 "이 대화가 직접 하는 길"을 없앤다. 한 세션 일은 모두 작업자가 하고, 관리자는 맡기고·답하고·검토를 맡기고·확인만 한다.

이 문서는 계획이다. 사용자가 2026-11-14에 승인했다(정렬 `grill-with-docs` 뒤 "추천대로"). 그날 정한 용어는 저장소 루트의 [GLOSSARY.md](../GLOSSARY.md), 되돌리기 어려운 결정은 [adr/](adr/)에 있다. 이 계획이 "한 세션"이라고 부른 갈래는 용어집에서 **맡기기**다. 아래 "지금(0.13.0)" 칸은 옛 이름을 그대로 쓴다.

## 사용자 결정(2026-11-13)

1. `refactoring`, `ui-polish`, 레시피 없는 일도 작업자에게 맡긴다. 관리자는 관리만 한다.
2. Orca가 없는 환경에서는 쓰지 않는다. Orca 없이 맡기는 수단은 만들지 않는다.
3. "맡기기는 한 번에 하나" 제약을 푼다.
4. `ui-polish`를 작업자용으로 고친다.
5. agent-orchestra 제거와 아카이브는 vstack이 완성된 뒤에 한다(이 계획의 범위 밖). 완성의 기준은 [ADR 0001](adr/0001-move-agent-orchestra-into-vstack.md).

## 사용자 결정(2026-11-14, 정렬)

6. 갈래 이름을 **바로 / 맡기기 / 지휘**로 바꾼다. "한 세션"은 피할 말이다. 크기의 뜻(한 단위의 일, 티켓으로 나누지 않는다)은 "맡기기"의 정의로 옮긴다.
7. 맡기기와 지휘는 티켓과 계약이 필요한가로 나누고, 합치지 않는다([ADR 0011](adr/0011-delegation-and-orchestration-boundary.md)).
8. 관리자가 하는 것은 갈래 고르기, 명세, 답하기, 수용 기준을 다시 돌려 확인하기, 반영, 보고, 그리고 바로 갈래다. 하지 않는 것은 제품 코드 쓰기, 검증 수단 만들기, 충돌 풀기다. vstack 자신의 문서 수정은 바로 갈래다.
9. 바로 갈래의 경계는 **동작이 바뀌는가**다. 오타·문구·주석·문서처럼 동작이 바뀌지 않는 수정만 바로 한다. 동작이 바뀌는 수정은 한 줄이어도 맡긴다([ADR 0010](adr/0010-manager-writes-no-product-code.md)).
10. 역할 이름을 맞춘다: Orca가 띄운 에이전트 세션은 **작업자**, 작업자의 역할은 **구현자**와 **검토자**, 관리자나 구현자 안에서 띄우는 읽기 전용 조사는 **서브에이전트**다. "구현 작업자"는 피할 말이다.
11. 조사 에이전트 `vstack:explorer`를 더한다(위 "바뀌는 것" 4).
12. `ui-polish@3`은 병합 전에 `my-video-manager`의 작은 화면 하나로 시범한다(아래 "시범 B").
13. 이 계획을 병합한 뒤 전체 검수를 하고, pstack에서 더 가져올 것은 그 검수 안에서 원문으로 확정한 뒤 하나씩 가져온다.
14. 결정 기록은 `docs/adr/`에 번호를 붙여 둔다. `docs/design.md`의 결정 표는 요약이고 ADR이 우선한다.

## 원칙

- 맡기기 갈래의 일은 모두 작업자가 한다. 관리자(사용자가 `/vstack:v-mode`를 실행한 대화)는 제품 코드를 쓰지 않는다. 검증 수단을 만드는 일도 작업자가 한다.
- 바로 갈래(읽기 전용 질문·조사, 동작이 바뀌지 않는 수정)는 이 대화가 한다. 지금 라우터의 "한두 줄의 자명한 수정"은 "동작이 바뀌지 않는 수정"으로 좁힌다.
- 맡기려면 Orca가 있어야 한다.
- 한 저장소의 관리자는 지금처럼 하나다. 지휘는 바꾸지 않는다.

이유: 0.13.0의 근거는 "쓴 쪽과 확인하는 쪽이 다르다"였다. 직접 하는 길이 남아 있으면 그 근거가 일부 작업에서만 성립한다. 첫 `ui-polish` 실사용에서 어긋난 것 둘(비교 화면이 다른 채로 커밋, 판정 규칙을 결과를 본 뒤에 바꿈)도 코드를 쓴 대화가 자기 결과를 스스로 통과시킨 경우였다.

### 2. 맡기기 절차(`skills/v-mode/delegate.md`와 명세 양식)

**입력과 절차 범위를 옮긴다.** v-mode "레시피 직접 따르기"의 1(레시피별 입력)과 2(레시피의 어느 단계를 따르는가)를 `delegate.md`로 옮긴다. `delegate.md`의 절차 1과 `delegate-spec.md`의 "따를 절차"가 그 절을 가리키던 문장도 함께 고친다.

**레시피 없는 일.** 구현 명세의 "따를 절차"에 레시피 대신 "레시피 없음"을 적는다. 작업자는 수용 기준, 범위 밖, 건드리지 말 곳, 후보 원칙(v-mode "후보 원칙"에서 관리자가 고른 것)만 따른다. "맡겨도 되는 일인가" 3(수용 기준과 검증 명령을 정할 수 있다)은 그대로 적용한다. 검토는 같은 검토 명세를 쓴다.

**검증 수단이 없을 때.** 요구 동작을 검증할 수단이 없으면(고정 규칙 7) 그 수단을 만드는 일을 **먼저 따로 맡긴다**(레시피 없는 일). 작업자가 `create-verification-skill`을 따르거나, 프로젝트에 verify 스킬이 이미 있으면 그 스킬과 스크립트에 시나리오를 더한다. 수용 기준은 만든 것이 실제로 돌고(시작 커밋에서 기대한 결과를 낸다) 산출물을 남기는 것이다. 그 결과를 사용자가 정한 방법으로 기준 브랜치에 반영한 뒤에 제품 변경을 맡긴다. `ui-polish`의 임시 촬영 수단(레시피가 OS 임시 폴더에 두라고 한 것)은 지금처럼 그 맡기기 안에서 만든다.

**`refactoring`.** 기본값을 바꾸고, 양식에 다음을 넣는다.

- 구현 명세: 원래 동작 기준 `S`, 고정 명령(pin), 목표 구조, 전환 방식, 영향 범위, scratch 사본에 넣을 입력(Git이 무시하는 파일의 출처).
- 완료 보고: 고정 확정 커밋 `P`, 고정이 코드를 지나가는지 본 결과(scratch에서 코드를 틀리게 바꿔 본 결과), 원래 동작 기준에서 고정을 돌린 결과, 더한 고정 테스트.
- 검토 명세: 위 값들을 그대로 넘긴다.

**맡길 수 없을 때.** "맡겨도 되는 일인가"(위험, 여러 단위, 수용 기준 없음)의 판정은 지금 그대로다. "지금 맡길 수 있는가"는 조건별로 이렇게 한다.

| 조건이 안 맞음 | 할 일 |
| --- | --- |
| Orca가 아니다 | "한 세션 일은 Orca에서 v-mode를 실행해야 한다"고 알리고 끝낸다 |
| 이 저장소에 진행 중인 지휘 작업이 있다 | 지휘가 끝난 뒤에 하거나, 그 작업에 속한 일이면 지휘 절차로 보낸다고 알린다 |
| 맡길 기준이 정해지지 않는다(필요한 변경이 커밋되지 않음 등) | 사용자에게 묻는다: 기준 브랜치에 먼저 커밋한다, 그것이 있는 브랜치를 기준으로 삼는다, 기다린다 |
| 준비할 수 없다(검증 명령이 쓰는 환경 파일을 둘 수 없다 등) | 사용자에게 묻는다: 준비한 뒤 다시 한다, 사용자가 그 검증을 수용 기준에서 빼기로 정한다, 기다리거나 그만둔다 |
| 진행 중인 맡기기와 겹친다(아래 "여러 맡기기") | 그 맡기기가 끝난 뒤에 맡긴다고 알린다 |
| 시작 실패 뒤 다시 띄우지 않기로 했다 | 기다리거나 그만둔다(`끝(중단)`). "이 대화에서 직접 할지 묻는다"를 지운다 |

어느 칸에도 "직접 한다"는 선택지를 두지 않는다.

**여러 맡기기.** "맡기기는 한 번에 하나"를 푼다.

- 기록, worktree, 작업자는 지금도 맡기기마다 따로다(`.local/vstack-delegate/<이름>/`). 이름은 지금처럼 끝난 기록과도 겹치지 않게 한다.
- **Run은 관리자 세션 하나에 하나를 쓴다.** 같은 저장소에 진행 중인 맡기기가 있으면 새 Run을 만들지 않고 그 기록의 Run을 쓴다. Orca의 `run-use`는 이름을 준 Run 하나만 남기기 때문에(`orca skills get orchestration --reference references/coordinator-loop.md` "Several Runs"), 맡기기마다 Run이 다르면 관리자가 다시 시작했을 때 하나밖에 이어받지 못한다. 맡기기는 그 Run 안에서 Task와 Dispatch로 가린다. Run을 받는 명령에는 지금처럼 `--run`을 붙인다.
- **서로 독립인 요청만 함께 맡긴다.** 맡기기 전(예약할 때)에 두 가지를 본다.
  - 쓰는 곳: 새 일의 **예정 쓰기 영역**이 진행 중인 맡기기의 예정 쓰기 영역(그 명세의 할 일, seam, 쓰기 범위)과 겹치는가. 비교하는 것은 두 쓰기 영역의 교집합이다. "건드리지 말 곳"은 겹침 판정에 쓰지 않는다. 그것은 그 작업자가 범위를 지켰는지 볼 때 쓴다. 지금까지 커밋된 변경 파일은 참고로만 본다(아직 커밋되지 않은 작업은 거기에 없다).
  - 검증이 쓰는 자원: 검증 명령이 포트, DB, 데이터 폴더, 브라우저 프로필 같은 것을 함께 쓰는가. worktree가 달라도 이것들은 나뉘지 않는다. 맡기기마다 나눌 수 있으면(임시 데이터 파일, 다른 포트) 명세에 그렇게 적는다.
  - 겹치거나 나눌 수 없으면 그 맡기기가 끝난 뒤에 맡긴다.
- **범위가 넓어질 때 다시 본다.** 범위를 넓히는 질문에 답하기 전, 후속 요구를 보내기 전, `ui-polish`의 항목을 확정하기 전, 기준을 맞추는 일을 보내기 전에 위 확인을 다시 한다. 겹치게 되면 넓히지 않고 사용자에게 알린다.
- 한 요청을 여러 개로 쪼개 동시에 맡기지 않는다. 여러 단위로 나눠야 하는 일은 지금처럼 지휘다.
- **동시에 셋까지**다. 검증된 값이 아니다. 시범은 둘만 본다.
- **깨우는 메시지의 주인을 가린다.** 작업자의 보고와 질문은 Dispatch로 어느 기록의 것인지 가린다. 어느 기록의 Dispatch 이력에도 없는 메시지는 처리하지 않고 사용자에게 알린다.
- **사용자의 말이 어느 맡기기의 것인지 가린다.** 이름, 브랜치, 하는 일로 가리고, 가릴 수 없으면 묻는다. "병합해"처럼 되돌리기 어려운 지시는 어느 맡기기인지 이름으로 확인한다.
- 관리자가 다시 시작했을 때: 그 Run 하나에 `run-use`를 하고, 진행 중인 기록마다 지금 절차를 따른다.

**반영(절차 15 "끝낸다")을 고친다.** 지금 절차는 병합한 뒤 수용 기준이 실패하는 경우와, 기준 브랜치가 움직인 경우를 다루지 않는다.

- **기준 브랜치에 반영하는 일은 한 번에 하나만 한다.** 한 맡기기의 반영이 끝나기 전(아래 실패 처리 포함)에는 다른 맡기기를 반영하지 않는다.
- **반영 전에 기준을 본다.** 견주는 것은 최초 기준 `B`가 아니라 **현재 확인 기준 `C`**다(아래 "기준을 둘로 나눠 적는다". 기준을 맞춘 적이 없으면 `C`=`B`). 기준 브랜치의 지금 SHA(tip)와 `C`를 견주고, 견준 tip SHA와 실제로 반영에 쓴 tip SHA를 기록한다.
  - tip이 `C`와 같으면 지금 절차대로다.
  - tip이 `C`와 다르고 `C`의 자손도 아니면(되돌려졌거나 다른 계통으로 갈라졌다) 반영하지 않고 사용자에게 알린다.
  - tip이 `C`의 자손이면(다른 것이 먼저 반영됐다) **먼저 작업 유형을 가린다.** `ui-polish`면 충돌이 있든 없든 아래 3의 "기준이 움직였을 때"로 간다. 아래 두 줄은 `ui-polish`에 쓰지 않는다.
  - 그 밖의 일이면 `git merge-tree --write-tree <기준 브랜치> <작업 브랜치>`로 충돌이 나는지 본다. 이 명령은 작업 폴더를 건드리지 않는다. 관리자의 기준 checkout에서 실제 병합을 시도해 충돌을 남기지 않는다. 충돌이 없으면 사용자에게 "기준이 움직였고 충돌은 없다"를 알리고, 사용자가 정한 방법으로 반영한다.
  - 충돌이 있으면 관리자가 풀지 않는다. 구현 작업자에게 **기준을 맞추는 일**을 "보내기"로 맡긴다(아래).
- **기준을 맞추는 일.** `bug-fix`·`feature`·`refactoring`이면 그 레시피의 `rebase` 절차를 따르게 한다. 빼는 것은 계약의 증거 폴더, manifest, 계약 보고 양식뿐이다. **rebase한 마지막 HEAD에서 필수 수용 기준을 모두 다시 돌리는 단계는 남긴다**(새 빌드와 새 서버로). 그 결과는 맡기기의 완료 보고에 싣는다. 레시피가 없으면 `git rebase <기준 브랜치>` 뒤 수용 기준을 모두 다시 돌리게 한다. `ui-polish`는 아래 3의 "기준이 움직였을 때"를 따른다(rebase하지 않는다). 작업자의 권한에 "이 worktree의 작업 브랜치를 기준 브랜치 위로 rebase한다"를 이 후속 지시에 한해 더한다. 원격에 올린 브랜치면 force-push가 따르므로 v-mode 고정 규칙 5대로 사용자 확인을 받는다.
  - **기준을 둘로 나눠 적는다.** 처음 맡길 때의 `B`(최초 기준)는 이력으로 남긴다. **현재 확인 기준 `C`**를 따로 둔다. 처음에는 `C`=`B`이고, 기준을 맞출 때마다 `C`를 새 기준 SHA로 바꾼다. 구현 확인(절차 8)과 마지막 확인(절차 14), 검토가 "이 맡기기의 변경"으로 읽는 범위는 `C..H`다. `B..H`로 읽으면 다른 맡기기가 기준에 넣은 변경까지 이 작업자의 변경(건드리지 말 곳 위반 포함)으로 보게 된다.
  - `refactoring`의 역할: 관리자가 후속 지시에 옛 `S`와 옛 `P`, 새 원래 동작 기준(새 `C`)을 적는다. 그 기준에 대응하는 새 `P`는 작업자가 레시피대로 찾아 확인하고 보고한다. 관리자는 보고된 새 `P`를 기록에 적을 뿐, 스스로 정하지 않는다.
  - 그 뒤 구현 확인(절차 8)을 하고 재검토를 맡긴다. 재검토의 범위는 `git range-diff <직전 C>..<옛 H> <새 C>..<새 H>`와 `git diff <새 C>...<새 H>`다(지휘의 검토 양식이 rebase에 쓰는 범위와 같다). 두 번째로 기준을 맞출 때의 "직전 `C`"는 최초 `B`가 아니라 바로 앞의 `C`다. 재검토 상한에 센다.
- **반영한 뒤 기준 브랜치에서 수용 기준이 실패하면** `끝`으로 닫지 않는다. 실패한 통합 SHA와 명령·결과를 기록하고 `확인 실패`로 둔 뒤 사용자에게 알린다. 사용자가 정한다: 반영을 되돌린다, 구현 작업자에게 고치게 한다(작업 브랜치를 기준에 맞춘 뒤 고치고, 구현 확인과 재검토를 거쳐 다시 반영한다). 그동안 다른 맡기기의 반영은 멈춘다.
- 여러 맡기기를 반영한 뒤에는 그 맡기기들의 수용 기준을 모두 기준 브랜치에서 돌린다.

### 3. `ui-polish@3`(작업자용)

`ui-polish@2`는 "구현자는 이 대화이고 관리자는 사용자다"로 쓰였다. 바꾸는 것:

- **역할**: 구현자는 구현 작업자, 관리자는 관리자다. 사용자만 정할 수 있는 것(모양, 값, 문구)을 관리자가 대신 정하지 않는다. `recipes/FORMAT.md`의 "한 세션에서 구현자는 이 대화"라는 문장도 고친다.
- **묻는 것과 알리는 것을 나눈다.** 질문이 오가는 횟수를 줄이려는 것이다.
  - 답을 기다리는 것(`ask`): 항목 확정(아래), 값이나 문구를 사용자가 정해야 할 때, 필수 비교 화면이 찍히지 않거나 흔들릴 때, 첫 전·후에 눈에 띄는 부수 변화가 있을 때, 그 밖에 레시피가 "멈추고 묻는다"고 한 곳.
  - 답을 기다리지만 사용자에게 묻지 않는 것(`ask`, 관리자가 바로 답한다): 기준 인계(아래 "기준을 넘긴다").
  - 알리고 계속하는 것(orchestration `send --type status`): 시작 커밋과 작업 경로, 부수 변화가 없는 첫 전·후 한 쌍. 관리자가 사용자에게 전한다. 지금 레시피도 이 경우에는 답을 기다리지 않는다.
- **순서**: 항목이 정해져야 변경 범위와 화면 목록이 정해지고, 그래야 기준을 찍을 수 있다. 그래서 이렇게 한다.
  1. 요청이 이미 관찰 가능한 항목으로 정해져 있으면(사용자가 값과 문장을 줬다) 관리자가 명세의 수용 기준에 적고 3으로 간다. 다시 묻지 않는다.
  2. 아니면("더 깔끔하게") 작업자가 먼저 **관찰용 촬영**(`probe/`)만 한다. 지금 화면을 찍고 재서 항목 초안(지금 어떻게 보이는지 → 어떻게 보여야 하는지)을 `ask`로 보낸다. 이때까지 제품 파일을 고치지 않는다. 관리자가 사용자에게 사진과 초안을 보이고, 확정된 항목을 답으로 보낸다. 관리자는 확정 항목을 기록 폴더의 `spec.md` 수용 기준 표에 더하고(검토 명세도 그 표를 읽는다), 그 시각을 기록에 적는다.
  3. 작업자가 확정된 항목으로 레시피의 "새 다듬기" 1~4를 한다(변경이 닿는 곳, 시작점, 수단 준비와 확인, 기준 확정).
  4. **기준을 넘긴다.** 작업자가 기준을 확정하면("새 다듬기" 4) 제품 파일을 고치기 전에, 목록 파일과 `baseline/`의 경로, 촬영 수단의 설정을 `ask`로 관리자에게 보내고 기다린다. 관리자가 그 파일들을 직접 읽어 목록의 내용, `baseline/`의 파일 이름과 해시, 수단의 설정을 기록(`state.md`)에 적은 뒤 "기록했다"고 답한다. 사용자에게 묻는 답이 아니다. 작업자는 이 답을 받은 뒤에 "새 다듬기" 5를 시작한다. 이 기록이 뒤에 기준이나 목록이 바뀌었는지 대조하는 근거다.
  5. 뒤에 항목이 더해지거나 바뀌면(사용자의 추가 요구) 그 항목으로 범위를 다시 본다. 변경이 닿는 화면이 늘면 레시피대로 대상에 더하고 필요한 촬영을 다시 한다. 이미 확정한 기준 사진은 고치지 않는다. 목록이나 기준에 더한 것이 있으면 4를 다시 한다(관리자가 "승인된 변경"으로 기록에 더한다).
- **파일을 두는 곳**: 레시피가 정한 파일(`target.txt`·`keep.txt`·`keep-other.txt` 같은 목록, `probe/`, `baseline/`, 시도별 폴더, 다시 찍은 폴더, 기록)을 모두 메인 저장소 기본 checkout의 `.local/vstack-delegate/<이름>/shots/` 아래에 둔다. 파일 이름은 레시피의 것을 그대로 쓴다. 촬영마다 새 빈 폴더를 쓰는 규칙은 그대로다. 관리자와 검토자가 같은 파일을 본다. 임시 촬영 수단과 scratch는 지금처럼 OS 임시 폴더에 둔다.
  - 구현 명세의 권한에 "이 맡기기의 `shots/` 절대 경로에 쓴다"를 예외로 넣는다. 그 밖의 worktree 밖 쓰기는 지금처럼 금지다.
- **완료 보고**: 맡기기의 완료 보고에 레시피 "완료 보고"의 항목을 그대로 싣는다(끝의 결론, 항목마다 남김·미충족·사용자가 거둠, 픽셀 비교로 보존을 확인하지 못한 화면, 사람이 볼 것). `--outcome`은 결론이 "하지 못했다"면 `failed`, 그 밖("완료", "일부만 했다", "요청대로 되돌렸다")이면 `succeeded`이고 결론을 본문 첫 줄에 적는다. **`succeeded`는 모든 수용 기준이 통과했다는 뜻이 아니다.** 관리자는 결론을 읽고 아래처럼 한다.
- **일부만 했거나 사용자가 거둔 항목이 있을 때**: 지금 절차 8에 그대로 넣으면 미충족 항목이 확인 실패가 되어 작업자에게 되돌아간다. 레시피는 그 결정을 사용자에게 준다. 그래서:
  - 결론이 "일부만 했다"면 관리자는 구현 확인에서 미충족 항목을 실패로 치기 전에 사용자에게 묻는다: 남긴 것만 받는다, 미충족 항목을 더 시도하게 한다, 그만둔다.
  - 사용자가 항목을 거두거나 일부만 받기로 하면, 처음 요구는 지우지 않고 사건으로 기록에 남긴다. 그리고 **지금 유효한 수용 기준**을 `spec.md`의 표에 표시한다(항목마다 유효, 사용자가 거둠, 미충족으로 닫음). 검토 명세와 재검토 요청은 이 표를 넘긴다. 거둔 항목이 되돌려졌다는 것은 검토자가 "실패"가 아니라 "요청대로 되돌려짐"으로 본다.
  - 유효한 필수 기준을 모두 확인한 뒤에만 `확인 통과`로 간다. 사용자에게 알릴 때 닫은 항목과 그 이유를 함께 적는다.
- **기준이 움직였을 때**(다른 맡기기가 먼저 반영됐다): `ui-polish`에는 `rebase` 절차가 없고, 옛 기준에서 찍은 사진으로 새 기준을 통과시킬 수 없다. 그래서 rebase하지 않는다. 사용자에게 알리고 정하게 한다.
  - 새 기준에서 다시 맡긴다. 확정된 항목은 그대로 쓰고 수단 확인과 기준 사진은 새로 한다. 옛 브랜치, 사진, 기록은 남기고 옛 기록은 `끝(다시 맡김)`으로 닫는다.
  - 그대로 반영한다. 이 선택지는 `git merge-tree`로 본 충돌이 없고, 기준에 더해진 변경(`git diff --name-only <C>..<기준 브랜치>`)이 화면을 그리는 파일에 닿지 않는다고 사용자가 판단할 때만 고를 수 있다. 이때 결과 보고에 "새 기준에서 화면을 다시 확인하지 않았다"를 적는다.
  - 그만둔다.
  - 이 비용을 줄이려고, `ui-polish` 맡기기가 진행 중일 때 다른 맡기기를 반영하려 하면 관리자가 그 사실을 먼저 사용자에게 알린다(반영을 `ui-polish` 뒤로 미룰 수 있다).
- **실행 환경**: 화면을 띄우는 데 필요한 것(의존성, 환경 파일)은 새 worktree에 없다. `delegate.md` "맡기기 전에" 7을 그대로 쓴다. 의존성 설치는 명세의 "준비"에 적는다. 여러 맡기기가 같은 포트나 프로필을 쓰면 위 "여러 맡기기"의 자원 확인에 걸린다.
- **검토**: 검토 명세에 넘기는 것은 확정 항목(수용 기준 표), `keep.txt`와 `keep-other.txt`, 기준 폴더와 마지막 촬영 폴더, 마지막 촬영의 대상 SHA와 촬영 명령의 종료 코드, 관리자가 적어 둔 기준의 해시다. 검토자가 보는 것:
  1. diff가 동작, 데이터, 문구의 뜻을 바꾸지 않았는가.
  2. 항목의 관찰 가능한 문장(숫자, 상태)이 마지막 사진과 잰 값에서 성립하는가. 모양이 더 나은지(취향)는 판정하지 않는다. 그것은 사용자가 본다.
  3. `image_diff.py`를 `--expect keep.txt`로 다시 돌려 비교 화면이 기준과 같은가. `keep.txt`가 비어 있으면 이 비교는 건너뛰고 그렇게 적는다.
  4. `keep-other.txt`의 화면마다: 명령으로 하는 확인이면 다시 돌리고, 눈으로 하는 확인이면 사용자의 판정이 기록에 있는지 본다.
  5. 프로젝트의 기존 검사.
  6. 목록 파일의 내용, 기준 폴더의 파일 이름과 해시, 촬영 수단의 설정이 관리자가 적어 둔 것(승인된 변경 포함)과 같은가.
  - 한계: 검토자는 화면을 다시 찍지 않는다. 사진이 그 커밋에서 제대로 찍혔는지는 작업자의 촬영 기록(대상 SHA, 종료 코드)과 기준의 해시 대조까지만 본다. 보고서에 이 한계를 적는다.
- **마지막 확인**: 관리자가 항목마다 전·후 한 쌍을 사용자에게 보인다. 사용자가 거두겠다는 항목이 있으면 "보내기"로 되돌리게 하고, 구현 확인과 재검토를 거친다.
- 레시피 머리말의 "한 세션 갈래에서만 쓴다 … 구현자는 이 대화"를 "한 세션 갈래에서 작업자에게 맡긴다. 지휘에는 연결하지 않았다"로 고친다. 지휘에 연결하지 않는 것은 그대로다.

비용: 모든 `ui-polish` 맡기기에 기준 인계가 한 번 온다(관리자가 바로 답한다). 항목이 정해지지 않은 요청은 사용자에게 가는 질문이 적어도 한 번(항목 확정) 더 온다.

### 4. 조사 에이전트(`vstack:explorer`)

사용자 요청(2026-11-14)으로 더한다. 지금 `subagents.md`는 "Agent 도구의 `Explore`를 `model: sonnet`으로, 읽기 전용이라고 적어 띄워라"라고 한다. 부르는 쪽이 셋을 매번 기억해야 한다. 플러그인에 에이전트를 정의해 두면 모델과 도구가 정의에 고정되고, 사용자가 다른 세션에서 직접 쓸 때도 같은 설정으로 뜬다.

- **파일**: 플러그인의 `agents/explorer.md`. Claude Code에서는 `vstack:explorer`로 부른다(이름 형식은 만들 때 확인한다).
- **정의**: 모델 `sonnet`, 도구 `Read`·`Grep`·`Glob`만. `Bash`는 주지 않는다. `Bash`로는 파일을 쓸 수 있어서 읽기 전용이 다시 지시에 기대게 된다. git 이력 조사는 부른 쪽이 직접 한다.
- **본문 규칙**(지금 `subagents.md`의 "요청문"과 "답을 다루는 법"을 옮긴다): 읽기 전용, 사실마다 파일과 줄, 판단하지 않고 자료만 모은다, 이미 배제한 것은 다시 보지 않는다.
- **설명**(pstack `poteto-agent`의 방식): 쓸 때와 쓰지 않을 때를 설명에 적는다. 쓸 때는 넓게 훑기·서로 독립인 조사 여러 개·긴 출력 요약. 쓰지 않을 때는 어디를 볼지 알 때·코드 쓰기·검토·판단. "새 조사마다 새로 띄운다"도 적는다. 부르는 쪽이 설명만 보고 고를 수 있게 하려는 것이다.
- **`subagents.md`**: "무엇을 쓰는가"를 `vstack:explorer`로 바꾸고, 정의에 옮긴 규칙은 정의를 가리키게 줄인다. 적용 대상(한 세션 갈래의 Claude, 계약 작업자 제외)은 그대로다.
- **확인**: 브랜치 사본을 `claude -p --plugin-dir <worktree>`로 띄워 이 에이전트가 목록에 나오고, 정한 모델로 돌고, 편집 도구가 없는지 본다. Orca 구현 작업자가 이 에이전트를 부를 수 있는지는 시범 A에서 작업자가 부르면 관측한다. 부르지 않으면 "보지 못했다"로 적는다.
- **출처**: 정의는 vstack이 새로 쓴다(`own`). pstack에서 가져온 것은 설명에 쓸 때와 쓰지 않을 때를 적는 방식이고, `UPSTREAM.md`에 적는다. mattpocock-skills 1.3.1에는 에이전트 정의가 없다(설치본에서 확인). 겹치지 않는다.
- 만들지 않는 것: 구현 에이전트(Orca 작업자가 한다), 검토 에이전트(Codex가 한다. 같은 계열 검토는 교차 검토가 아니다).

4. 쓰는 곳이 겹치거나 검증 자원을 나눌 수 없는 두 일은 함께 맡기지 않는다.
5. 검증 수단을 만드는 일은 따로 먼저 맡긴다.
6. 기준이 움직였을 때 관리자는 `git merge-tree`로 충돌만 보고, 충돌은 작업자가 rebase로 푼다. `ui-polish`는 예외다. rebase하지 않고 사용자에게 묻는다.
7. `ui-polish`의 검토자는 화면을 다시 찍지 않는다.
8. 전체 검수는 이 변경을 병합한 뒤에 한다. 정해진 모습을 한 번만 훑으려는 것이다.

## 하지 않는 것

- 지휘(계약, 관문, 작업자 종류, 지휘와 맡기기의 상호 배제)를 바꾸는 것.
- Orca 없이 맡기는 수단.
- `ui-polish`를 지휘에 연결하는 것.
- 맡기기에 계약(증거 폴더, manifest)을 붙이는 것.
- 검증만 차례로 돌리게 하는 장치. 자원을 나눌 수 없으면 맡기기를 기다리게 한다.
- agent-orchestra 제거와 아카이브.
