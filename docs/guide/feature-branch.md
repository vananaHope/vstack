# 기능 브랜치에서 지휘하기

기본 브랜치에서 기능 worktree를 하나 만들고 그 안에서 지휘를 시작하면, 그 기능 브랜치가 이 지휘의 기준 브랜치가 된다. 작업 worktree는 기준 브랜치에서 뻗고, 이슈는 기준 브랜치에 모이고, 마지막에 기준 브랜치→기본 브랜치 PR 하나로 기본 브랜치에 넣는다. 기능마다 이렇게 따로 지휘할 수 있다([ADR 0015](../adr/0015-base-branch-per-orchestration.md), [ADR 0016](../adr/0016-local-merge-orchestration.md)).

1. 프로젝트 설정 "병합" 절에 병합 위치를 적는다. `로컬`이면 이슈마다 PR을 만들지 않고 관리자가 기준 브랜치에 로컬로 병합하며, 원격은 마지막 PR에서만 쓴다. 비우면 `원격`(이슈마다 PR을 열어 원격 기준 브랜치로 병합)이고, 그때는 기준 브랜치를 먼저 원격에 올려 둬야 한다.

   ```
   ## 병합

   - 기본 브랜치: main
   - 병합 방식: 자동
   - 병합 방법: squash
   - 병합 위치: 로컬
   ```

2. 기본 브랜치에서 기능 worktree를 만들고 그 안에서 Claude Code를 연다.

   ```
   git worktree add ../myapp-feature-a -b feature-a main
   cd ../myapp-feature-a
   claude
   ```

3. `/vstack:v-mode`로 다룰 이슈를 좁혀 지휘를 맡긴다(예: "#12, #13, #14 지휘해"). 기준 브랜치가 기본 브랜치가 아니면 다룰 이슈를 번호·마일스톤·라벨로 정해야 하고, 정하지 않으면 v-mode가 묻는다. 갈래 줄에 기준 브랜치와 관리자 작업 트리가 나온다.
4. 지휘는 이슈마다 병합 관문(G1~G5)을 거쳐 기준 브랜치에 병합하고, 이슈를 직접 닫는다. GitHub는 기본 브랜치로 병합한 PR에서만 `Closes #<n>`으로 이슈를 닫기 때문이다. 같은 기능 worktree에서 맡기기를 하면 그 결과도 기준 브랜치로 간다.
5. 다룰 이슈가 모두 끝나면 지휘가 "기준 브랜치를 기본 브랜치에 넣을 준비가 됐다"고 알리고 멈춘다. 넣으라고 하면 기본 브랜치를 기준 브랜치에 합치고, 전체 테스트를 돌린 뒤 기준 브랜치를 push해 기준 브랜치→기본 브랜치 PR을 연다. 병합 방식이 `자동`이어도 이 단계는 지시로만 한다.
6. 그 PR은 "병합해"로 지휘에 맡기거나, GitHub나 `gh pr merge`로 직접 병합한다. 직접 병합하면 지휘는 PR head가 전체 테스트를 돌린 커밋과 같은지만 사후에 알린다.

`로컬`이면 이슈마다의 PR 기록, PR에서 받는 사람의 리뷰, 이슈마다 도는 원격 검사, 진행 중인 작업의 원격 백업이 없다. 대신 병합 커밋 메시지와 마지막 PR 본문에 이슈마다의 검증 기록이 모이고, 사람의 리뷰는 마지막 PR에서 한 번 받는다. 기준 브랜치에 사용자가 직접 커밋하면 지휘가 새 작업을 시작하기 전에 알리고 멈춘다. 기능 worktree를 여러 개 두고 따로 지휘해도 되고, 그때 서로 다른 기준 브랜치의 작업끼리는 검증 자원(포트, DB 등)만 견준다.

개념은 [concepts.md](concepts.md) "장소", 지휘 전체 흐름은 [orchestrate.md](orchestrate.md)에 있다. 절차의 정본은 [orchestrate-issues](../../skills/orchestrate-issues/SKILL.md)의 "기준 브랜치"와 8단계다.
