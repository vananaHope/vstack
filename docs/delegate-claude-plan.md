# 맡기기 바꾸기 계획: omp를 빼고 Claude 작업자와 Codex 검토로

> 지난 계획(0.13.0)이다. 2026-11-14에 "관리자는 관리만"으로 바뀌어, 아래의 "이 대화가 직접 한다" 갈래(`ui-polish`, 레시피 없는 일, Orca가 없는 환경)는 없어졌다. 지금 규칙은 [design.md](design.md) 14절과 [manager-only-plan.md](manager-only-plan.md).

한 세션 갈래의 "omp에 맡기기"([design.md](design.md) 12절, 정본 `skills/v-mode/delegate-omp.md`)를 바꾼다. omp를 쓰지 않는다. 한 세션 일은 Claude 작업자가 구현하고, Codex 작업자가 교차 검토하고, Claude 관리자가 마지막에 확인한다. 한 세션에서 서브에이전트를 쓰는 지침도 함께 둔다.

이 문서는 계획이다. 사용자가 2026-11-13에 승인했다. 시범 결과는 [pilot-delegate.md](pilot-delegate.md), 반영된 결정은 [design.md](design.md) 13절에 있다. 계획과 다르게 한 것: `ui-polish@2` 병합을 기다리지 않고 겹치지 않는 새 파일 넷을 먼저 썼고, 병합(PR #17) 뒤에 나머지를 연결했다.

## 사용자 결정(2026-11-13)

1. omp를 쓰지 않는다. 작업자로도, v-mode를 돌리는 도구로도 쓰지 않는다.
2. 간단한 일은 지금처럼 이 대화가 바로 한다("바로" 갈래).
3. 한 세션 일은 관리자가 직접 하지 않고 작업자에게 맡긴다. 구현은 Claude Opus 작업자가 한다.
4. 교차 검토는 Codex가 한다. Orca 작업자로 띄운다.
5. 마지막 결과는 Claude 관리자(사용자가 `/vstack:v-mode`를 실행한 대화)가 확인한다.
6. 서브에이전트를 쓰는 지침을 둔다. 서브에이전트 모델은 Sonnet이다.

## 왜 바꾸는가

- 맡기기의 이점(쓴 쪽과 확인하는 쪽이 다르다, 관리자 대화가 가볍다, 새 worktree로 격리된다)은 omp가 아니라 작업자에서 나온다.
- omp 작업자는 구현을 Claude 계열로 하고 다른 계열 검토를 자기 안에서 받았다. 관리자는 검토 결과를 요약 보고로만 봤다. 새 구조에서는 관리자가 Codex의 검토 보고서를 직접 읽는다.
- omp는 의존 도구가 하나 더 든다. 2026-11-12에는 이 PC의 OS 보안 정책이 omp 네이티브 모듈을 막아 하루 동안 맡기기를 못 썼다. Orca는 omp의 턴 시작을 관측하지 못한다(`turnStart: unsupported`). Claude와 Codex는 지휘에서 이미 쓴다.

잃는 것: omp 설정(`modelRoles`, fallback)으로 모델을 고르고 한도가 떨어지면 넘어가는 것, omp로 돌린 시범 세 번의 검증. 관리자와 작업자가 모두 Claude라서 Claude 한도를 더 쓴다.

| 바로 | 이 대화. 지금과 같다 |
| 한 세션, 레시피 있음 | 관리자가 명세 → Claude 작업자가 새 worktree에서 구현 → Codex 작업자가 검토 → 관리자가 마지막 확인 |

맡기기는 지금처럼 **계약 밖**이다. 증거 폴더, manifest, 시도 정산, 병합 관문이 없다. Codex 검토는 계약의 교차 검토(`rev` 시도)가 아니다. 여러 단위의 일이거나 관문이 필요하면 지금처럼 지휘를 권한다. 지휘와의 경계는 작업자 수가 아니라 계약이다.

### 기본값

- `bug-fix`, `feature`: 조건이 맞으면 맡긴다.
- `refactoring`: 직접 하는 것이 기본이다. 사용자가 맡기라고 하면 "돌려 보지 않았다"를 알리고 맡긴다. 한 번 맡겨 본 뒤 기본값을 올린다.
- 사용자가 "여기서 해"나 "맡겨"라고 하면 그 말을 따른다. 맡기려면 조건은 그대로 맞아야 한다.

검증 범위는 구조별로 나눠 적는다. 이 계획의 시범이 끝나면 "새 구조: `bug-fix` 한 번. `feature`는 omp 구조에서만 돌려 봤다"가 된다.

### 구현 확인부터 마지막 확인까지

두 작업자가 같은 worktree를 쓴다. 그래서 **한 역할을 깨우기 전에 다른 역할의 마지막 Dispatch가 끝났는지**(`worker-show`의 `state`)를 본다. 구현 작업자와 검토자의 마지막 Task·Dispatch는 기록에 따로 적는다. 끝난 작업자를 다시 쓸 때는 그 작업자의 마지막 Dispatch에 "보내기"를 하고, 결과의 새 Dispatch를 기록한다(backends/orca.md "보내기"). 작업자 터미널의 해제("정리")는 검토 시작의 조건이 아니다. 지금처럼 "끝낸다"에서 한다.

**구현 확인**은 지금 절차 8의 검사 항목이다: 구현 Dispatch가 끝났는가, 보고한 HEAD가 실제 HEAD인가, 작업 트리가 깨끗한가, 건드리지 말 곳이 그대로인가, 수용 기준 명령을 직접 다시 돌린 결과, 다시 돌린 뒤 HEAD와 status가 그대로인가. 결과는 확인 기록에 HEAD와 함께 적는다. 구현 확인의 통과는 상태 `확인 통과`가 아니다.

1. **구현 확인.** 구현 작업자의 `worker_done`을 받을 때마다 한다.
   - 실패: 상태를 `확인 실패`로 적고 사용자에게 알린 뒤 5로 간다(검토로 보내지 않는다).
   - 명령을 돌릴 수 없거나 무결성을 판정할 수 없음: `확인 필요`로 두고 사용자에게 알린다.
   - 통과: 쓸 수 있는 첫 검토 결과를 아직 받지 않았으면 2로, 받았으면 6으로 간다. 첫 구현의 확인이 실패해 고친 경우도 검토를 받은 적이 없으므로 2로 간다.
2. **첫 검토를 맡긴다.** 검토할 HEAD `H`와 그때의 `git status`를 기록한다. 검토 명세(아래)를 쓴 뒤 같은 worktree에 Codex 작업자를 새로 띄운다: `worker-start --spec-file <검토 명세> --worktree path:<worktree> --agent codex --run <run>`. 모델 옵션은 주지 않는다(Codex 설정의 기본값). 상태를 `검토 중`으로 바꾼다.
3. **검토 결과를 받는다.** 검토자의 `worker_done`을 받으면 그 Dispatch가 끝났는지 본다. 지금 HEAD와 `git status`가 검토를 맡길 때 적어 둔 것과 같은지 대조한다. 다르면 그 검토 결과를 쓰지 않고 `확인 필요`로 둔 뒤 사용자에게 알린다. 같으면 보고서를 읽고 검토 이력 표에 적는다.
   - **재검토 상한**: 재검토는 두 번까지다. 사용자의 추가 요구 때문에 맡긴 재검토도 센다. 두 번째 재검토의 결론도 `수정 필요`면 4로 가지 않는다. `확인 필요`로 두고 사용자에게 묻는다(더 돌린다, 지휘로 넘긴다, 그만둔다).
4. **지적을 판정한다.** 지적마다 `지금 고침` 또는 `안 고침(이유)`을 기록에 적는다. 차단·중요 지적을 고치지 않으려면 사용자에게 이유를 알리고 확인받는다. 사소한 지적은 관리자가 정한다. 고칠 것이 없으면 7로 간다.
5. **고치게 한다.** 고칠 것(확인 실패, `지금 고침` 지적, 사용자의 추가 요구)을 구현 작업자에게 "보내기"로 보낸다. 규칙은 처음 명세 그대로라고 적는다. 범위를 넓히는 요구면 무엇이 달라지는지와 새 수용 기준을 함께 적는다. 상태를 `배정됨`으로 바꾼다. 완료 보고를 받으면 1로 간다.
6. **수정 뒤 갈림.** 검토를 받은 뒤의 수정이다. 여기서 "이전 `H`"는 검토자가 마지막으로 본 HEAD다.
   - 이전 `H` 뒤에 고친 것이 사소한 검토 지적뿐이면 재검토하지 않는다. 관리자가 `git diff <이전 H>..<새 H>`를 직접 읽고 7로 간다.
   - 그 밖의 수정(차단·중요 지적, 검토 뒤에 난 확인 실패의 수정, 사용자의 추가 요구)이 하나라도 있으면 **재검토**를 맡긴다. 같은 검토자에게 "보내기"로 보낸다: 새 `H`, 이전 `H`, 고치기로 한 것의 목록(범위가 넓어졌으면 새 수용 기준도), 새 보고서 경로(`review-<k+1>.md`). 범위는 그 목록의 해결 여부와 `git diff <이전 H>..<새 H>`다. 새 `H`와 status를 기록하고 상태를 `검토 중`으로 바꾼 뒤 3으로 간다. 재검토를 이미 두 번 받았으면 세 번째를 맡기지 않는다. `확인 필요`로 두고 사용자에게 묻는다(3의 상한과 같다).
7. **마지막 확인.** 마지막 HEAD에서 한다.
   - `B..H` 전체 diff를 읽는다.
   - `지금 고침`으로 정한 지적이 모두 처리됐는지 본다.
   - 그 HEAD에서 관리자의 구현 확인이 이미 통과했고 그 뒤 HEAD와 status가 그대로면 수용 기준을 다시 돌리지 않는다. HEAD나 실행 조건이 달라졌거나 관리자와 검토자의 결과가 어긋나면 다시 돌린다.
   - 통과하면 상태를 `확인 통과`로 바꾸고 사용자에게 알린다: 검토 결론, 지적 처분, 수용 기준 결과.
   - 실패하면(다시 돌린 수용 기준이 실패했다, diff에서 빠진 수정이나 새 결함을 찾았다) 상태를 `확인 실패`로 적고 사용자에게 알린 뒤 5로 간다. 고친 뒤에는 1을 거쳐 6의 "그 밖의 수정"으로 재검토를 받는다.
   - 명령을 돌릴 수 없거나 무결성을 판정할 수 없으면 `확인 필요`로 두고 사용자에게 알린다.

상태의 뜻을 정리하면 이렇다.

| 상태 | 뜻 |
| --- | --- |
| `배정됨` | 구현 작업자가 일하는 중이다(첫 구현, 수정) |
| `검토 중` | 검토자가 일하는 중이다(첫 검토, 재검토) |
| `확인 실패` | 구현 확인이나 마지막 확인이 실패했다. 고치게 하면 `배정됨`으로 간다 |
| `확인 필요` | 관리자가 혼자 판정할 수 없다(명령 실행 불가, 검토자가 worktree를 바꿈, Codex를 못 씀, 재검토 상한) |
| `확인 통과` | 마지막 확인이 통과했다. 이 상태는 7에서만 쓴다 |

Codex를 쓸 수 없으면(시작 실패, 한도 소진) 검토 없이 `확인 통과`로 넘어가지 않는다. `확인 필요`로 두고 사용자에게 묻는다: 기다린다, 교차 검토 없이 끝낸다(기록과 사용자 보고에 "교차 검토 없음"을 적는다), 지휘로 넘긴다.

### 검토 명세

새 양식 `delegate-review-spec.md`다. 지휘의 `review-template.md`에서 계약 부분(시도 ID, 증거 폴더, manifest)을 뺀 짧은 양식이다.

- 대상: 기준 커밋 `B`와 검토할 HEAD `H`. 시작할 때 HEAD가 `H`가 아니면 아무것도 하지 않고 보고한다.
- 먼저 읽을 것: 맡긴 명세(`spec.md` 절대 경로), `git diff <B>...<H>`.
- 검토 항목: 수용 기준 명령을 직접 돌린 결과, 실제 동작을 깨뜨리는 결함, 테스트가 공개 동작을 검증하는가, 범위를 넘었거나 건드리지 말 곳을 바꿨는가, 위생(커밋되면 안 되는 파일, 비밀 정보).
- 제약: 제품 파일을 고치거나 커밋하지 않는다. 쓰는 곳은 보고서 경로와 OS 임시 폴더뿐이다. 지적마다 근거(파일과 줄, 실행 결과)를 붙인다. 추측성 지적은 하지 않는다. Orca 작업자를 띄우지 않는다.
- 결과: 보고서를 **메인 저장소 기본 checkout**의 `.local/vstack-delegate/<이름>/review-<k>.md`에 쓴다. 명세에는 절대 경로로 적는다(검토자는 worktree에서 돌기 때문에 상대 경로로 적으면 worktree 안으로 읽힌다). 결론은 `통과` 또는 `수정 필요`다. 지적은 심각도(차단, 중요, 사소), 내용, 근거, 제안으로 적는다. 완료 보고는 `worker_done`에 `--report-path`를 붙인다.

Orca에는 Codex 작업자를 읽기 전용으로 띄우는 옵션이 없다(`worker-start --help`, Orca 1.4.257). 읽기 전용은 명세의 지시와 위 3의 대조로 지킨다. 이 대조는 보는 시점의 Git 상태가 같다는 것만 보인다. Git이 무시하는 파일에 쓴 것, 고쳤다가 되돌린 것은 잡지 못한다.

## 서브에이전트 지침

### 내용

- **누구에게 적용하는가**: 한 세션 갈래에서 일하는 Claude(맡긴 구현 작업자, 직접 할 때의 이 대화, 명세를 준비하는 관리자). 지휘의 계약 작업자는 지금처럼 서브에이전트를 띄우지 않는다(`contracts/worker-contract.md`). 레시피에도 넣지 않는다(`recipes/FORMAT.md`). Codex 검토자에게는 적용하지 않는다.
- **종류와 모델**: Agent 도구의 `Explore` 종류, `model: sonnet`. `Explore`는 편집 도구가 없다. 모델은 별칭으로 적는다(버전 이름을 적지 않는다).
- **쓰는 때**: 여러 파일을 넓게 훑어야 할 때, 서로 상관없는 조사 여러 개를 동시에 돌릴 때, 긴 출력(로그, 큰 파일)을 읽고 요약만 필요할 때.
- **쓰지 않는 때**: 어디를 볼지 이미 알 때, 도구 호출 몇 번이면 끝날 때. 두 쪽에 다 걸리면(볼 파일은 알지만 아주 긴 로그) 직접 찾아 읽는 것으로 되는지를 먼저 본다.
- **맡기지 않는 일**: 코드 쓰기, 수용 기준 실행, 원인과 설계의 판단, 코드 검토. 검토는 Codex가 한다. 같은 계열의 Sonnet 검토는 교차 검토가 아니다.
- **요청문**: 사용자의 목표, 볼 곳(파일 내용을 붙여넣지 않고 경로로), 이미 배제한 것, 돌려받을 형식(파일과 줄 포함), "읽기 전용, 파일을 바꾸지 말 것"을 적는다.
- **답은 단서다**: 서브에이전트의 일은 부른 쪽이 책임진다. 그 답에 기대어 코드를 고치거나 사실을 주장하기 전에 해당 파일과 줄을 직접 다시 읽는다. 받은 말을 그대로 옮기지 않는다.
- **새로 띄운다**: 후속 조사는 앞선 서브에이전트를 이어 쓰지 않고, 범위를 모아 새 서브에이전트에게 준다.
- **동시에 띄우는 수**: 서로 독립인 조사만 함께 띄우고, 한 번에 셋까지다(초안 값. 시범 뒤에 다시 본다).
- **보고**: 완료 보고에 서브에이전트마다 무엇을 맡겼고 무엇을 받았는지 적는다.
- **Orca 작업자**: 맡긴 구현 작업자와 조사 서브에이전트는 Orca 작업자를 띄우지 않는다. 관리자는 `delegate.md`가 정한 구현 작업자와 검토자만 띄운다.
- **스킬이 정한 서브에이전트**: 사용자가 실행한 스킬(예: `/mattpocock-skills:code-review`)이 자기 서브에이전트를 정하면 그 스킬을 따른다. 맡긴 구현 작업자가 이 줄을 근거로 읽기 전용과 `sonnet` 제한을 스스로 풀지는 않는다.

  - 범위 안의 차단·중요 지적을 고친 뒤의 재검토가 실제로 있었는지는 따로 적는다. 없었으면 "그 경우는 관측하지 못했다"로 적는다.

### 관측할 것

Orca 상태(`worker-show`, `worker-list`, `inbox --full`)와 작업자의 세션 기록으로 본다. 기록으로 판정할 수 없으면 `미확인`으로 적는다.

- **O1 구현 작업자 시작**: Run·Task·Dispatch·worktree가 맞는가. 시작 HEAD가 `B`인가. `turnStart` 값은 무엇인가. 실제로 돈 모델이 Opus인가.
- **O2 보고 경로**: `worker_done`이 Orca 절차대로 오는가. 후속 지시를 같은 터미널에서 받고 새 Dispatch로 보고하는가.
- **O3 서브에이전트**: 작업자가 서브에이전트를 불렀는가. 불렀다면 종류(`Explore`), 모델(Sonnet), 쓰기 없음, 완료 보고에 적었는가. 부르지 않았다면 "이번 일에는 필요 없었다. 부르는 길은 검증하지 못했다"로 적는다. 작은 버그라 부르지 않는 것이 맞을 수 있다.
- **O4 검토**: Codex 작업자가 같은 worktree에서 시작했는가. 검토를 맡길 때와 받은 뒤의 HEAD와 status가 같은가(위 "검토 명세"의 한계가 그대로 있다). 보고서가 정한 경로에 있고 결론과 지적 형식이 양식대로인가. 수용 기준을 직접 돌렸는가.
- **O5 재검토**: 같은 Codex 터미널에서 "보내기"로 받았는가. 범위(수정 diff와 넘겨준 목록)를 지켰는가. 새 보고서 경로에 썼는가.
- **O6 정리**: "끝낸다"의 정리를 마친 뒤에 판정한다. 두 작업자의 마지막 Dispatch가 `released`인가. 앞선 Dispatch가 `ownership_transferred`로 답하면, 그 터미널을 이어받은 마지막 Dispatch가 `released`인지로 본다.
- **O7 시간**: 띄우기부터 `확인 통과`까지, 그리고 단계별(구현, 구현 확인, 검토, 수정, 재검토, 마지막 확인) 시간.
- **O8 경계**: 작업자와 검토자가 Orca 작업자를 띄우지 않았는가. 관리자가 맡긴 worktree를 고치지 않았는가. 커밋이 작업 브랜치에만 있는가.

### 멈춤 기준

- 결과가 불명확한 명령(응답 없음, `outcome_unknown`, `stop_unknown`, `release_unknown`)은 되풀이하지 않는다. 조회로 이미 효과가 났는지 먼저 본다. 판정할 수 없으면 `확인 필요`로 두고 사용자에게 알린다.
- 검토자가 worktree를 바꿨으면 멈춘다. 그 검토 결과를 쓰지 않는다. 검토를 맡길 때 적어 둔 `H`와 status를 기준으로 그 뒤의 커밋, 추적 파일 diff, 추적되지 않는 파일을 기록한다. `B`와의 비교는 구현 변경이 섞이므로 참고로만 쓴다.
- 검토자가 worktree 밖의 허용되지 않은 곳(보고서 경로와 OS 임시 폴더가 아닌 곳: 전역 설정, 다른 저장소)에 썼으면 위반으로 기록하고, 검토자의 정지를 확인한 뒤 영향을 본다. 검토자가 worktree 안을 바꾼 경우는 바로 위 줄을 따른다.
- 조사 서브에이전트의 쓰기를 찾으면 위반으로 기록한다. 아직 쓰는 중이거나 맡긴 worktree 밖에 썼으면 구현 작업자의 정지를 확인하고 영향을 본다. 맡긴 worktree 안에서 이미 끝난 쓰기면 기록하고 시범을 이어 간다(그 쓰기가 커밋에 들어갔는지는 구현 확인의 diff 읽기에서 본다).
- 위 두 줄에서 누가 언제 썼는지 판정할 수 없으면 `확인 필요`다.
- 작업자나 검토자가 Orca 작업자를 띄웠으면 그 작업자의 정지를 확인하고 멈춘다.
- 관리자가 맡긴 worktree를 고쳐야 할 것 같으면 고치지 않고 멈춘다.
- 건드리지 말 곳이 바뀌었으면 누가 썼든 그 결과를 `확인 통과`로 치지 않는다.

### 끝

push와 PR은 없다(원격이 없다). 결과를 시범 저장소 `main`에 반영할지, worktree를 지울지는 사용자가 정한다. 시범 기록은 사용자의 "시범 기록을 써라" 뒤 `docs/pilot-delegate.md`에 쓴다: 단계별 기대와 실제, O1~O8 답, 어긋난 곳과 원인(문서 / Orca 동작 / 작업자 동작 / 실행 실수), 고칠 것, 돌려 보지 않은 것. omp 결과(`763399e`)와 무엇이 달랐는지도 참고로 적는다.

## 순서

1. 이 계획을 Codex가 검토한다. 사용자가 승인한다.
2. `ui-polish@2`가 병합된 뒤의 `main`에서 초안 문서를 쓴다("문서 변경 목록").
3. 사용자가 시범 실행을 승인하면 시범을 돌린다.
4. 시범 결과를 문서에 반영하고 Codex가 검토한다.
5. 사용자 지시로 PR을 올리고 병합한다. 플러그인을 갱신하고 구조도를 고친다.

## 내가 정한 값(사용자가 바꿀 수 있다)

사용자가 말하지 않은 곳을 이렇게 정했다.

1. `refactoring`은 한 번 맡겨 본 뒤에 기본값을 올린다. 지금은 직접 하는 것이 기본이다.
2. 부르는 이름을 "지휘자"에서 "관리자"로 맞춘다.
3. Codex 검토자의 모델은 Codex 설정의 기본값을 쓴다.
4. 재검토는 두 번까지다. 그 뒤에는 사용자에게 묻는다.
5. 사소한 지적만 고쳤으면 재검토하지 않는다.
6. 서브에이전트는 한 번에 셋까지다.
7. 같은 HEAD에서 관리자가 이미 수용 기준을 돌렸으면 마지막 확인에서 다시 돌리지 않는다.

## 하지 않는 것

- 지휘(계약, 관문, 작업자 종류)는 바꾸지 않는다.
- `ui-polish`를 맡기는 것. 지금처럼 이 대화가 직접 한다.
- 검토에 `blast-radius` 점검을 넣는 것. 지휘의 교차 검토에만 있다.
- 한 세션 맡기기에 한도 확인(`check-limits`)을 미리 넣는 것. Codex를 못 쓰면 그때 사용자에게 묻는다.
- 비정상 경로(관리자 재시작, 중단, 보고 없이 끝난 작업자, 재검토 상한) 시범. 실제로 만나면 기록한다.
- `feature`·`refactoring` 맡기기 시범, 라우터를 거친 시범.
- 이미 쓴 omp 시범 기록을 고치는 것.
