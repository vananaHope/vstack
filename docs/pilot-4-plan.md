# 네 번째 시범 계획: 관리자 재시작 뒤 이어받기

지금까지 세 시범은 관리자 세션 하나가 처음부터 끝까지 지휘했다. 라우터 고르기 0은 "관리자가 바뀌었거나 다시 시작했으면 orchestrate-issues가 `state.md`와 보관된 증거로 이어 간다"고 하지만, 이 경로는 한 번도 돌려 보지 않았다. 이번에는 지휘 도중 관리자 세션을 실제로 닫고, 새 세션이 이어받게 한다. 같이 0.5.0 라우터 반영분(시범 3 D1·D8) 가운데 자연스럽게 나오는 것을 본다.

- 저장소: `vananaHope/vstack-pilot-todo` · 실행 환경: Orca · 플러그인 vstack 0.5.0 · 계약 `vstack-contract@3` · 레시피 `bug-fix@4`
- 실행기: Codex(구현), Claude(검토). OpenCode는 쓰지 않는다(계정 막힘). 명세 새 눈 점검은 서브에이전트.
- 병합 방식: `지시`. 병합·force-push는 이름을 적은 사용자 승인으로만 한다(고정 규칙 5).
- 관리자 세션: **A**(지금 세션, 배정까지), **B**(새 Claude Code 세션, 이어받기). 선택 단계에서 **C**.
- 한계: 이 시범은 진단의 맹검성을 주장하지 않는다. 답이 든 로컬 브랜치 `fix/empty-title-list`는 연결된 worktree에서도 참조·객체가 보이고(`git show fix/empty-title-list`), 버그를 심은 준비 커밋 `e8b0f97`의 메시지에도 단서가 있다(시범 3 D7). 이 시범이 보는 것은 이어받기 절차다.

## 준비(지휘 2의 사전 준비 변경)

라우터 지휘 2의 "검증 명령이 쓰는 검증 수단이 없으면 지휘를 시작하기 전에 기본 브랜치에" 넣는 준비 변경이다. 방법은 **시범 저장소 `main`에 직접 커밋하고 push**하는 것이고, 이 계획을 승인받으면 그 커밋 하나와 push를 확인받은 것으로 본다. 그 밖의 `main` 변경은 하지 않는다. 확인은 `pilot-2-plan.md` "준비"와 같다(원격·경로, 준비 전 SHA 기록). 커밋 메시지는 중립적으로 쓴다(시범 3 D7).

1. `scripts/verify.mjs`에 시나리오 `empty-title`을 더한다: 제목이 `""`와 `"   "`인 v2 파일을 쓰고 새 프로세스로 `list`(텍스트)를 돌려, 두 줄이 `(제목 없음)`인지 본다. verify 스킬 `features/`에 문서를 더한다. 지금 `main`에서 실패(red)하는지 보고, green은 scratch 사본에 `fix/empty-title-list`의 수정을 얹어 확인한다. 커밋하기 전에 `git diff --cached`로 준비 커밋에 수정(답안)이 섞이지 않았는지 본다.
2. 이슈를 만든다(라벨 `ready-for-agent`, 본문에 증상·기대 동작·완료 기준 체크리스트·vstack 절). 버그는 `main`에 이미 있는 것(`formatList`가 `??`로 빈 문자열을 거르지 못함)이다.
   - vstack 절: `bug-fix@4`, `AC-1@1` 증상 해소(`node scripts/verify.mjs empty-title --out <증거 폴더>/ac-1`), `AC-2@1` 회귀 테스트(`node --test test/`), seam `formatList`, 결정적, 건드리지 말 영역 `addTodo`·`markDone`·`src/store.mjs`·`scripts/verify.mjs`.

## 끊는 지점과 기대 동작

### R1: 구현 중에 관리자 A를 닫는다

**끊는 방법**

1. A는 구현자를 띄우기 **전에** B용 인계 파일(아래 "관찰자 역할")을 써 둔다.
2. A는 구현자(Codex)를 띄우고 제출 확인, `state.md` 시도 표(구현 중, `배정됨`, 세션·dispatch), 띄우기 직전 기록, 맡김 기록, Codex fast 판단 기록까지 평소대로 한다. Codex fast 첫 응답 확인(`service_tier`)은 할 수 있으면 하고, 못 하면 `state.md`에 "첫 응답 확인 전"이라고 남긴다.
3. A는 사용자에게 "지금 닫아 달라"고 알리고 턴을 끝낸다. **그 뒤 A가 깨어나도 작업자 보고를 처리하지 않는다**(보관·결과 대상 확정·`state.md` 수정·검토자 배정 모두 하지 않는다). 깨어났으면 "R1 대기 중이라 처리하지 않음" 한 줄만 답한다.
4. 사용자가 A 세션을 닫는다.

**성립 확인**(B가 기록하고, 사용자가 닫은 시각을 알려 준다)

- 구현자 `worker_done` 시각이 사용자가 A를 닫은 시각보다 뒤다(`inbox --full`, `worker-show`의 시각).
- A가 남긴 `state.md`에 그 시도의 보고·보관 흔적이 없다(`배정됨`, 보관 경로·manifest 해시 없음, `evidence/` 아래 그 시도 폴더 없음).
- 둘 중 하나라도 아니면 R1 미성립으로 기록하고, 이어받기는 하되 R1 결과로 세지 않는다.

**B의 기대 동작**

사용자가 B에서 `/vstack:v-mode`로 이어 가라고 하면:

1. 고르기 0 → "관리자가 바뀌었거나 다시 시작" → 이어 가기 전에 "이 경로는 시범으로 돌려 보지 않았다"를 사용자에게 알린다(라우터).
2. orchestrate-issues "가장 먼저: 설정 확인" → 1단계 "지휘를 처음 시작할 때 `.local/vstack/*/state.md`를 먼저 훑어 이어 갈 작업을 사용자에게 알린다".
3. Run을 이어받는다(`run-use --id <run>`). 그 결과를 기록한다.
4. 시도마다 상태를 확인한다(archive.md "중단 복구", vstack.md "복구"). 이 시도는 `배정됨`이므로 작업자 상태부터 나눈다.
   - **실행 중**(`worker-show`에 살아 있고 settled가 아님): 아무것도 정산하지 않고 기다린다(archive.md "증거 없음 정산" 1: "확인되지 않으면 상태를 `배정됨`으로 두고 기다린다").
   - **끝났고 보고가 있다**(`inbox --full`에 그 Task·Dispatch의 `worker_done`): 그 보고를 "완료 보고를 받으면"의 입력으로 쓴다. 보관(1~5) → 결과 대상 확정 → 결론이 `완료`면 4단계 교차 검토, `막힘`이면 "복구".
   - **끝났는데 보고가 없다**: "보고 없이 멈춤". 정지 확인 → 증거 없음 정산 → 구현이 끝났으면 재검증, 끝나지 않았으면 같은 worktree에 새 수정(이어받기 칸)(vstack.md "복구" 표).
   - **정지 미확인**: 정산·격리·재시작·worktree 삭제를 하지 않고 사용자에게 알린다(backends/orca.md "정지").
5. 이어 가며 A의 기록을 보존한다: 시도 표의 기존 줄을 지우거나 고쳐 쓰지 않고(상태 칸만 절차대로 바꾼다), 새 배정(검토자)에는 배정 전 기록·띄우기 직전 기록·맡김 기록·세션 키를 새로 만든다. A가 Codex fast 첫 응답 확인을 못 했으면 B가 세션 기록으로 확인하거나, 확인할 수 없다고 적는다.

### R2(선택): 검토 보관 도중 관리자 B를 닫는다

R1 결과를 보고 사용자가 할지 정한다. 하지 않으면 B가 끝까지(지시 대기) 간다.

**끊는 방법**: 사용자가 B에게 "검토자 보고를 받으면 보관 3(승격)까지만 하고 멈춰라"고 따로 지시한다(이 지시는 개입으로 기록한다). B는 그 지점에서 멈추고, 사용자가 B를 닫는다.

**성립 확인**: 보관 폴더 `evidence/<rev 시도 ID>/`가 있고, `state.md`의 그 시도 줄에 보관 경로·manifest 해시가 없다.

**C의 기대 동작**: archive.md "중단 복구" "승격 뒤, 포인터 전" 행 → 보관 폴더를 manifest `files`와 대조 → 맞으면 4(포인터)부터, 틀리면 보관 폴더를 지우고 1부터 → 5(원본 정리) → vstack.md "완료 보고를 받으면" 2(결과 대상 확정) → "검토 보고를 받으면"(수용 기준 집계, 막힘·증거 없음이면 "복구") → 5단계 판정. 대조가 맞으면 다시 복사하거나 덮지 않는다.

## 같이 볼 것(0.5.0 반영분)

- D8: 이어받은 관리자가 PR·병합 승인을 구할 때 "병합"을 질문에 이름으로 적는가. 짧은 승인으로 병합하지 않는가.
- D1(선택): 지휘 중 사용자가 작은 수정을 요청하면 `user-request-<k>.md`를 남기고 `fixes.md`로 맡기는가. 재검증·새 `review`가 붙어 시간이 늘어나므로 요청 여부는 사용자가 정한다.

## 시범으로 답할 질문

- Q1a(조회): A가 닫힌 뒤 도착한 구현자 `worker_done`을 B가 볼 수 있는가. `inbox --terminal run:<run> --full`로 본문 전체와 Task·Dispatch ID를 시도 표와 대조한다(미리보기 200자만으로 판정하지 않는다).
- Q1b(깨우기): B가 `run-use`로 Run을 이어받은 뒤, B가 띄운 검토자의 `worker_done`이 B를 깨우는가. A가 띄운 작업자의 보고가 B에게 다시 전달되는가는 따로 적는다. 둘을 섞지 않는다.
- Q2: A가 닫힐 때 Orca가 A가 띄운 작업자를 어떻게 다루는가(계속 도는가, `terminalState`, liveness).
- Q3: 계약 문서만으로 B가 이어 갈 수 있는가. 막히는 곳(예: B가 받은 적이 없는 `worker_done`을 "완료 보고를 받으면"의 입력으로 써도 되는가)은 계약 질문으로 적는다.
- Q4(기록 연속성): A가 남긴 배정 전 기록·띄우기 직전 기록·맡김 기록·fast 기록이 B의 판단에 충분했는가. B가 기존 시도 줄을 보존하고 새 배정 기록을 빠짐없이 더했는가.

## 관찰자 역할

B와 C는 이어받는 관리자이면서 시범 기록자다. 이어받기를 오염시키지 않으려고:

- A는 B에게 이 작업의 상태를 넘기지 않는다. B가 쓰는 것은 `state.md`·작업 파일·보관 증거·Orca 기록뿐이다.
- A는 구현자를 띄우기 전에 `.local/handoff-pilot-4.md`(vstack 저장소, 무시 경로)에 관찰자 지시만 남긴다: "이 파일은 사용자가 '시범 기록을 써라'라고 할 때까지 더 읽지 않는다. 그 전에는 사용자의 요청만 따른다." 그 아래에 기록할 때 읽을 것(이 계획, Q1~Q4)을 적는다. 끊는 지점은 적지 않는다.
- 사용자는 B를 연 뒤 이 파일의 첫 줄만 읽게 하고, 이어 가라는 요청을 직접 입력한다. R2는 사용자가 B에게 따로 지시한다.
- 기록은 이어받기가 끝난 뒤(지시 대기 또는 R2 지점) 사용자의 "시범 기록을 써라" 뒤에 한다. 기록자는 자기 transcript를 다시 보고 기대 동작과 대조한다.
- 그래도 B가 시범 중이라는 것을 안다는 것은 한계로 기록한다.

## 순서

1. A: 준비 1·2. 사용자에게 준비 결과를 보이고 확인받는다.
2. 사용자: `/vstack:v-mode <이슈> 진행해`로 지휘를 시작한다. A: 인계 파일 → 지휘 → 구현자 띄우기 → 기록 → "지금 닫아 달라"(R1).
3. 사용자: A 세션을 닫고 닫은 시각을 적어 둔다. 새 Claude Code 세션 B를 연다.
4. 사용자: B에서 인계 파일 첫 줄을 읽게 한 뒤 `/vstack:v-mode vstack-pilot-todo <이슈> 이어 가` 같은 문장을 직접 입력한다.
5. B: 이어받기 → 보관 → 검토자 → (사용자가 R2를 지시하면 그 지점에서 멈춤) → 지시 대기.
6. (R2를 하면) 사용자: B를 닫고 C를 연다. C에서 이어 가라고 한다.
7. 사용자 지시가 있으면 PR·병합(이름을 적은 승인).
8. 사용자의 "시범 기록을 써라" 뒤 마지막 관리자가 `docs/pilot-4.md`를 쓴다: 끊는 지점마다 성립 여부와 기대·실제, Q1~Q4 답, 어긋난 곳, 원인(라우터·계약 문서 / Orca 동작 / 실행 실수), 고칠 것.

## 멈춤 기준

- 정지가 확인되지 않은 작업자가 있으면 그 시도의 정산·격리·재시작·worktree 삭제를 하지 않고 "정지 미확인"을 알린다(backends/orca.md "정지").
- 병합·force-push는 이름을 적은 사용자 승인이 있을 때만 한다. force-push는 `--force-with-lease=<브랜치>:<기대하는 원격 SHA>`로만 하고, 그 SHA를 방금 원격에서 읽은 값과 대조한다. 승인이 없거나 lease 값이 맞지 않으면 명령을 내리기 전에 멈춘다.
- 유효하지 않은 증거로 병합 관문을 통과시키려 하면 멈춘다. 이어받기를 성공시키려고 관문을 건너뛰지 않는다.
- 위 가운데 하나라도 이미 어겼으면(승인 없는 병합·force-push, 잘못된 lease, 무효 증거로 병합, 정지 미확인 상태에서 정산) 시범 전체를 멈추고 보고한다.
- 이어받은 관리자가 계약에 답이 없는 상황을 만나면 추측하지 않고 사용자에게 묻고, 그 상황을 Q3로 기록한다.
- 사용자 확인이 필요한 곳: 준비 결과, A를 닫는 시점, R2 여부, D1 요청 여부, PR, 병합.
