# 지휘마다 기준 브랜치를 두고, 기준 브랜치가 다른 기록과는 검증 자원만 견준다

지금까지 지휘는 프로젝트 설정의 기본 브랜치 하나를 기준으로 했다. 작업 worktree를 거기서 만들고(`backends/orca.md`의 `--base-branch main`), 이슈 PR을 거기로 보냈다. 사용자의 실제 작업 방식은 다르다. 기본 브랜치에서 기능 worktree `A`를 만들고, 그 안에서 지휘를 시작해 `A`에서 작업 worktree를 뻗고 이슈를 `A`에 병합한 뒤, 모두 끝나면 `A`를 기본 브랜치에 넣는다(2026-11-25 사용자 설명과 결정).

그래서 지휘마다 **기준 브랜치**를 둔다. 지휘를 시작한 관리자 작업 트리의 브랜치이고, 지휘가 끝날 때까지 바꾸지 않는다. 작업 worktree, 이슈 PR, 병합 관문의 `B`는 모두 그 브랜치다. 병합 관문은 이미 `<기준 브랜치>`로 쓰여 있어 계약은 바뀌지 않는다(`vstack-contract@5` 그대로). 기준 브랜치는 작업마다 `task.md` Constraints의 "기준 브랜치" 줄에 적는다. `state.md` 형식은 계약이라 건드리지 않았다.

기준 브랜치가 생기면 0.26.0~0.27.0 규칙 가운데 같은 기준 브랜치를 전제한 것이 갈린다.

- **같은 기준 브랜치에 들어가는 기록끼리**: 그대로다. 쓰는 곳과 검증 자원의 겹침, 반영과 병합은 한 번에 하나, 지휘 중 로컬 병합 금지.
- **기준 브랜치가 다른 기록끼리**: 검증 자원만 견준다. 같은 기계에서 포트와 DB는 함께 쓰기 때문이다. 쓰는 곳은 서로 다른 브랜치에 들어가므로 작업 중에는 보지 않고, 기준 브랜치들을 기본 브랜치에 넣을 때 Git과 전체 테스트가 드러낸다. 반영·병합 순서도 서로 기다리지 않는다.
- **이어받기**: 지휘를 시작하면 기준 브랜치가 같은 끝나지 않은 작업만 이어받는다. 기록은 여전히 메인 저장소의 `.local/vstack/` 한 곳이므로, 이 구분이 없으면 두 번째 지휘가 첫 지휘의 작업을 가져간다. 기준 브랜치가 다른 작업은 "진행 중"에는 넣어 두 지휘가 같은 이슈를 고르지 않게 한다. 지휘의 관리자는 기준 브랜치마다 하나다([ADR 0014](0014-one-manager-per-record.md)의 "지휘의 관리자는 저장소에 하나"를 바꾼다).
- **다룰 이슈**: 기준 브랜치가 기본 브랜치가 아니면 지휘를 시작할 때 다룰 이슈를 좁힌다. 그래야 "모두 끝났다"를 판정할 수 있다.
- **맡기기도 같다**: 맡기기의 기준 브랜치 기본값도 관리자 작업 트리의 지금 브랜치다. 전에는 "보통 기본 브랜치"였다. 기능 worktree 안에서 맡기면 결과가 그 기능 브랜치로 가야 한다(2026-11-25 사용자 결정).
- **이슈 닫기**: GitHub는 기본 브랜치로 병합한 PR에서만 `Closes #<n>`으로 이슈를 닫는다. 기준 브랜치가 기본 브랜치가 아니면 관리자가 이슈 병합을 확인한 뒤 직접 닫는다. 닫지 않으면 그 이슈가 맡길 이슈 목록에 다시 나오고, 그 이슈를 선행으로 둔 이슈가 프런티어에 들지 않는다(리뷰 지적). 이슈는 기준 브랜치에 들어갔을 때 끝난 것으로 보고, 기본 브랜치에 들어가는 일은 8단계가 따로 맡는다.

기준 브랜치를 기본 브랜치에 넣는 일은 지휘의 마지막 단계(`orchestrate-issues/SKILL.md` 8단계)로 둔다. 병합 방식이 `자동`이어도 사용자 지시로만 한다. 이슈마다 이미 병합 관문을 거쳤으므로 다시 증거를 요구하지 않고, 기본 브랜치를 받은 뒤 전체 테스트를 돌린 커밋 `T`와 PR head가 같은지, 기본 브랜치가 `T`의 조상인지만 본다. 이 확인은 계약의 병합 관문 밖이다. 관문은 관리자가 하는 이슈 병합에만 보장한다는 [ADR 0006](0006-merge-gate-only-for-manager-merges.md)과 어긋나지 않는다.

**Considered Options**: 기록을 기준 브랜치의 worktree 안(`A/.local/`)에 두는 길도 있었다. 그러면 지휘끼리 기록이 저절로 나뉜다. 하지만 메인 저장소 기준으로 기록을 찾는 곳(v-mode 고르기 0, 맡기기의 겹침 판정, `main-repo.md`)을 모두 바꿔야 하고, 다른 지휘의 작업을 "진행 중"으로 보지 못해 같은 이슈를 두 지휘가 고를 수 있다. 그래서 기록 위치는 두고 기준 브랜치 줄로 가렸다. `state.md`에 줄을 더하는 길은 계약 숫자와 레시피 일곱의 머리말을 함께 올려야 해서, 0.26.0의 "검증 자원" 줄처럼 `task.md`에 두었다. A를 기본 브랜치에 넣을 때 병합 관문을 다시 하는 길은 버렸다. 관문의 증거는 이슈 단위이고, 합친 결과에 대한 증거는 전체 테스트가 맡는다.

**돌려 보지 않았다.** 기본 브랜치가 아닌 기준 브랜치로 지휘한 시범은 아직 없다.
