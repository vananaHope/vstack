# 04. 보관 실패, 복구, 새로 시작

01a의 rev 시도 `rev-3ecbf1e7-1`이 완료 보고를 보낸 뒤 관리자가 보관을 시작한다. 경로:

- 원본: `C:\wt\issue-42\.vstack\evidence\issue-42\rev-3ecbf1e7-1\`
- staging: `<메인>\.local\vstack\issue-42\evidence\.staging\rev-3ecbf1e7-1\`
- 보관: `<메인>\.local\vstack\issue-42\evidence\rev-3ecbf1e7-1\`

manifest `files`에는 `ac-1/before.png`, `ac-1/after-reload.png`, `ac-1/run.log`, `ac-2/test.log` 4개가 있다.

## 04a. 중단 지점별 복구

관리자 세션이 각 지점에서 끊긴 뒤 다시 시작했다. 시작하면 `state.md` 시도 표를 먼저 본다.

| # | 끊긴 지점 | 재시작 때 상태 | 시도 표 | 복구 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 1 | 복사 중(2개만 복사) | staging에 2개, 보관 폴더 없음 | `보고됨` | staging 삭제 → 1부터 | `정리됨` |
| 2 | 대조 뒤, 승격 전 | staging에 4개, 보관 폴더 없음 | `보고됨` | staging 삭제 → 1부터 | `정리됨` |
| 3 | 승격 뒤, 포인터 전 | 보관 폴더에 4개, 포인터 없음 | `보고됨` | 보관 폴더를 manifest `files`와 대조 → 일치 → 4(포인터)부터 | `정리됨` |
| 4 | 포인터 뒤, 원본 정리 전 | 포인터 있음, 원본 있음 | `보관됨` | 보관 확인(manifest 해시 + 4개 파일 해시) → 5 | `정리됨` |
| 5 | 원본 정리 중(`run.log` 잠김) | 포인터 있음, 원본에 `run.log`만 | `보관됨` | 5 다시 → 또 잠김 | `원본정리대기` |

어느 경우에도 같은 시도가 두 번 보관되지 않는다.

### 원본정리대기가 남았을 때

- 정산되지 않았다 → G4 **실패** → 병합하지 않는다. worktree도 지우지 않는다.
- 다음에 깨어났을 때 5를 다시 한다. 로그를 잡던 개발 서버가 내려가 있어 성공 → `정리됨` → G4 통과.

## 04b. 증거 없음 정산

01b의 재수정 시도 `impl-d195b9cc-2`(세션 `term-c1`)가 작업 중 멈췄다. Orca가 `escalation`을 보냈고 `worker_done`은 오지 않았다. worktree에는 시도 폴더(`ac-1/run.log` 하나)가 있고 manifest가 없다.

1. `escalation`만으로는 정지로 보지 않는다. 관리자가 정지를 요청하고, 작업자 상태가 정지로 확인될 때까지 시도는 `배정됨`으로 둔다.
2. 정지 확인 → `격리대기`, 비고 `격리: 원인=증거없음(작업자 멈춤), 단계=시작`.
3. 격리: `.staging\impl-d195b9cc-2.void\`로 복사 → 대조, `void-manifest.json` 작성 → `evidence\impl-d195b9cc-2.void\`로 확정 → 포인터(단계 `확정`) → 원본 삭제(단계 `원본정리`).
4. `증거없음(작업자 멈춤, manifest 없음)`.
5. 이 시도가 맡았던 AC-1·AC-2는 대상 (H2, B1)에서 impl **증거 없음**이 된다(03e와 같은 규칙). 관리자는 새 시도 `impl-d195b9cc-3`을 맡긴다. 세션 `term-c1`이 닫혔으면 아래 04f의 impl 인계를 쓴다.

원본 삭제가 잠김으로 실패하면 `격리대기`(단계 `원본정리`)로 남고, 정산되지 않으므로 G4 실패.

## 04c. 보관 손상에서 완료까지

`rev-3ecbf1e7-1`이 `정리됨`인데, 병합 직전 G4·G1을 보려고 보관 확인을 하자 `ac-1/run.log`의 sha256이 manifest와 다르다(누군가 열어 고쳤다). manifest 파일 자체의 해시는 포인터와 같다.

1. 보관 확인은 manifest 해시만이 아니라 `files`의 모든 파일 해시를 본다 → 손상 발견.
2. 먼저 `격리대기`, 비고 `격리: 원인=손상(ac-1/run.log), 단계=시작`. 관문 기록과 사용자 보고에 "보관 손상(rev-3ecbf1e7-1, ac-1/run.log)".
3. 보관 폴더를 `rev-3ecbf1e7-1.damaged\`로 이름을 바꾸고 단계를 `damaged`로. worktree 원본은 이미 지워졌다(정리됨이었으므로) → 격리할 것 없음.
4. `손상정산(ac-1/run.log 해시 불일치)`.
5. 이 시도가 맡았던 AC-1·AC-2는 rev **증거 없음**, 그리고 (H1, B1)의 가장 나중 `review` 시도가 손상정산이라 G3도 실패 → 차단.
6. 관리자가 같은 대상에 새 rev `review` 시도 `rev-3ecbf1e7-3`(세션 `term-r1`)을 맡긴다. 통과, `정리됨`.
7. 다시 판정: G1 통과(`rev-3ecbf1e7-3`), G3 통과(`rev-3ecbf1e7-3`), G4 통과(손상정산은 정산됨), G5 통과 → 병합.

손상은 숨겨지지 않는다. 관문 기록과 `.damaged\` 폴더가 남는다.

## 04d. 격리 원본 일부만 지운 뒤 재시작

04b의 격리에서 원본이 `ac-1/run.log`, `ac-1/partial.png` 두 파일이었다고 하자. 확정 `.void`에 둘 다 있고 포인터(단계 `확정`)도 적었다. 원본 정리에서 `partial.png`는 지웠고 `run.log`는 잠겨 실패했다(단계 `원본정리`). 이때 관리자가 재시작했다.

- 복구표 "격리 포인터 뒤": `.void`를 포인터로 확인한다(`void-manifest.json` 해시 일치, 두 파일 모두 해시 일치).
- 원본에 **남아 있는** `run.log`만 지운다. 확정 `.void`는 지우지 않는다. `partial.png`는 원본에 없어도 `.void`에 있으므로 잃지 않는다.
- 성공 → 격리 끝 → `증거없음(작업자 멈춤)` → 정산됨.

## 04e. 손상 이름 바꾸기 직후 재시작

04c의 3에서 `rev-3ecbf1e7-1.damaged\`로 이름을 바꾼 직후, 단계를 `damaged`로 적기 전에 관리자가 끊겼다.

- 재시작 때 비고는 `원인=손상, 단계=시작`이고, 디스크에는 `.damaged\`가 있고 원래 이름의 폴더가 없다.
- 복구표 "손상 이름 바꾸기 뒤, 단계 기록 전": 단계를 `damaged`로 적고 보관 손상 4부터. 원본이 없으므로 5 → `손상정산`.
- 손상 표시(단계 `시작`)를 이름 바꾸기 **전에** 적었기 때문에, 끊겨도 원인(손상)을 잃지 않는다.

## 04f. 새로 시작과 impl 인계

`issue-42`가 `PR 열림` 상태인데 진행에 문제가 생겨, 사용자가 이 PR을 버리고 같은 이슈를 처음부터 다시 하기로 했다(state-and-rollback.md "새로 시작").

1. vstack 관리자가 이 작업의 작업자(`term-c1`, `term-r1`)를 정지하고 정지를 확인한다.
2. 시도 표의 미정산 시도를 정산한다(04a~c 절차).
3. 사용자에게 물어 PR #57을 닫는다.
4. worktree `C:\wt\issue-42`는 지우지 않는다. 미병합이라 orchestra 지우기 규칙(병합됨)을 채우지 못한다. 브랜치를 `vstack-abandoned/issue-42-20261110`로 이름을 바꾸고, 보존 경로와 브랜치를 사용자에게 알린다.
5. 사용자가 "버려도 돼"라고 폐기를 고르면: 브랜치를 원격에 백업할지 묻고, 답에 따라 백업한 뒤 worktree를 지운다(작업자 정지와 정산은 이미 확인됨). 고르지 않으면 보존한 채로 둔다.
6. vstack `state.md` 첫 줄 `끝`, `소유: 포기(2026-11-10, 새로 시작)`.
7. #42를 vstack 지휘의 새 작업으로 다시 맡길 수 있다. 열린 PR이 없고 `issue-42`의 `state.md`가 `끝`이므로 진행 중이 아니다. 새 작업 이름은 `issue-42-r2`다(state-and-rollback.md "다시 맡길 때의 작업 이름"). 새 폴더 `.local\vstack\issue-42-r2\`에 새 `state.md`(`이전 작업: issue-42(포기 2026-11-10)`)를 쓰고, 새 브랜치 `issue-42-r2-<slug>`는 보존 브랜치와 겹치지 않는다. `issue-42` 폴더의 `state.md`와 보관 증거는 그대로 남고 새 작업의 판정에 쓰지 않는다.

PR을 열어 둔 채 "새로 시작"을 하면 열린 PR 때문에 그 이슈는 진행 중으로 보여 다시 맡겨지지 않는다. PR을 살리려면 새로 시작하지 않고 이 작업을 vstack에서 이어 간다(관리자 재시작). `@3`에 있던 "명시적 이행"(PR과 worktree를 살려 기존 agent-orchestra 관리자에게 넘김)은 `@4`에서 뺐다.

**impl 인계**

vstack을 계속 쓰는 경우로 돌아가서, 04b 뒤 세션 `term-c1`이 Orca에서 닫혀 다시 열 수 없다고 하자. 대상은 그대로 (H2, B1)이다.

- 관리자가 새 codex 세션 `term-c9`를 띄우고 시도 표에 `impl-c9c9c9c9-1`, 비고 `impl 인계(term-c1 닫힘)`를 적는다.
- `term-c9`는 (H2, B1)에 커밋하지 않고 필수 수용 기준 전부를 돌린다. 자기 검증이다.
- rev 자격은 그대로 따진다: rev 세션은 `term-c1`(변경 작성자)도 `term-c9`(impl)도 아니어야 하고, 계열이 변경 작성자(codex)와 달라야 한다.
