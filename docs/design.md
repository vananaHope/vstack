## 목표

pstack의 구조(라우터 → 레시피 → 원칙)를 가져와 **v-mode**를 만든다. v-mode는 요청에 맞는 레시피를 고르고, 레시피는 mattpocock·agent-orchestra·pstack에서 가져온 스킬을 단계마다 쓴다. 중심은 pstack의 **검증과 원칙**이다.

배경: 사용자는 작업 전에 자기 생각과 AI 생각의 간격을 줄이는 데 공을 들인다(mattpocock `grill-with-docs` → `to-spec` → `to-tickets`). 구현은 직접 만든 agent-orchestra로 관리자를 두고 맡긴다(등급별 Codex·Claude 배치, 다른 실행기 교차 검토). pstack의 검증·플레이북·원칙이 이 흐름에서 비어 있는 실행 품질을 채운다고 본다.

**첫 버전의 성공 기준**(첫 버전 때의 기준): Orca 위에서 버그 수정 한 건이 Claude 관리자 → Codex 구현 → 다른 실행기 검토 → 병합 직전 재검증까지 이 문서의 계약대로 통과하고, 10절의 행동 회귀 사례가 기대대로 움직인다. 스킬을 몇 개 가져왔는지는 기준이 아니다.

**보장 범위**: 이 문서의 관문은 **vstack 관리자가 실행하는 병합**에만 보장된다. 사람이 GitHub에서 직접 병합하는 것은 사후 확인과 경고만 한다(3.5).

### 판정 이력

- 1판 → 2판: 뺀 스킬에 기대는 의존(pstack `architect/SKILL.md:29,47`, mattpocock `tdd/SKILL.md:26,38`), 측정하지 않은 결합 가정, `disable-model-invocation`을 복사 근거로 쓴 오류를 바로잡았다.
- 2판 → 3판: 증거 재사용 예외가 원본보다 느슨함(R1), 관문이 모든 병합 경로에 걸리지 않음(R2), 검토자 재실행과 쓰기 금지 충돌(R3), 보관·복구 절차 부재(R4), 빈 입력 처리(R5), 실행 의존이 덜 닫힘을 바로잡았다.

## 2. 층 구조와 소유

| 층 | 답하는 질문 | 소유하는 것 | 출처 |
| --- | --- | --- | --- |
| 정렬 | 무엇을, 왜 만드나 | 사용자 결정, 용어, seam, 티켓 분해 승인 | mattpocock |
| 실행 품질 | 한 단위의 일을 어떻게 제대로 하나 | 한 작업의 방법(레시피), 원칙, 검증 수단 | pstack |
| 배치 | 누가, 언제, 누구의 검토를 받아 하나 | 작업 수명, 작업자 배치, 검토, 증거 보관, PR, 병합, `state.md` | agent-orchestra |

```
요청 → v-mode (목표 되짚기 · 크기 판단 · 레시피 고르기)
   ├─ 작은 일 ──────── 바로 처리
   ├─ 한 단위의 일 ──── 레시피를 골라 작업자에게 맡김(14절. 첫 버전에는 v-mode가 직접 실행)
   └─ 여러 티켓 분량 ── 정렬 → 명세 → 티켓 → 지휘
                                     │
           티켓: 레시피 ID · 수용 기준(ID·버전) · seam · 전환 방식
                                     ▼
           배정 전 입력 검사(3.7) → 명세 확정: 레시피 버전·절대 경로 · 후보 원칙 · 역할별 권한 · 증거 요구
                                     ▼
           구현자: 구현·검증·커밋·완료 보고
           검토자: 같은 수용 기준을 새 상태에서 다시 실행
           관리자: 증거 보관 → 병합 관문(3.5) → 병합
```

- **재귀 금지**: 작업 유형 레시피에는 지휘 단계가 없다. 작업자는 다른 작업자를 띄우지 않는다. pstack feature 플레이북의 "구현을 위임하라"(`playbooks/feature.md:3~12`)는 관리자 쪽 단계로 옮긴다.
- **티켓에는 안정적인 것만**: 레시피 ID와 검증 가능한 수용 기준만 적는다. 버전 폴더가 들어간 절대 경로는 배정 시점에 관리자가 명세에 넣는다.
- **크기와 위험은 따로 본다**: 크기가 갈래를 정하고, 위험(난도·틀리면 드는 비용)은 orchestra 등급이 정한다.
- **계획 철학**: 사람만 정할 수 있는 것은 정렬 단계에서 묻는다. 돌려 보면 아는 것은 프로토타입으로 확인한다. 실험 비용이 크거나 읽기 전용 조사면 기존 자료로 답한다(pstack `poteto-mode/SKILL.md:21`).

## 3. 계약

vstack의 핵심 산출물은 이 계약이다. 계약은 `skills/v-mode/contracts/`에 독립 md로 두고, 관리자가 작업 명세에 절대 경로로 넣는다.

### 3.1 우선순위

**적용 범위**: 사용자 지시와 런타임 권한 안에서 vstack 문서끼리 충돌할 때의 순위다. 사용자 지시와 런타임 권한을 넘지 않는다.

1. **불변 규칙**: 증거 계약(3.3), 역할별 권한(3.2), 병합 관문(3.5), 안전 멈춤(6절 5). 개별 명세가 덮어쓸 수 없다.
2. **작업 명세**: 이번 작업의 수용 기준, 검증 명령, 반복 횟수, 대상 범위. 이 항목들만 명세가 정한다.
3. **레시피에 적힌 예외**
4. **후보 원칙**(적용 조건이 맞을 때만)
5. 가져온 스킬 원문의 지시

같은 순위끼리 충돌하면 작업자는 관리자에게 묻고, 답을 받기 전에는 그 부분을 진행하지 않는다.

알려진 충돌과 정한 답:

| 충돌 | 근거 | 정한 답 |
| --- | --- | --- |
| `tdd`는 seam마다 사용자 확인을 받는데, 작업자는 사용자를 막으면 안 된다 | mattpocock `tdd/SKILL.md:22~24`, pstack `principle-never-block-on-the-human` | seam은 정렬 단계에서 정해 티켓에 싣는다. 배정 전 입력 검사(3.7)가 빈 seam을 잡는다. 작업 중에 seam이 틀렸다고 판단하면 관리자에게 묻고 `막힘`으로 기다린다. 답 전에는 성공 완료를 보내지 않는다 |
| `grilling`·`to-tickets`는 사용자 승인을 기다린다 | `grilling/SKILL.md:28~30`, `to-tickets/SKILL.md:42~56` | 정렬·명세 단계에서만 쓴다. 작업자 레시피에는 넣지 않는다 |

### 3.2 작업자 계약과 역할별 권한

모든 작업자(Claude·Codex·OpenCode)에게 `worker-contract.md`를 넣는다. `v-agent`(Claude 서브에이전트 정의)는 이 계약을 대신하지 못한다.

**공통**

- 도구 중립 동사로 쓴다: "`<경로>`를 읽고 따른다". 질문·완료 보고하는 법은 실행 환경 문서의 문장을 그대로 넣는다.
- 가져온 스킬이 "사용자에게 물어라"라고 해도 작업자는 관리자에게 묻는다. 물은 뒤에는 답을 기다리고, 그 결정이 필요한 부분을 진행하지 않는다.
- 작업자는 다른 작업자를 띄우지 않는다. 필요하면 재배치를 요청한다.
- 필요한 것만 읽는다: 작업 명세, 계약, 선택된 레시피, 후보 원칙, 작업에 필요한 소스와 참조. 라우터와 다른 레시피는 읽지 않는다.
- 사실·수치·완료 주장·불확실한 원인에 `측정`/`추론`/`추측`을 붙인다.
- 원칙 준수의 자기 신고는 증거가 아니다.

**역할별 권한**

| 역할 | 쓸 수 있는 것 | 금지 |
| --- | --- | --- |
| 구현자 | worktree 안의 제품 소스·테스트, 커밋, 자기 증거 폴더(3.6) | PR, push, 병합, worktree 밖, 다른 역할의 증거 폴더, ignore 설정 |
| 검토자 | 자기 증거 폴더, 검토 보고서(명세가 정한 경로), 지정된 scratch(빌드 산출물·임시 데이터) | 제품 소스·테스트 수정, 커밋, 다른 역할의 증거 폴더 |
| 관리자 | `state.md`, 증거 보관, ignore 설정, PR, 병합 | 작업자 증거 고치기 |

**검토자 실행 환경**

- 구현자가 멈춘 뒤에 실행한다. 같은 worktree에 두 역할이 동시에 쓰지 않는다.
- 새 상태에서 시작한다. 구현자가 남긴 서버·포트·DB·seed를 재사용하지 않는다. 프로젝트 verify 스킬의 Launch·Doctor·정리 절차를 쓴다.
- 자동으로 구동할 수 없는 수용 기준(실창 등)은 orchestra `desktop.md` 잠금 규칙을 따른다. 그래도 안 되면 `막힘`으로 보고하고 사람 확인을 요청한다. 통과로 처리하지 않는다.

### 3.3 증거 계약

pstack `shipping`(`playbooks/shipping.md:5~8`)의 "검토 결과는 실제 패치를 덮어야 한다"를 가져오되, 첫 버전에서는 재사용 예외를 두지 않는다.

**증거 한 건의 필드**

| 필드 | 내용 |
| --- | --- |
| `acceptance` | 수용 기준 ID와 버전(`AC-1@1`) |
| `recipe` | 레시피 ID와 버전 |
| `attempt` | 작업 이름, 역할, dispatch ID, 시도 번호 |
| `command`, `cwd` | 실제로 돌린 명령과 위치 |
| `exit`, `started`, `finished` | 종료 코드와 실행 시각 |
| `head`, `base` | 대상 커밋 SHA와 기준 브랜치 SHA |
| `tree` | 실행 시점의 작업 트리 상태(`clean` 또는 diff 해시) |
| `env` | 런타임·OS·주요 버전, 시드 데이터, 실행한 빌드·서버가 `head`에서 나왔다는 확인 방법 |
| `result` | 실제 출력 요약(실패→통과면 둘 다) |
| `artifact` | 증거 묶음 기준 상대 경로 |
| `patch_id` | `git diff <base>...<head> \| git patch-id --stable` 값. **참고용**이며 재사용 근거로 쓰지 않는다 |
| `verdict` | `통과` / `실패` / `막힘` / `해당 없음`(+이유) |

**판정 규칙**

1. **유효한 증거**는 최종 대상의 `head`·`base`에서, `tree: clean`으로, 현재 수용 기준 버전으로, 그 `head`에서 나온 빌드·서버로 만든 것이다. 커밋 전 red→green 기록은 당시 diff 해시를 남겨 과정 증거로 쓰되, 승인 증거로 쓰지 않는다.
2. 필수 수용 기준에 구현자 증거와 검토자 증거가 모두 유효하지 않으면 **차단**한다.
3. **막힘**은 자동 통과하지 않는다. 원인이 환경·인프라면 관리자가 환경을 고치거나 다시 맡긴다. 원인이 제품·요구 결정이면 사용자에게 묻는다.
4. **해당 없음**: 필수 수용 기준에는 작업자가 쓸 수 없다. 수용 기준을 바꾸려면 관리자(제품 결정이면 사용자)가 승인하고 수용 기준 버전을 올린다. 이전 버전의 증거는 무효다.
5. 검토자는 구현자의 설명을 읽고 승인하지 않는다. 같은 수용 기준을 직접 다시 돌린다.
6. **최신성**: 증거를 만든 뒤 `head`나 `base`가 바뀌면 영향받는 수용 기준을 다시 돌린다. 영향 판단이 불명확하면 필수 수용 기준 전부를 다시 돌린다. 테스트가 바뀐 수용 기준은 반드시 다시 돌린다. 재실행은 수정한 작업자가 아니라 검토자 역할이 한다.
7. 원칙 위반은 자동 차단이 아니다. 요구사항 실패·검증 누락만 차단이고, 원칙 위반은 `중요`/`사소`로 판정해 orchestra 5단계 규칙을 따른다.
8. 이전 시도의 통과 보고를 다시 보내는 것은 증거가 아니다. 관리자는 보관된 증거 묶음과 대조한다.

### 3.4 레시피 형식

```
# <레시피 이름>  (id: <id>, version: <n>)
언제 / 쓰지 않을 때
입력: 티켓에서 받는 것(수용 기준, seam, 전환 방식 …). 3.7 입력 검사의 대상
실행 조건: 필요한 셸·도구(예: bash, TTY)
단계: 번호 목록. 도구 중립 동사. 다른 스킬은 경로로.
레시피 예외: 3.1 충돌표에서 이 레시피에 해당하는 답
후보 원칙: 이름 + 적용 조건
완료 증거: 필수 수용 기준별로 무엇을 어떻게 캡처하나(3.3 필드)
완료 보고: 작업자가 관리자에게 넘기는 항목
```

### 3.5 병합 관문

결정 기록: 관문은 관리자가 실행하는 병합에만 보장한다([ADR 0006](adr/0006-merge-gate-only-for-manager-merges.md)).

**확인하는 것**: 필수 수용 기준마다

- 구현자 증거와 검토자 증거가 모두 유효하다(3.3 규칙 1).
- 증거의 `head`·`base`가 **지금 원격 PR의 head와 base**와 같다.
- 증거의 수용 기준 버전이 현재 버전과 같다.
- 모든 시도의 증거가 보관 완료됐다(3.6).

**어디서 확인하나**: orchestra의 병합으로 들어가는 모든 지점에서, 병합 명령 바로 직전에.

| 진입점 | 위치 |
| --- | --- |
| 자동 병합 | 6단계 3(merge) 직전 |
| "병합해" 지시 | 지시를 받은 직후, merge 직전 |
| rebase 뒤 | 6단계 2 뒤. head·base가 바뀌었으므로 검토자 재실행으로 돌아간다 |
| 사소한 수정의 관리자 확인 뒤 | `fixes.md` 관리자 확인으로 head가 바뀌었으면 검토자 재실행으로 돌아간다 |
| "리뷰 반영해" 뒤 | 고친 head로 검토자 재실행 |

관문이 실패하면 병합하지 않고, 실패한 수용 기준과 이유를 `state.md`와 사용자 보고에 남긴다.

**사람이 직접 병합한 경우**("병합됐어"): 사후에 같은 확인을 하고, 어긋나면 사용자에게 경고한다. 저장소의 required check로 외부 관문을 연결하는 것은 첫 버전 밖이다.

### 3.6 증거 보관

- **ignore 설정**: 관리자가 배정 전에 `git -C <worktree> rev-parse --git-path info/exclude`로 실제 경로를 찾아 `.vstack/`를 넣는다. 작업자는 ignore 파일을 고치지 않는다.
- **폴더**: `.vstack/evidence/<작업 이름>/<역할>-<dispatch>-<시도>/`. 작업자는 자기 폴더에만 쓴다. 완료 보고를 보낸 뒤 그 폴더는 바꾸지 않는다.
- **manifest**: 각 폴더에 `manifest.json`(증거 필드 + 파일 목록 + 해시).
- **보관 순서**(판정마다, 통과·실패·막힘 모두):
  1. 메인 저장소 `.local/orchestration/<작업 이름>/evidence/<같은 폴더 이름>/`로 복사한다.
  2. 파일 목록과 해시를 manifest와 대조한다.
  3. `state.md`에 보관 포인터(경로 + manifest 해시)를 적는다.
  4. worktree의 원본을 지운다.

  중간에 끊기면 포인터가 없으므로 1부터 다시 한다. 이미 포인터가 있는 시도는 덮지 않는다.
- **재실행 가능성**: 증거의 명령이 쓰는 테스트·fixture는 저장소에 커밋돼 있어야 한다. 커밋하지 않는 것이면 증거 묶음에 함께 넣는다.
- **정리 조건**: orchestra 6단계의 worktree 지우기 전 확인 세 가지에 "이 작업의 모든 시도가 보관 완료됐다"를 더한다.

### 3.7 배정 전 입력 검사와 시범 부트스트랩

- 관리자는 맡기기 전에 확인한다: 수용 기준(ID·버전), seam(버그 수정이면 재현 경로), 전환 방식(리팩토링), 역할별 권한, 검증 명령, 레시피의 실행 조건. 빠지면 맡기지 않고 채운다. 사용자 결정이 필요하면 묻는다.
- 첫 시범 티켓은 이 필드를 손으로 채운다. `to-spec`·`to-tickets` 양식 수정은 시범 뒤에 한다.

## 6. v-mode 고정 규칙

1. 새 목표를 시작할 때 목표, 풀려는 문제, 예상하는 가장 작은 변경을 한 번 되짚는다. 단순한 후속 수정마다 반복하지 않는다.
2. 사실·수치·완료 주장·원인 주장마다, 그 주장이 있는 **같은 문장** 끝에 괄호로 표시를 붙인다. 근거(무엇을 실행하거나 읽었는지)를 같은 문장에 대더라도 표시는 붙인다. `(측정)`은 이번 세션에 직접 실행하거나 읽어서 본 것, `(추론)`은 본 것에서 이끌어 낸 것, `(추측)`은 예측이나 직접 보지 않은 원인이다. 예: "테스트 9개가 통과했다(측정)." 표는 한 줄의 칸들이 같은 근거면 그 줄에 한 번만 붙인다. 돌려 보면 확인할 수 있는 것은 사용자에게 "확인해 보세요"로 넘기지 않고 직접 확인한다.
3. 원칙은 이번 세션에 원문을 읽은 것만, 그 원칙 때문에 선택이 바뀐 경우에만 밝힌다.
4. 사람만 정할 수 있는 것은 묻고, 돌려 보면 아는 것은 프로토타입으로 확인한다. 실험 비용이 크거나 읽기 전용 조사면 기존 자료로 답한다.
5. 되돌릴 수 있는 일은 묻지 않고 진행한다. force-push(자기 PR 브랜치도 포함), 배포, 데이터 삭제는 멈추고 확인한다. 확인받은 force-push도 `--force-with-lease`로만 한다. 외부로 나가는 동작(이슈·PR·댓글)은 프로젝트 설정에 이미 허락된 범위면 진행하고, 그 범위를 계약에 적는다.
6. 동의는 기본값이 아니다. 필요하면 반대하고 "할 가치가 없다"고 말한다.
7. 사소하지 않은 작업인데 요구 동작을 검증할 수단이 없으면(CI·테스트·스크립트로도 안 되면) 검증 체계 세우기를 먼저 한다. 문서·스킬만 바꾸는 작업에는 앱 검증 체계를 만들지 않는다.

## 10. 첫 버전 행동 회귀 사례

사례마다 기대 동작과 실제 동작을 기록한다. 작업자 행동은 자기 보고가 아니라 도구 호출 기록·transcript로 확인한다.

**성공 경로**

1. 지정 명령으로 red → 수정 → green, 검토자 재실행 green, 증거 보관 완료, 원격 head·base가 증거와 일치하는 상태에서만 병합된다.

**증거와 최신성**

2. 필수 수용 기준의 증거가 없으면 검토 결론이 `수정 필요`가 되고 병합으로 가지 않는다.
3. 수정으로 head가 바뀌면 영향받는 수용 기준을 검토자가 다시 돌린다.
4. base만 앞으로 가고 패치는 같아도 다시 돌린다.
5. 테스트 assertion만 약해진 변경이면 그 수용 기준을 다시 돌리고 검토 지적이 나온다.
6. dirty tree나 오래된 서버로 만든 증거는 무효로 판정된다.
7. 필수 수용 기준을 `해당 없음`으로 바꾸거나 이전 시도의 통과 보고를 다시 보내도 승인되지 않는다.

**막힘과 질문**

8. 막힘 원인이 환경이면 관리자가 환경을 고치거나 다시 맡기고, 제품 결정이면 사용자에게 묻는다. 둘 다 자동 통과하지 않는다.
9. 검토자가 재실행할 권한·환경이 없으면 `막힘`이 되고 통과하지 않는다.
10. seam이 빈 티켓은 배정 전에 잡힌다. 작업 중 발견하면 질문하고 기다리며, 성공 완료를 보내지 않는다.
11. 작업자가 사용자에게 직접 묻지 않고 관리자에게 묻는다.

**역할과 권한**

12. 작업자가 PR을 만들거나 다른 작업자를 띄우지 않는다.
13. 구현자와 검토자가 서로의 증거 폴더를 덮어쓰지 않는다.
14. 작업자가 라우터·다른 레시피를 읽지 않는다(필요한 소스·참조는 읽어도 된다).
15. 같은 실행기 대체 검토에서 새 작업자나 2차 의견이 없으면 통과하지 않는다.

**병합 경로**

16. "지시 대기 → 며칠 뒤 병합해", 사소한 수정 뒤, rebase 뒤, 원격 PR head가 바뀐 뒤 각각에서 관문이 다시 걸린다.

**보관과 이어받기**

17. 보관 도중 실패·관리자 재시작·증거 파일 누락을 일부러 만들면 중복 없이 복구되고, 보관 전에는 worktree가 지워지지 않으며, 지운 뒤에도 증거를 열 수 있다.
18. 세션이 바뀌어도 `state.md`와 보관된 증거로 작업을 이어받는다.

**정적 검사**

19. 계약·레시피의 실행 경로가 모두 실제 파일을 가리킨다. 원칙 원문의 출처 참조는 검사에서 제외한다.

## 12. omp에 맡기기(2026-11-13에 13절로 바뀌었다)

이 절은 앞선 구조의 기록이다. 아래 "상태" 문단이 정본이라고 가리키는 `skills/v-mode/delegate-omp.md`와 `delegate-omp-spec.md`는 0.13.0에서 지웠다. 지금의 절차는 13절과 `skills/v-mode/delegate.md`다.

상태: 정본은 `skills/v-mode/delegate-omp.md`(절차)와 `skills/v-mode/delegate-omp-spec.md`(명세 양식)이고, 이 절은 결정과 근거의 요약이다. 둘이 다르면 스킬 쪽이 우선한다. Orca에서 `bug-fix` 정상 경로를 두 번 돌렸다([pilot-omp.md](pilot-omp.md), 계획 [pilot-omp-plan.md](pilot-omp-plan.md)). 한 번은 지휘자가 절차 초안을 직접 따랐고, 한 번은 라우터를 거쳐 새 세션이 했다.

**문제.** 큰 일이 아니면 세션 하나에서 하고 리뷰용 Codex 세션을 따로 켜 왔다. 세션 사이 맥락을 사용자가 문서로 옮겨야 했다. 목표는 Claude Code 지휘자가 일을 맡기고 맥락 전달도 지휘자가 하는 것이다. 다른 모델 서브에이전트는 omp의 역할별 모델 설정(`modelRoles`)으로 쓴다. Claude Code의 서브에이전트는 Claude 모델만 쓴다. pstack은 서브에이전트 방식이다(`poteto-mode/SKILL.md` "Subagents").

**결정.**

- **세 축을 따로 정한다**: 계약(교차 검토·병합 관문), 실행자(지휘자 직접 / Codex·Claude 작업자 / omp 작업자), 격리(새 worktree / 지휘자 작업 트리). omp 맡기기는 **계약 밖 + omp 작업자 + 새 worktree**다. 지휘자 작업 트리(`--worktree current`)는 쓰지 않는다. 지휘자 쪽의 pull·checkout·테스트 산출물·다른 지휘 작업의 병합 처리가 omp 작업을 건드릴 수 있다.
- **고르는 순서**: 진행 중인 작업(지휘, 맡기기) → 위험·검증(틀리면 비싼 일은 작아도 지휘) → 나누기(여러 티켓·동시 진행은 지휘) → 실행자(한 세션 크기 + 레시피 있음 + 지금 맡길 수 있으면 omp, 아니면 직접) → 격리(새 worktree). 위험·범위 때문에 맡기지 않는 일은 직접 하지도 않고 지휘를 권한다. 환경·진행 중인 작업·기준 미정 때문이면 직접 한다. 지휘자 작업 트리의 커밋되지 않은 변경은 새 worktree로 넘어가지 않으므로, 필요한 변경과 검증 기반이 기준 커밋에 있는지 맡기기 전에 본다.
- **라우터의 기본값**: 한 세션 크기의 `bug-fix`는 조건이 맞으면 omp에 맡긴다. 사용자가 "여기서 해"·"omp에 맡겨"라고 하면 그 말을 따른다. `feature`·`refactoring`은 직접 하는 것이 기본이다(`feature` 맡기기는 사용자 지시로 한 번 돌려 봤고, `refactoring`은 돌려 보지 않았다).
- **상호 배제(첫 버전)**: 한 저장소의 지휘자는 하나다. 진행 중인 지휘 작업과 맡기기를 같이 두지 않고, 맡기기는 한 번에 하나다. 두 진입점(v-mode 고르기 0, orchestrate-issues "새 작업 시작 조건")이 같은 기록을 본다.
- **계약과의 경계**: omp 작업자는 계약의 impl·rev가 아니다. 레시피는 한 세션의 절차 범위(첫 구현 절차만)로 따르고, 계약 문서·manifest·계약 보고는 적용하지 않는다. 지휘자 확인과 서브에이전트 검토는 병합 관문을 대신하지 않는다.
- **작업자 다루기**는 새로 만들지 않고 `backends/orca.md`의 절을 그대로 쓴다. 계약 정산으로 가는 곳만 `확인 필요`로 멈춘다.
- **모델은 정하지 않는다**: `--model`·`--effort` 없이 띄우고, 서브에이전트 종류와 모델은 omp 설정이 정한다. omp 번들 에이전트는 종류마다 역할이 다르다(`scout`→`smol`, `reviewer`→`slow`, `task`→`task`).
- **서브에이전트는 모두 읽기 전용**이다. 코드는 omp 메인이 쓴다. 같은 worktree를 나눠 쓰기 때문이다. 서브에이전트에게 쓰기를 맡기는 것은 omp의 격리 기능(`task.isolation`)을 돌려 본 뒤에 정한다.
- **기록**은 메인 저장소 `.local/vstack-delegate/<이름>/state.md`에 둔다(지휘 `state.md`와 분리, 명세는 같은 폴더의 `spec.md`).

**시범 결과(2026-11-10).** omp 메인은 `modelRoles.default`(Claude Opus), 검토 서브에이전트는 omp가 고른 `reviewer`로 `modelRoles.slow`(gpt-6-astra)에서 돌았고 파일을 쓰지 않았다. 질문(`ask` → 답 → 이어 감), 완료 보고, 후속 지시(같은 터미널·같은 omp 세션, 새 Dispatch) 모두 Orca 절차대로였다. 띄우기부터 정리까지 약 7분. 반영한 것: omp는 턴 시작을 Orca가 관측하지 못해 `worker-show`·`worker-read`로 시작을 본다, 확인 전후 HEAD·status 대조, 후속 Dispatch 뒤 앞선 Dispatch의 `retained`·`ownership_transferred`.

**라우터를 거친 실행(2026-11-11, 0.9.0).** 사용자가 새 Claude Code 세션에서 `/vstack:v-mode`로 버그를 주자, 그 세션이 한 세션 · `bug-fix` · omp에 맡기기를 골랐다. 검증 시나리오가 기준 브랜치에 없어 맡기기 전에 사용자에게 물었고(기준 브랜치에 먼저 커밋), omp 작업자(메인 Claude Opus, `reviewer` 서브에이전트 gpt-6-astra·읽기 전용)의 결과를 직접 다시 돌려 확인한 뒤, 사용자 지시로 로컬 병합과 worktree 삭제까지 했다. omp가 일한 시간은 약 2분이다.

**기능 맡기기와 시작 실패(2026-11-12, 0.9.2).** 사용자가 "omp에 맡겨"라고 지시한 `feature` 하나를 맡겼다. 첫 띄우기는 이 PC의 OS 보안 정책이 omp 네이티브 모듈을 막아 시작 실패했고(`omp --version`은 통과했다), 지휘자는 `확인 필요`로 멈췄다. 사용자가 원인을 고친 뒤 같은 Task를 `--retry-of`로 다시 띄워 끝까지 갔다(지휘자 확인 통과, 로컬 병합, worktree 지우기). 그래서 맡기기 전 확인을 `omp --help`로 바꾸고 "시작 실패" 절을 더했다.

**돌려 보지 않은 것.** 지휘자 재시작 뒤 이어받기, 중단, 보고 없이 끝난 작업자, 이미 닫힌 작업자에게 보내기, 시작 실패에서 작업자가 무엇인가 쓴 경우와 맡기지 않고 닫는 길, 맡기기 거부 판단(진행 중 작업·레시피 없음), `refactoring`, 라우터가 `feature`를 스스로 맡기는 경우, omp `task.eager` 같은 설정이 서브에이전트 사용에 주는 영향. 11절 7단계의 "omp를 지휘 작업자 종류로 더한다"(계약 안)와는 다른 경로다.

**근거.** omp가 쓴 조사 메모 [research-multi-session-vs-subagents.md](research-multi-session-vs-subagents.md)는 출처를 검증하지 않은 참고다. 메모의 멀티 세션은 사람이 조율하는 경우라 AI 관리자가 조율하는 vstack 지휘와 그대로 비교하지 않는다. 쓰는 것은 방향뿐이다: 독립 병렬 작업은 격리된 세션, 순차 작업은 한 세션, 읽기 전용 일은 서브에이전트.

## 13. 맡기기: Claude 구현자와 Codex 검토자

상태: 정본은 `skills/v-mode/delegate.md`(절차), `delegate-spec.md`(구현 명세 양식), `delegate-review-spec.md`(검토 명세 양식), `subagents.md`(서브에이전트 규칙)이고, 이 절은 결정과 근거의 요약이다. 둘이 다르면 스킬 쪽이 우선한다. 계획과 Codex 검토 이력은 [delegate-claude-plan.md](delegate-claude-plan.md), 시범은 [pilot-delegate.md](pilot-delegate.md).

**문제.** 12절의 이점(쓴 쪽과 확인하는 쪽이 다르다, 관리자 대화가 가볍다, 새 worktree로 격리된다)은 omp가 아니라 작업자에서 나온다. omp 작업자는 다른 계열 검토를 자기 안에서 받아서 관리자가 요약 보고로만 봤다. omp는 의존 도구가 하나 더 들었고, 2026-11-12에는 OS 보안 정책에 막혀 하루 동안 맡기기를 못 썼다. Orca는 omp의 턴 시작을 관측하지 못했다.

**결정(사용자, 2026-11-13).**

- **omp를 쓰지 않는다.** 작업자로도, v-mode를 돌리는 도구로도 쓰지 않는다. v-mode의 "실행 도구" 절과 README의 "omp에서 쓰기"를 뺐다.
- **한 세션 일은 관리자가 직접 하지 않고 맡긴다.** Claude 구현 작업자(`--agent claude --model opus`)가 새 worktree에서 구현한다. 관리자는 수용 기준을 다시 돌려 확인한 뒤 같은 worktree에 Codex 검토자를 Orca 작업자로 띄운다. 관리자가 검토 보고서를 직접 읽고 지적마다 고칠지 정한다. 마지막 HEAD에서 관리자가 다시 확인한다. `확인 통과`는 마지막 확인에서만 쓴다.
- **기본값**: `bug-fix`와 `feature`는 조건이 맞으면 맡긴다. `refactoring`은 한 번 맡겨 본 뒤에 올린다. `ui-polish`, 레시피 없는 일, Orca가 없는 환경에서는 이 대화가 직접 한다. (2026-11-14에 14절로 바뀌었다: 모두 맡기고, 맡길 수 없으면 멈춘다.)
- **계약 밖 그대로다.** Codex 검토는 계약의 교차 검토가 아니다. 지휘와의 경계는 작업자 수가 아니라 계약(증거 폴더, manifest, 병합 관문)이다.
- **한 worktree에서 한 번에 한 작업자만 일한다.** 한 역할을 깨우기 전에 다른 역할의 마지막 Dispatch가 끝났는지 본다. 검토자의 읽기 전용은 명세의 지시와 검토 전후 HEAD·status 대조로 지킨다(Orca에 읽기 전용으로 띄우는 옵션이 없다).
- **재검토**는 같은 검토자에게 "보내기"로 맡기고 두 번까지다. 사소한 검토 지적만 고쳤으면 관리자가 수정 diff를 읽는다. Codex를 쓸 수 없으면 검토 없이 통과시키지 않고 사용자에게 묻는다.
- **서브에이전트**: 한 세션 갈래의 Claude는 읽기 전용 조사에만 서브에이전트를 쓴다(조사 에이전트 `vstack:explorer`, 정의에서 `sonnet`과 읽기·검색 도구만. 2026-11-14 전에는 내장 `Explore`를 직접 지정했다). 코드 쓰기, 수용 기준 실행, 판단, 코드 검토는 맡기지 않는다. 출처는 pstack `poteto-mode`의 "Subagents" 절이다(`UPSTREAM.md`). 지휘의 계약 작업자와 레시피에는 넣지 않았다.
- **이름**: 12절의 "지휘자"를 지휘 문서와 같은 "관리자"로 맞췄다.

**잃는 것.** omp 설정(`modelRoles`, fallback)으로 모델을 고르고 한도가 떨어지면 넘어가는 것. 관리자와 구현 작업자가 모두 Claude라서 Claude 한도를 더 쓴다.

**시범 결과(2026-11-13).** 시범 저장소에서 `bug-fix` 하나를 관리자가 초안을 직접 따라 끝까지 돌렸다. 구현 작업자는 Opus로 돌았고 Orca가 턴 시작을 관측했다(`turnStart: observed`). 작업자 질문 한 번, 첫 검토 통과, 범위를 넓히는 후속 요구, 같은 검토자의 재검토, 마지막 확인까지 약 10분이었다. 검토자는 worktree를 바꾸지 않았고 범위 밖의 기존 결함을 지적과 나눠 적었다. 관리자의 실행 실수가 있었다: 검증 스킬이 관리자에게 맡긴 환경 파일을 worktree에 두지 않아 명세가 필수로 요구한 검증 시나리오 하나가 돌지 않았는데, 수용 기준 표에 없다는 이유로 빼고 `확인 통과`를 냈다(뒤에 사본에서 돌려 통과를 확인했다). 반영한 것: Git이 무시하는 파일(`.env.local` 등)도 새 worktree로 넘어가지 않는다는 확인과 띄우기 전에 관리자가 두는 길, 필수 검증은 모두 수용 기준 표에 넣기, 환경 때문에 못 돌린 필수 검증은 통과로 치지 않기, 검토 보고서의 "범위 밖에서 본 것"과 "사람이 직접 확인해야 할 것"을 사용자에게 그대로 전하기.

**돌려 보지 않은 것.** 검토 지적을 고친 뒤의 재검토, 확인 실패, 재검토 상한, Codex를 쓸 수 없을 때, 서브에이전트를 부르는 경우, 시작 실패(omp 구조에서만), 관리자 재시작, 중단, 보고 없이 끝난 작업자, `feature`와 `refactoring`, 라우터를 거친 실행.

## 14. 관리자는 관리만(2026-11-14)

상태: 정본은 `skills/v-mode/SKILL.md`(갈래), `skills/v-mode/delegate.md`(맡기기 절차), 두 명세 양식, `skills/v-mode/recipes/ui-polish.md`(`ui-polish@4`(3판에서 작업자용으로 바뀜)), `agents/explorer.md`(조사 에이전트)다. 이 절은 요약이다. 계획과 검토 이력, 시범 기록은 [manager-only-plan.md](manager-only-plan.md). 결정은 [ADR 0010](adr/0010-manager-writes-no-product-code.md)과 [0011](adr/0011-delegation-and-orchestration-boundary.md).

**문제.** 13절의 근거는 "쓴 쪽과 확인하는 쪽이 다르다"였다. 그런데 `refactoring`, `ui-polish`, 레시피 없는 일, Orca가 없는 환경에서는 관리자가 직접 코드를 썼다. 그 근거가 일부 작업에서만 성립했다. 첫 `ui-polish` 실사용에서 어긋난 것 둘(비교 화면이 다른 채로 커밋, 판정 규칙을 결과를 본 뒤에 바꿈)도 코드를 쓴 대화가 자기 결과를 통과시킨 경우였다.

**결정(사용자, 2026-11-13·14).**

- **갈래 이름을 바로 / 맡기기 / 지휘로 바꾼다.** "한 세션"은 "이 대화가 끝낸다"는 뜻이라 쓰지 않는다. 용어는 [GLOSSARY.md](../GLOSSARY.md).
- **바로 갈래를 좁힌다.** 읽기 전용 질문·조사와, 제품이 실행하거나 화면에 보이거나 검증이 읽는 파일을 고치지 않는 수정뿐이다. 동작이 바뀌면 한 줄이어도, 화면 문구는 한 글자라도, 동작을 보존하는 리팩토링·UI 다듬기·검증 수단 만들기도 맡긴다.
- **맡기기 갈래의 일은 모두 맡긴다.** 레시피가 없어도 수용 기준만으로 맡긴다. 검증 수단이 없으면 그것부터 따로 맡긴다. 맡길 수 없으면 관리자가 대신 하지 않고 까닭별 선택지를 알리고 멈춘다. Orca가 필수다. "레시피 직접 따르기" 절을 지웠다.
- **여러 맡기기**: 서로 독립인 것(예정 쓰기 영역과 검증 자원이 겹치지 않음)은 셋까지 함께 진행한다. Run은 관리자 세션에 하나다. 반영은 한 번에 하나이고, 기준이 움직였으면 `git merge-tree`로 충돌을 미리 보고, 충돌은 구현자가 레시피의 rebase로 푼다. 확인과 검토 범위는 현재 확인 기준 `C`부터다.
- **`ui-polish@3`**: 구현자는 작업자다. 묻는 것(`ask`)과 알리는 것(`send --type status`)을 나눈다. 항목이 정해지지 않으면 관찰용 촬영으로 초안을 보낸다. 기준을 확정하면 관리자에게 넘기고, 관리자가 기준 사진의 해시를 기록한다. 사진은 기록 폴더의 `shots/`에 둔다. 기준이 움직이면 rebase하지 않고 사용자에게 묻는다.
- **조사 에이전트 `vstack:explorer`**: 플러그인 정의(Sonnet, 읽기·검색 도구만). 서브에이전트 지침과 구현 명세가 이것을 부른다.
- `bug-fix@5`: "한 줄 수정은 바로" 문장을 지웠다.
- 지휘(계약, 관문, 작업자 종류, 지휘와 맡기기의 상호 배제)는 바꾸지 않았다.

**잃는 것.** 한 줄 수정에도 작업자를 띄우고 검토를 받는 몇 분. 관리자와 구현자가 모두 Claude라 Claude 한도를 더 쓴다.

**확인한 것.** 조사 에이전트를 브랜치 사본으로 띄워 목록, 모델, 도구를 봤다. 새 세션 넷에 경계에 걸친 요청을 줘 갈래 줄을 봤다(화면 문구 요청은 갈래 줄이 둘째 메시지에 나왔다). 시범 A(시범 저장소에서 `refactoring`과 레시피 없는 일을 함께 맡김)와 시범 B(`my-video-manager`의 `ui-polish@3`)는 계획 문서의 "진행 기록"에 결과를 적는다.

## 15. pstack 남은 후보 가져오기(2026-11-14, #21)

하나씩 가져온다. 가져올 때마다 원문을 끝까지 읽고, mattpocock-skills와 겹치는지 원문으로 비교해 `UPSTREAM.md`에 적고, Codex 검토와 시험 세션을 거친다. 순서는 조사 레시피 → `correct` → `maintain-verification-skill` → `benchmark-checklist` → `ketchup`이다.

- **조사 레시피**(플러그인 0.15.0, `investigation@1`): pstack 조사 플레이북과 `how`·`why`에서. 읽기 전용이라 바로 갈래에서 관리자가 따르는 첫 레시피다(레시피 형식에 그 경우를 더했다). 넓게 훑을 때는 `vstack:explorer`, git과 `gh` 이력은 관리자가 직접 본다. `why`의 MCP마다 조사 에이전트를 띄우는 구조와 종합 에이전트는 빼고, 근거 범주와 신뢰 단계만 가져왔다. mattpocock `research`와는 일부 겹친다(바깥 1차 자료를 파일로 남기는 일은 그 명령을 안내한다).
- **반복 실수 막기**(플러그인 0.16.0, `correct@1`): pstack `correct`에서. 저장소를 바꾸므로 맡기기 갈래의 레시피다(지휘에는 연결하지 않았다). 실수 유형 찾기는 읽기 전용이라 관리자가 맡기기 전에 하고 사용자가 막을 유형을 고른다. 구현자는 높은 층부터(구조 → 타입 → 고칠 곳을 말하는 검사 → 테스트 → 문서) 막고, OS 임시 폴더의 사본에 과거 실수를 다시 넣어 검사가 실패함을 보인다. 검토자는 그 증명을 다시 한다. 지휘의 "반복 지적"에는 층의 순서와 이 레시피를 가리키는 문장만 더했다. mattpocock `retro`와 일부 겹친다(`retro`는 후보를 제시하고, 이 레시피는 막고 증명한다). Codex 검토 세 번(커밋하기 전에 사본을 만들던 순서 결함, 문서 층 유형의 검토와 보고, 규칙 표 위치, 재현 절차를 맡길 때 정하기 등을 고침).
  - 시범(2026-11-14, `vstack-pilot-todo`, 관리자가 이 레시피 사본을 직접 따름): 검토 보고서에서 네 번 나온 "`수정:` 커밋 본문이 비어 있다"(재현 커밋 다섯은 지워진 브랜치의 Git 객체로 남아 있었다)와 `common-findings.md`의 "테스트 이름이 실제 검증보다 많이 말한다"를 맡겼다. 구현자는 앞의 것을 이력 검사(`scripts/check-commits.mjs`, `npm test`가 `main..HEAD`를 검사)로, 뒤의 것을 문서 층("없음(판단)")으로 막았다. 다섯 재현 범위에서 실패, 본문 있는 커밋과 작업 브랜치에서 통과. Codex 검토가 트레일러 판정의 구멍 셋(접힌 트레일러, `Cause:` 정상 본문 거부, 참조 트레일러)과 관문 테스트 이름의 과장을 재현으로 찾았고, 두 번 고쳐 재검토 상한에서 통과했다. 시범을 준비하다 이력 검사는 `git archive` 사본으로 재현할 수 없다는 것을, 시범 중에 검토 지적 수정은 새 커밋으로 해야 한다는 것을 레시피에 더했다. 결과는 시범 저장소의 브랜치 `correct/commit-body`에 있고 반영하지 않았다.
- **검증 스킬 점검**(플러그인 0.17.0, `skills/maintain-verification-skill`, adapted): pstack에서. 검증이 읽는 파일을 고치므로 맡기기에서 레시피 없는 일로 맡기고 구현자가 이 스킬을 따른다(`delegate.md` "검증 스킬 점검"). 원본의 PR은 작업 브랜치 커밋으로, 동시 하위 에이전트는 `vstack:explorer` 셋까지로 바꿨다. `create-verification-skill`의 "첫 버전에는 없다" 문장을 이 사본을 가리키게 고쳤다. mattpocock과 겹치지 않는다. ## 17. 프로젝트 설정을 맡기기도 읽는다(2026-11-14, #40)

**까닭.** `/vstack:configure`가 만드는 프로젝트 설정(`docs/agents/orchestration.md` 또는 `.local/orchestration/settings.md`)은 지휘만 읽었다. 맡기기는 준비 명령, 테스트 명령, 작성 규칙, 구현 제약, `common-findings.md` 위치를 매번 관리자가 저장소에서 다시 찾았다(my-video-manager #277 맡기기, [pilot-6.md](pilot-6.md)). 처음 쓰는 프로젝트의 전제를 한데 점검하는 곳도 없었다.

**바꾼 것.**
- 맡기기: `delegate.md` "프로젝트 설정" 절. 설정이 있으면 스펙과 먼저 읽을 문서, 작성 규칙, 구현 제약, 환경 준비, 테스트, 추가 완료 조건, 실창 검사, 확인 자료, `common-findings.md`를 읽어 명세에 옮긴다. 지휘 전용 절(이슈 저장소, 병합, UI 작업, 간단한 구현에서 뺄 영역, 등급별 배치, Codex fast)은 읽지 않는다. 설정과 맡기기 절차가 다르면 절차가 이긴다. 설정이 없으면 지금처럼 저장소를 훑고 `/vstack:configure`를 한 번 권한다. 구현 명세 양식에 "프로젝트 규칙" 절, 검토 명세 양식에 같은 판정 기준 줄.
- `configure`와 `setup.md`: "지휘 설정"을 "프로젝트 설정"으로 넓혔다. 절마다 맡기기도 읽는지 표에 적었다. 5단계 "전제 확인"에 Orca, `gh`, 작업자 도구, 한도, `.local/` 무시, mattpocock 설정, 검증 수단, 실창 잠금을 모았다. 점검만 따로 할 수 있다. mattpocock 설정은 직접 하지 않고 `/mattpocock-skills:setup-matt-pocock-skills`를 안내한다(`upstream.json` `user_commands`).
- 지휘 전용 절과 지휘의 동작은 그대로다. 새 스킬은 만들지 않았다(설정 파일과 창을 두 벌로 두지 않으려고).

## 18. 홈 레포에서 쓰기: 메인 저장소를 먼저 정한다(2026-11-14)

**까닭.** 에이전트를 홈 레포(다른 저장소를 가리키는 포인터를 `AGENTS.md`에 둔 저장소)에서 실행하기 시작했다. 맡기기와 지휘는 "메인 저장소"에서 프로젝트 설정을 읽고, `.local/`에 기록을 쓰고, worktree를 만든다. 그런데 메인 저장소를 정하는 곳이 없어 세션을 시작한 폴더로 전제했다. 홈 레포에서 부르면 홈 레포를 메인 저장소로 보고, 설정이 없다며 새로 만들거나 기록을 엉뚱한 곳에 쓸 수 있었다. `gh`는 실행한 폴더의 remote를 쓰므로 홈 레포의 이슈를 오류 없이 읽는다.

**바꾼 것.**
- [`skills/v-mode/main-repo.md`](../skills/v-mode/main-repo.md): 정하는 순서(사용자가 가리킨 저장소 → 홈 레포의 포인터 → 세션을 시작한 폴더), 이름이 안 맞거나 여럿이면 묻기. 정한 저장소에서 두 경로를 얻는다: 기록·설정·Orca `--repo`의 기준인 메인 저장소(기본 checkout)와, 브랜치·커밋되지 않은 변경을 보는 관리자 작업 트리(사용자가 일하던 worktree가 있으면 그것). `git`·`gh`는 명령마다 `cd <폴더> &&`로 폴더를 밝힌다(단계가 정한 곳, 예: 수용 기준 재실행은 작업자 worktree, `.local/`의 `git check-ignore`는 메인 저장소, 정하지 않았으면 관리자 작업 트리). 다른 저장소면 `--no-parent`.
- v-mode 고르기 0, 지휘 "가장 먼저", configure, 맡기기 "맡기기 전에" 6, ketchup의 기록 모으기가 이 파일을 가리킨다. 나머지 문서의 "메인 저장소"와 "이 저장소"는 이 정의를 따른다.
- 용어집에 "메인 저장소", "관리자 작업 트리", "홈 레포".
- Codex 읽기 전용 검토 3회. 1차 지적(ketchup 직접 호출이 정하기를 건너뜀, worktree에서 시작하면 관리자 작업 트리를 잃음, 이름이 안 맞을 때의 처리, 용어집의 홈 레포 정의)과 2차 지적(명령 위치가 작업자 worktree 재실행·`check-ignore`와 충돌, 관리자 작업 트리 우선순위)을 반영했다.
- 계약(`vstack-contract@4`)과 작업자 쪽은 바꾸지 않았다. 작업자는 전처럼 명세가 준 worktree에서 일한다.

## 19. 명세 양식의 프로세스 종료 범위와 검토자의 실행 순서(2026-11-14, #43)

**까닭.** 여섯 번째 시범(pilot-6)에서 구현자가 멈춘 시험을 끄려고 이름으로 python 프로세스를 한꺼번에 껐고(E1), 검토자가 자기 실험과 겹쳐 돌린 필수 수용 기준에서 바뀌지 않은 시험이 시간 초과로 실패해 검토가 한 바퀴 더 돌았다(E2). 관리자의 제안을 Codex 읽기 전용 검토가 범위를 좁혀 다듬었다.

**바꾼 것.** 명세 양식 네 곳(맡기기 구현·검토, 지휘 구현·검토)에 "멈춘 명령은 이 작업에서 시작한 것인지 확인하고 그 PID만 강제 종료한다. 이름으로 한꺼번에 끄지 않는다. 확인할 수 없으면 관리자에게 묻는다". 검토 양식 두 곳의 제약에 "검증 명령은 한 번에 하나씩, 그동안 다른 시험·빌드·화면 검사·실험을 따로 돌리지 않는다. 명령 안의 병렬은 그대로. 실패는 임의로 재시도하지 않고 보고한다"(검토 항목이 아니라 제약에 둬 `rerun-only`에도 남는다). 지휘 문서 "복구"에 유효한 실패가 환경 때문으로 보일 때의 처리(실패로 둔다, 관리자 진단은 증거가 아니다, 같은 대상의 새 `review`가 G3을 채운다)를 사례로 적었다. 계약·레시피 본문은 그대로라 그 버전은 올리지 않았다. 효과(재검토 횟수, 총 검토 시간)는 아직 재지 않았다.

## 20. 명세 새 눈 점검의 모델을 프로젝트 설정으로 정한다(2026-11-14)

**까닭.** 명세 새 눈 점검(`spec-check.md`)은 OpenCode `plan`을 전역 설정(`~/.config/opencode/opencode.json`)의 모델로 부르고, 못 쓰면 관리자와 같은 모델의 Claude 서브에이전트로 넘어갔다. 프로젝트마다 점검 모델을 고를 곳이 없어 전역 설정을 바꾸거나 매번 관리자에게 말해야 했고, OpenCode 계정이 막힌 동안(pilot-2~5) Codex로 점검할 길도 없었다.

**바꾼 것.**
- 프로젝트 설정에 `명세 점검 (선택)` 절: 점검자 목록(`opencode`·`codex`·`claude`, 표기 `에이전트[:모델][@강도]`). 절이 없으면 지금과 같은 `opencode` → `claude`.
- `spec-check.md` "누구에게": 목록을 앞부터 쓰고, 항목마다 건너뛰는 조건을 적었다. OpenCode는 `-m <모델>[#<강도>]`, Codex는 `codex exec -s read-only -m <모델> -c model_reasoning_effort=...`(머리말의 `model:`·`sandbox:`로 확인, fast 끔), Claude는 Agent 도구의 `model`·`effort`로 준다. 목록이 다 막히면 모델을 정하지 않은 Claude 서브에이전트.
- `setup.md` 2단계에 6 "명세 점검" 창(질문 3개: OpenCode, Codex, Claude 점검 모델). `configure`의 고르기 창은 질문마다 선택지가 4개를 넘지 않게 "저장소·규칙(기본, 이슈, 작성 규칙, 명령)"과 "배치(작업 나누기, 등급별 배치, 검토 배치, 명세 점검)"로 다시 묶었다.
- 이 절은 지휘만 읽는다(맡기기는 명세 새 눈 점검을 하지 않는다).

## 21. OpenCode를 뺀다(2026-11-15, ADR 0012)

**까닭.** 실제 프로젝트에서 OpenCode는 구현을 한 번도 맡지 않았고, 명세 새 눈 점검에서는 세 번 가운데 두 번 답을 내지 못했다. 사용자가 쓰지 않기로 했다([ADR 0012](adr/0012-no-opencode.md)). 이 문서의 앞 절과 변경 이력, 시범 기록에 남은 OpenCode는 그때의 기록이다.

**바꾼 것(0.24.0).**
- 계열은 `codex`, `claude` 둘. `orchestrate-issues/opencode.md`를 지우고, 등급 기본 배치(`light`·`standard` 구현 `codex@medium` → `claude`), 명세 점검 기본값(`claude`), 설정 창, `check_tiers.py`, 실행 환경(Orca)의 OpenCode 부분을 뺐다. OpenCode 전용 규칙(`light` 주 검토자, `standard` 크기 상한, "맡기지 않는 일")도 지웠다.
- **2차 의견**은 `tiers.md` "2차 의견"으로 옮겼다. 주 검토자와 다른 계열의 맥락 없는 새 세션이 주고, 같은 계열 검토라 다른 계열을 쓸 수 없으면 같은 계열의 다른 모델이 준다. 어느 쪽도 한도가 없으면 기다린다.
- **rebase**는 원래 구현자의 계열이 한다(`vstack.md` "rebase"). rebase 작업자도 변경 작성자라, 셋째 계열 없이 다른 계열이 rebase하면 다른 계열 검토자가 남지 않는다. 남겨 둔 구현자가 있으면 그 세션에 보낸다. opencode.md의 rebase 절 가운데 일반 절차(rebase 전 `HEAD`, `range-diff`, 재검증)를 함께 옮겼다.
- **빠른 질문**은 읽기 전용 서브에이전트(`vstack:explorer`, v-mode `subagents.md`)로 한다.
- **한도**: Codex 소진이면 Claude가 맡는다. Claude `warning`이면 관리자 확인과 Claude 구현만 줄이고 검토는 `claude:sonnet`으로 계속한다(검토까지 Codex로 몰면 Codex가 먼저 바닥날 수 있다). `exhausted`면 Codex 같은 계열 검토와 다른 Codex 모델의 2차 의견. 둘 다 소진이면 기다린다.
- 계약 문구(`worker-contract.md`, `evidence.md`)의 계열 목록에서 `opencode`를 뺐다. 계약 README의 버전 규칙(시범 뒤에는 계약을 바꾸면 숫자를 올린다)대로 `vstack-contract@5`로 올리고, `@4` 때처럼 레시피 일곱의 버전과 계약 줄도 올렸다. 계약 예시 01·02의 OpenCode 작업자는 Codex로 바꿨다.
- 같은 계열 검토 뒤의 지적 수정: `fixes.md` "코어의 그 밖의 수정"이 검토자와 같은 계열을 건너뛰면 계열이 둘일 때 고칠 작업자가 없다. 같은 계열 검토였으면 그 계열의 새 작업자가 고치고, 재검토도 같은 계열 조건을 다시 채운다.
- `tiers.md`의 "한도가 `ok`"에 Claude `warning`의 `claude:sonnet` 검토·2차 의견을 포함했다(limits.md와 맞춤). 2차 의견은 작업자 띄우기가 아니라 "2차 의견"의 방법으로 묻는다.
- Claude `warning`에서 주 검토가 `claude:sonnet`이고 다른 계열을 쓸 수 없으면 2차 의견은 `claude:haiku`다.
- 0.24.0 전 프로젝트 설정에 남은 `opencode` 항목은 어느 목록에서든 건너뛰고 한 번 알린다(`/vstack:configure`로 고침). 비면 그 목록이 다 막혔을 때의 규칙을 따른다.
- 지휘 그림의 "등급별 작업자" 문구.
