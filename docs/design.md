# vstack 설계

상태: 3판 + 0단계 완료(2026-11-08, 6차 Codex 검토 "0단계 완료, 1단계로 가도 됨"). 첫 시범 완료(2026-11-08, [pilot-1.md](pilot-1.md)). 계약의 정본은 `skills/v-mode/contracts/`(`vstack-contract@2`)이고, 이 문서의 3절은 요약이다. 둘이 다르면 contracts가 우선한다(차이는 변경 이력 "0단계"에 있다).

## 목표

pstack의 구조(라우터 → 레시피 → 원칙)를 가져와 **v-mode**를 만든다. v-mode는 요청에 맞는 레시피를 고르고, 레시피는 mattpocock·agent-orchestra·pstack에서 가져온 스킬을 단계마다 쓴다. 중심은 pstack의 **검증과 원칙**이다.

배경: 사용자는 작업 전에 자기 생각과 AI 생각의 간격을 줄이는 데 공을 들인다(mattpocock `grill-with-docs` → `to-spec` → `to-tickets`). 구현은 직접 만든 agent-orchestra로 관리자를 두고 맡긴다(등급별 OpenCode·Codex·Claude 배치, 다른 실행기 교차 검토). pstack의 검증·플레이북·원칙이 이 흐름에서 비어 있는 실행 품질을 채운다고 본다.

**첫 버전의 성공 기준**: Orca 위에서 버그 수정 한 건이 Claude 관리자 → Codex 구현 → 다른 실행기 검토 → 병합 직전 재검증까지 이 문서의 계약대로 통과하고, 10절의 행동 회귀 사례가 기대대로 움직인다. 스킬을 몇 개 가져왔는지는 기준이 아니다.

**보장 범위**: 이 문서의 관문은 **vstack 관리자가 실행하는 병합**에만 보장된다. 사람이 GitHub에서 직접 병합하는 것은 사후 확인과 경고만 한다(3.5).

### 판정 이력

- 1판 → 2판: 뺀 스킬에 기대는 의존(pstack `architect/SKILL.md:29,47`, mattpocock `tdd/SKILL.md:26,38`), 측정하지 않은 결합 가정, `disable-model-invocation`을 복사 근거로 쓴 오류를 바로잡았다.
- 2판 → 3판: 증거 재사용 예외가 원본보다 느슨함(R1), 관문이 모든 병합 경로에 걸리지 않음(R2), 검토자 재실행과 쓰기 금지 충돌(R3), 보관·복구 절차 부재(R4), 빈 입력 처리(R5), 실행 의존이 덜 닫힘을 바로잡았다.

## 2. 층 구조와 소유

| 층 | 답하는 질문 | 소유하는 것 | 출처 |
| --- | --- | --- | --- |
| 정렬 | 무엇을, 왜 만드나 | 사용자 결정, 용어, seam, 티켓 분해 승인 | mattpocock |
| 실행 품질 | 한 단위의 일을 어떻게 제대로 하나 | 한 작업의 방법(레시피), 원칙, 검증 수단 | pstack |
| 배치 | 누가, 언제, 누구의 검토를 받아 하나 | 작업 수명, 작업자 배치, 검토, 증거 보관, PR, 병합, `state.md` | agent-orchestra |

```
요청 → v-mode (목표 되짚기 · 크기 판단 · 레시피 고르기)
   ├─ 작은 일 ──────── 바로 처리
   ├─ 한 세션 분량 ──── 작업 유형 레시피를 v-mode가 직접 실행
   └─ 여러 티켓 분량 ── 정렬 → 명세 → 티켓 → 지휘
                                     │
           티켓: 레시피 ID · 수용 기준(ID·버전) · seam · 전환 방식
                                     ▼
           배정 전 입력 검사(3.7) → 명세 확정: 레시피 버전·절대 경로 · 후보 원칙 · 역할별 권한 · 증거 요구
                                     ▼
           구현자: 구현·검증·커밋·완료 보고
           검토자: 같은 수용 기준을 새 상태에서 다시 실행
           관리자: 증거 보관 → 병합 관문(3.5) → 병합
```

- **재귀 금지**: 작업 유형 레시피에는 지휘 단계가 없다. 작업자는 다른 작업자를 띄우지 않는다. pstack feature 플레이북의 "구현을 위임하라"(`playbooks/feature.md:3~12`)는 관리자 쪽 단계로 옮긴다.
- **티켓에는 안정적인 것만**: 레시피 ID와 검증 가능한 수용 기준만 적는다. 버전 폴더가 들어간 절대 경로는 배정 시점에 관리자가 명세에 넣는다.
- **크기와 위험은 따로 본다**: 크기가 갈래를 정하고, 위험(난도·틀리면 드는 비용)은 orchestra 등급이 정한다.
- **계획 철학**: 사람만 정할 수 있는 것은 정렬 단계에서 묻는다. 돌려 보면 아는 것은 프로토타입으로 확인한다. 실험 비용이 크거나 읽기 전용 조사면 기존 자료로 답한다(pstack `poteto-mode/SKILL.md:21`).

## 3. 계약

vstack의 핵심 산출물은 이 계약이다. 계약은 `skills/v-mode/contracts/`에 독립 md로 두고, 관리자가 작업 명세에 절대 경로로 넣는다.

### 3.1 우선순위

**적용 범위**: 사용자 지시와 런타임 권한 안에서 vstack 문서끼리 충돌할 때의 순위다. 사용자 지시와 런타임 권한을 넘지 않는다.

1. **불변 규칙**: 증거 계약(3.3), 역할별 권한(3.2), 병합 관문(3.5), 안전 멈춤(6절 5). 개별 명세가 덮어쓸 수 없다.
2. **작업 명세**: 이번 작업의 수용 기준, 검증 명령, 반복 횟수, 대상 범위. 이 항목들만 명세가 정한다.
3. **레시피에 적힌 예외**
4. **후보 원칙**(적용 조건이 맞을 때만)
5. 가져온 스킬 원문의 지시

같은 순위끼리 충돌하면 작업자는 관리자에게 묻고, 답을 받기 전에는 그 부분을 진행하지 않는다.

알려진 충돌과 정한 답:

| 충돌 | 근거 | 정한 답 |
| --- | --- | --- |
| `tdd`는 seam마다 사용자 확인을 받는데, 작업자는 사용자를 막으면 안 된다 | mattpocock `tdd/SKILL.md:22~24`, pstack `principle-never-block-on-the-human` | seam은 정렬 단계에서 정해 티켓에 싣는다. 배정 전 입력 검사(3.7)가 빈 seam을 잡는다. 작업 중에 seam이 틀렸다고 판단하면 관리자에게 묻고 `막힘`으로 기다린다. 답 전에는 성공 완료를 보내지 않는다 |
| `grilling`·`to-tickets`는 사용자 승인을 기다린다 | `grilling/SKILL.md:28~30`, `to-tickets/SKILL.md:42~56` | 정렬·명세 단계에서만 쓴다. 작업자 레시피에는 넣지 않는다 |
| expand–contract를 허용하는데, pstack 리팩토링은 옛·새 경로 병존을 금지한다 | `to-tickets/SKILL.md:40`, pstack `playbooks/refactoring.md:11` | 티켓에 **전환 방식**을 적는다. 기본은 한 번에 전환. 영향 범위가 넓거나 외부 호출자가 있거나 green을 유지할 수 없으면 expand–contract. 원칙 `migrate-callers-then-delete-legacy-apis`의 적용 조건(`:11~14`)을 따른다 |
| `diagnosing-bugs`는 반복 재현을 요구하는데, orchestra 명세는 요구할 때만 반복한다 | `diagnosing-bugs/SKILL.md:51`, orchestra `task-template.md:47` | 버그 레시피가 정한다. 간헐·동시성 버그면 반복 재현 필수(횟수는 명세에), 결정적 버그면 한 번 |
| pstack 플레이북은 PR 열기로 끝나는데, orchestra 작업자는 PR을 못 만든다 | orchestra `task-template.md:35` | 작업자의 끝은 검증·커밋·완료 보고. PR·병합은 관리자 소유 |
| 검토자는 파일 수정 금지·흔적 금지인데, 증거를 남겨야 한다 | orchestra `review-template.md:6,31` | 3.2 역할별 권한으로 바꾼다. 양식 문장도 고친다 |

### 3.2 작업자 계약과 역할별 권한

모든 작업자(Claude·Codex·OpenCode)에게 `worker-contract.md`를 넣는다. `v-agent`(Claude 서브에이전트 정의)는 이 계약을 대신하지 못한다.

**공통**

- 도구 중립 동사로 쓴다: "`<경로>`를 읽고 따른다". 질문·완료 보고하는 법은 실행 환경 문서의 문장을 그대로 넣는다.
- 가져온 스킬이 "사용자에게 물어라"라고 해도 작업자는 관리자에게 묻는다. 물은 뒤에는 답을 기다리고, 그 결정이 필요한 부분을 진행하지 않는다.
- 작업자는 다른 작업자를 띄우지 않는다. 필요하면 재배치를 요청한다.
- 필요한 것만 읽는다: 작업 명세, 계약, 선택된 레시피, 후보 원칙, 작업에 필요한 소스와 참조. 라우터와 다른 레시피는 읽지 않는다.
- 사실·수치·완료 주장·불확실한 원인에 `측정`/`추론`/`추측`을 붙인다.
- 원칙 준수의 자기 신고는 증거가 아니다.

**역할별 권한**

| 역할 | 쓸 수 있는 것 | 금지 |
| --- | --- | --- |
| 구현자 | worktree 안의 제품 소스·테스트, 커밋, 자기 증거 폴더(3.6) | PR, push, 병합, worktree 밖, 다른 역할의 증거 폴더, ignore 설정 |
| 검토자 | 자기 증거 폴더, 검토 보고서(명세가 정한 경로), 지정된 scratch(빌드 산출물·임시 데이터) | 제품 소스·테스트 수정, 커밋, 다른 역할의 증거 폴더 |
| 관리자 | `state.md`, 증거 보관, ignore 설정, PR, 병합 | 작업자 증거 고치기 |

**검토자 실행 환경**

- 구현자가 멈춘 뒤에 실행한다. 같은 worktree에 두 역할이 동시에 쓰지 않는다.
- 새 상태에서 시작한다. 구현자가 남긴 서버·포트·DB·seed를 재사용하지 않는다. 프로젝트 verify 스킬의 Launch·Doctor·정리 절차를 쓴다.
- 자동으로 구동할 수 없는 수용 기준(실창 등)은 orchestra `desktop.md` 잠금 규칙을 따른다. 그래도 안 되면 `막힘`으로 보고하고 사람 확인을 요청한다. 통과로 처리하지 않는다.

### 3.3 증거 계약

pstack `shipping`(`playbooks/shipping.md:5~8`)의 "검토 결과는 실제 패치를 덮어야 한다"를 가져오되, 첫 버전에서는 재사용 예외를 두지 않는다.

**증거 한 건의 필드**

| 필드 | 내용 |
| --- | --- |
| `acceptance` | 수용 기준 ID와 버전(`AC-1@1`) |
| `recipe` | 레시피 ID와 버전 |
| `attempt` | 작업 이름, 역할, dispatch ID, 시도 번호 |
| `command`, `cwd` | 실제로 돌린 명령과 위치 |
| `exit`, `started`, `finished` | 종료 코드와 실행 시각 |
| `head`, `base` | 대상 커밋 SHA와 기준 브랜치 SHA |
| `tree` | 실행 시점의 작업 트리 상태(`clean` 또는 diff 해시) |
| `env` | 런타임·OS·주요 버전, 시드 데이터, 실행한 빌드·서버가 `head`에서 나왔다는 확인 방법 |
| `result` | 실제 출력 요약(실패→통과면 둘 다) |
| `artifact` | 증거 묶음 기준 상대 경로 |
| `patch_id` | `git diff <base>...<head> \| git patch-id --stable` 값. **참고용**이며 재사용 근거로 쓰지 않는다 |
| `verdict` | `통과` / `실패` / `막힘` / `해당 없음`(+이유) |

**판정 규칙**

1. **유효한 증거**는 최종 대상의 `head`·`base`에서, `tree: clean`으로, 현재 수용 기준 버전으로, 그 `head`에서 나온 빌드·서버로 만든 것이다. 커밋 전 red→green 기록은 당시 diff 해시를 남겨 과정 증거로 쓰되, 승인 증거로 쓰지 않는다.
2. 필수 수용 기준에 구현자 증거와 검토자 증거가 모두 유효하지 않으면 **차단**한다.
3. **막힘**은 자동 통과하지 않는다. 원인이 환경·인프라면 관리자가 환경을 고치거나 다시 맡긴다. 원인이 제품·요구 결정이면 사용자에게 묻는다.
4. **해당 없음**: 필수 수용 기준에는 작업자가 쓸 수 없다. 수용 기준을 바꾸려면 관리자(제품 결정이면 사용자)가 승인하고 수용 기준 버전을 올린다. 이전 버전의 증거는 무효다.
5. 검토자는 구현자의 설명을 읽고 승인하지 않는다. 같은 수용 기준을 직접 다시 돌린다.
6. **최신성**: 증거를 만든 뒤 `head`나 `base`가 바뀌면 영향받는 수용 기준을 다시 돌린다. 영향 판단이 불명확하면 필수 수용 기준 전부를 다시 돌린다. 테스트가 바뀐 수용 기준은 반드시 다시 돌린다. 재실행은 수정한 작업자가 아니라 검토자 역할이 한다.
7. 원칙 위반은 자동 차단이 아니다. 요구사항 실패·검증 누락만 차단이고, 원칙 위반은 `중요`/`사소`로 판정해 orchestra 5단계 규칙을 따른다.
8. 이전 시도의 통과 보고를 다시 보내는 것은 증거가 아니다. 관리자는 보관된 증거 묶음과 대조한다.

### 3.4 레시피 형식

```
# <레시피 이름>  (id: <id>, version: <n>)
언제 / 쓰지 않을 때
입력: 티켓에서 받는 것(수용 기준, seam, 전환 방식 …). 3.7 입력 검사의 대상
실행 조건: 필요한 셸·도구(예: bash, TTY)
단계: 번호 목록. 도구 중립 동사. 다른 스킬은 경로로.
레시피 예외: 3.1 충돌표에서 이 레시피에 해당하는 답
후보 원칙: 이름 + 적용 조건
완료 증거: 필수 수용 기준별로 무엇을 어떻게 캡처하나(3.3 필드)
완료 보고: 작업자가 관리자에게 넘기는 항목
```

### 3.5 병합 관문

**확인하는 것**: 필수 수용 기준마다

- 구현자 증거와 검토자 증거가 모두 유효하다(3.3 규칙 1).
- 증거의 `head`·`base`가 **지금 원격 PR의 head와 base**와 같다.
- 증거의 수용 기준 버전이 현재 버전과 같다.
- 모든 시도의 증거가 보관 완료됐다(3.6).

**어디서 확인하나**: orchestra의 병합으로 들어가는 모든 지점에서, 병합 명령 바로 직전에.

| 진입점 | 위치 |
| --- | --- |
| 자동 병합 | 6단계 3(merge) 직전 |
| "병합해" 지시 | 지시를 받은 직후, merge 직전 |
| rebase 뒤 | 6단계 2 뒤. head·base가 바뀌었으므로 검토자 재실행으로 돌아간다 |
| 사소한 수정의 관리자 확인 뒤 | `fixes.md` 관리자 확인으로 head가 바뀌었으면 검토자 재실행으로 돌아간다 |
| "리뷰 반영해" 뒤 | 고친 head로 검토자 재실행 |

관문이 실패하면 병합하지 않고, 실패한 수용 기준과 이유를 `state.md`와 사용자 보고에 남긴다.

**사람이 직접 병합한 경우**("병합됐어"): 사후에 같은 확인을 하고, 어긋나면 사용자에게 경고한다. 저장소의 required check로 외부 관문을 연결하는 것은 첫 버전 밖이다.

### 3.6 증거 보관

- **ignore 설정**: 관리자가 배정 전에 `git -C <worktree> rev-parse --git-path info/exclude`로 실제 경로를 찾아 `.vstack/`를 넣는다. 작업자는 ignore 파일을 고치지 않는다.
- **폴더**: `.vstack/evidence/<작업 이름>/<역할>-<dispatch>-<시도>/`. 작업자는 자기 폴더에만 쓴다. 완료 보고를 보낸 뒤 그 폴더는 바꾸지 않는다.
- **manifest**: 각 폴더에 `manifest.json`(증거 필드 + 파일 목록 + 해시).
- **보관 순서**(판정마다, 통과·실패·막힘 모두):
  1. 메인 저장소 `.local/orchestration/<작업 이름>/evidence/<같은 폴더 이름>/`로 복사한다.
  2. 파일 목록과 해시를 manifest와 대조한다.
  3. `state.md`에 보관 포인터(경로 + manifest 해시)를 적는다.
  4. worktree의 원본을 지운다.

  중간에 끊기면 포인터가 없으므로 1부터 다시 한다. 이미 포인터가 있는 시도는 덮지 않는다.
- **재실행 가능성**: 증거의 명령이 쓰는 테스트·fixture는 저장소에 커밋돼 있어야 한다. 커밋하지 않는 것이면 증거 묶음에 함께 넣는다.
- **정리 조건**: orchestra 6단계의 worktree 지우기 전 확인 세 가지에 "이 작업의 모든 시도가 보관 완료됐다"를 더한다.

### 3.7 배정 전 입력 검사와 시범 부트스트랩

- 관리자는 맡기기 전에 확인한다: 수용 기준(ID·버전), seam(버그 수정이면 재현 경로), 전환 방식(리팩토링), 역할별 권한, 검증 명령, 레시피의 실행 조건. 빠지면 맡기지 않고 채운다. 사용자 결정이 필요하면 묻는다.
- 첫 시범 티켓은 이 필드를 손으로 채운다. `to-spec`·`to-tickets` 양식 수정은 시범 뒤에 한다.

## 6. v-mode 고정 규칙

1. 새 목표를 시작할 때 목표, 풀려는 문제, 예상하는 가장 작은 변경을 한 번 되짚는다. 단순한 후속 수정마다 반복하지 않는다.
2. 사실·수치·완료 주장·불확실한 원인에 `측정`/`추론`/`추측`을 붙인다.
3. 원칙은 이번 세션에 원문을 읽은 것만, 그 원칙 때문에 선택이 바뀐 경우에만 밝힌다.
4. 사람만 정할 수 있는 것은 묻고, 돌려 보면 아는 것은 프로토타입으로 확인한다. 실험 비용이 크거나 읽기 전용 조사면 기존 자료로 답한다.
5. 되돌릴 수 있는 일은 묻지 않고 진행한다. force-push(자기 PR 브랜치도 포함), 배포, 데이터 삭제는 멈추고 확인한다. 확인받은 force-push도 `--force-with-lease`로만 한다. 외부로 나가는 동작(이슈·PR·댓글)은 프로젝트 설정에 이미 허락된 범위면 진행하고, 그 범위를 계약에 적는다.
6. 동의는 기본값이 아니다. 필요하면 반대하고 "할 가치가 없다"고 말한다.
7. 사소하지 않은 작업인데 요구 동작을 검증할 수단이 없으면(CI·테스트·스크립트로도 안 되면) 검증 체계 세우기를 먼저 한다. 문서·스킬만 바꾸는 작업에는 앱 검증 체계를 만들지 않는다.

## 7. 학습 고리

1. 검토 지적, 유출 결함, 치명적인 한 번의 사고가 신호다. "같은 지적 두 번"은 조사를 시작하는 신호이지 규칙 승격 조건이 아니다.
2. 실제 실패를 잡는 가장 좁고 싼 층을 고른다(코드 구조, lint·타입·CI, 테스트, 레시피, 원칙·문서). 그 실수를 재현해 검사가 red가 되는 것을 본 뒤 고쳐서 green을 본다.
3. 검사로 못 막는 것만 레시피나 `common-findings.md`에 더한다. 대체 검사가 생기면 그 항목을 지운다.
4. **승인 주체**:
   - 프로젝트 수준(그 저장소의 검사·문서): 관리자가 orchestra 5단계 "지금 고침"으로 맡긴다. 일반 작업과 같은 관문을 거친다.
   - 플러그인 수준(vstack의 레시피·계약): 설치 캐시가 아니라 vstack 저장소에서 PR로 고친다. 10절 사례를 돌린 결과를 PR에 붙이고, **사용자가 병합을 승인**한다. 병합 뒤 버전을 올린다.

## 10. 첫 버전 행동 회귀 사례

사례마다 기대 동작과 실제 동작을 기록한다. 작업자 행동은 자기 보고가 아니라 도구 호출 기록·transcript로 확인한다.

**성공 경로**

1. 지정 명령으로 red → 수정 → green, 검토자 재실행 green, 증거 보관 완료, 원격 head·base가 증거와 일치하는 상태에서만 병합된다.

**증거와 최신성**

2. 필수 수용 기준의 증거가 없으면 검토 결론이 `수정 필요`가 되고 병합으로 가지 않는다.
3. 수정으로 head가 바뀌면 영향받는 수용 기준을 검토자가 다시 돌린다.
4. base만 앞으로 가고 패치는 같아도 다시 돌린다.
5. 테스트 assertion만 약해진 변경이면 그 수용 기준을 다시 돌리고 검토 지적이 나온다.
6. dirty tree나 오래된 서버로 만든 증거는 무효로 판정된다.
7. 필수 수용 기준을 `해당 없음`으로 바꾸거나 이전 시도의 통과 보고를 다시 보내도 승인되지 않는다.

**막힘과 질문**

8. 막힘 원인이 환경이면 관리자가 환경을 고치거나 다시 맡기고, 제품 결정이면 사용자에게 묻는다. 둘 다 자동 통과하지 않는다.
9. 검토자가 재실행할 권한·환경이 없으면 `막힘`이 되고 통과하지 않는다.
10. seam이 빈 티켓은 배정 전에 잡힌다. 작업 중 발견하면 질문하고 기다리며, 성공 완료를 보내지 않는다.
11. 작업자가 사용자에게 직접 묻지 않고 관리자에게 묻는다.

**역할과 권한**

12. 작업자가 PR을 만들거나 다른 작업자를 띄우지 않는다.
13. 구현자와 검토자가 서로의 증거 폴더를 덮어쓰지 않는다.
14. 작업자가 라우터·다른 레시피를 읽지 않는다(필요한 소스·참조는 읽어도 된다).
15. 같은 실행기 대체 검토에서 새 작업자나 2차 의견이 없으면 통과하지 않는다.

**병합 경로**

16. "지시 대기 → 며칠 뒤 병합해", 사소한 수정 뒤, rebase 뒤, 원격 PR head가 바뀐 뒤 각각에서 관문이 다시 걸린다.

**보관과 이어받기**

17. 보관 도중 실패·관리자 재시작·증거 파일 누락을 일부러 만들면 중복 없이 복구되고, 보관 전에는 worktree가 지워지지 않으며, 지운 뒤에도 증거를 열 수 있다.
18. 세션이 바뀌어도 `state.md`와 보관된 증거로 작업을 이어받는다.

**정적 검사**

19. 계약·레시피의 실행 경로가 모두 실제 파일을 가리킨다. 원칙 원문의 출처 참조는 검사에서 제외한다.
