## 시범으로 답할 질문

- **Q1 리팩토링 기준** — 예(예외 하나). 첫 배정(`S`, `P=미정`) → 구현 보고(`P=d11b1d3`, 관리자 대조) → 검토 명세(`S`·`P`) → rebase(`확인 대기` → `range-diff`로 새 `P`=`215c05e` → 관리자 대조 → 확정) → 지적 수정에서 후속 고정 테스트 목록 추가 → 재검토 명세까지 SHA를 줄 하나로 넘기고 매번 다시 확인했다. `P` ≠ `S`라 특성화 테스트 커밋 대응 경로를 실제로 확인했다. 확인 대기 동안 다른 시도를 맡기지 않았다. 예외: 재검토 명세 `issue-12/review-task-3.md`의 같은 줄에 후속 고정 테스트 "5개" 설명과 앞 명세에서 복사된 "후속 고정 테스트 없음"이 함께 남았다(E6). 검토자는 앞의 구체 지시대로 5개를 검증해 결과에는 영향이 없었다.
- **Q2 고정 검사** — 계획의 질문에는 예. 구현자는 pin이 지나가지 않는 사용법·오류·불러오기 순서를 찾아 특성화 테스트를 더했고 `S..P`는 테스트 파일만이었다. 그와 별개로 추가로 드러난 한계: 출력 쓰기 실패 경로(닫힌 파이프)는 구현자·첫 검토자(18입력 차등 비교)·rebase 작업자가 모두 놓쳤고, rebase 뒤 두 번째 검토자가 잡았다(E1, D3).
- **Q3 기능 레시피** — 예. 데이터 모양을 티켓대로 썼고, 동작마다 red→green 커밋과 `process/` 기록이 있었다. 두 검토자 모두 구현을 되돌린 scratch 사본에서 테스트가 실패하는지 확인했다.
- **Q4 동시 시작** — 예. 시작 조건(작업자·검토자 고르기, 검토 대기, 파일 영역 겹침 없음)을 보고 #11·#12를 띄웠다(제출 확인 16:54:51, 16:55:01로 10초 차). #13은 이슈 본문의 "#12 병합 뒤"와 SKILL.md "진행 중" 정의로 #12 `끝`까지 미뤘다.
- **Q5 작업 종류 이름** — 예. 명세에 `새 수정`·`새 리팩토링`·`새 구현`·`rebase`·`지적 수정`을 레시피 이름대로 적었다. 복구는 일어나지 않아 "레시피 첫 구현 절차의 1부터"는 보지 못했다.
- **Q6 라우터** — 사전 가설대로. 레시피가 다른 세 이슈를 한 요청으로 받아 이슈마다 하나씩 쓰고, 첫 메시지에 갈래 근거를 적었다. 요청을 나누자고 하지 않았다(D2).
- **Q7 환경 입력** — 예. `S`·`P`·새 `P` 사본 모두에 worktree `.env.local`을 복사해 `done-idempotent`가 0이었다(검토자는 `cmp`로 같음 확인). 종료 코드 3은 한 번도 나오지 않아 "3을 동작 차이와 구분"은 문서·명세 문구로만 확인했다.

## D1·D2 판단

- **D1(scratch 사본의 환경 입력)**: 이번에는 명세 문장("사본에는 worktree의 `.env.local`을 그대로 복사, 없으면 막힘(환경)")으로 충분했다. 레시피 `refactoring.md`의 사본 절차(2, 검토자 3, rebase 3)와 명세 양식 `refactoring` 줄에 "사본에 필요한 무시 파일과 그 출처" 칸을 넣는 것을 권한다. 프로젝트 설정 "환경 준비"가 그 값을 준다.
- **D2(라우터 "한 요청에 레시피 최대 하나")**: 지휘 갈래에서는 "한 티켓에 레시피 최대 하나"로 고친다. 이번 관리자는 그렇게 읽었고 문제가 없었다.
- **D3(새로 나옴, 고정이 바꾼 호출의 실패 경로)**: 리팩토링이 출력 API를 `console.log`에서 `process.stdout.write`로 바꿨다. pin과 특성화 테스트는 성공 출력만 봐서 쓰기 실패(닫힌 파이프)의 동작 차이를 지나쳤다. 레시피는 이미 "변경이 크면 같은 입력으로 전·후 출력 비교"(새 리팩토링 7)와 "새 동작이 섞였는가"(검토자 4)를 요구한다. 그래서 D3은 새 의무가 아니라 그 비교·보존 의무를 구체화하는 개선 가설이다: 바뀐 입출력 **호출**이 실패할 때의 동작도 비교 대상에 넣는다. 이번 관리자는 그 비교를 pin 통과로 갈음해 두었으므로(E1), 비교를 그대로 했다면 잡혔을지는 확인하지 못했다.

## 관리자 실행에서 나온 것

- #12 명세 새 눈 점검의 셋째 질문에 답하며 레시피의 전·후 출력 비교를 pin 통과로 갈음했다(E1). 질문에 "명세와 레시피가 갈린다"고 나왔을 때, 레시피 의무를 줄이는 쪽으로 답한 관리자 판단이다.
- 반복 지적 반영 방법을 사용자에게 묻고 답을 기다리는 동안 #13의 PR 게시·병합을 진행했다(E5).
- 보관 순서를 작은 스크립트(복사 → manifest 대조 → 승격 → 해시 출력 / 보관 확인 → 경로 확인 → 원본 삭제)로 반복했다. 시도 12개 모두 대조 일치(파일 1,095개. 검토자가 보관본을 다시 해시해 불일치 0). `python -I`는 `PYTHONIOENCODING`을 무시해 Windows 콘솔에서 한국어 출력이 cp949로 깨졌다(`iconv`로 읽음). 경로를 `/c/...`로 주면 Windows Python이 못 찾는다(`C:/...`로 줌).
- Bash 도구의 heredoc이 `\\`를 바꿔 Windows 경로가 든 파이썬 스크립트가 깨졌다. 명세 생성 스크립트는 Write 도구로 파일을 쓰고 실행했다(메모리의 기존 교훈과 같다).
- 명세 새 눈 점검이 #12에서 3개, #13에서 5개의 실질 질문을 냈다. 모두 코드·이슈·실제 실행(`done 01`)으로 답할 수 있었다.
- Codex fast는 띄울 때마다 정했고, 첫 응답의 `service_tier`(`default`/`priority`)를 매번 확인했다.
- 관리자 세션이 다시 열렸을 때 `run-current`가 이미 같은 Run을 가리켜 `run-use`가 필요 없었다.

## 고칠 것

1. `refactoring.md`의 기존 동작 보존·전후 비교 의무("새 리팩토링" 7, "검토자: review" 4)를 구체화: 바꾼 코드가 입출력 호출(출력·파일·프로세스 종료 방식)을 바꾸면, 그 호출의 **실패 경로**(닫힌 파이프, 쓰기 오류)도 원래 동작 기준과 같은지 고정하거나 비교한다. 관리자가 명세에서 이 비교를 줄이려면 그 사실과 이유를 명세와 `state.md`에 적는다(D3, E1).
2. `refactoring.md` 사본 절차와 명세 양식에 "사본에 필요한 무시 파일과 출처" 칸(D1).
3. v-mode 고정 규칙 5 또는 orchestrate-issues 6단계: 병합 승인의 PR 번호는 **저장소와 함께** 대조한다. 메시지의 링크·저장소가 지휘 중인 저장소와 다르면, 조회 결과만으로 승인을 확정하지 않고 저장소를 적어 다시 묻는다(E3).
4. 라우터 2: 지휘 갈래에서는 "티켓마다 레시피 최대 하나"(D2).
5. SKILL.md 5단계 "반복 지적": `common-findings.md`가 저장소 추적 파일일 때의 반영 방법(예: 기준 브랜치로 가는 별도 PR, 사용자 확인)과, 반영 결정이 미결일 때 그 작업의 PR·병합을 어디까지 진행할 수 있는지(E5).
6. 명세 양식을 바꿔 쓴 뒤 리팩토링 기준 줄의 칸(`S`, `P`, 후속 고정 테스트)을 `state.md`와 대조하는 점검(E6).
